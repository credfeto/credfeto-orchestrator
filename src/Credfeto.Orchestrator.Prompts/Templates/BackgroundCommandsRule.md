MANDATORY: git commit, pre-commit (direct invocation), npm test, and bun test must always be run with run_in_background: true — this is unconditional, not a per-invocation judgement call, and the container hook blocks any other way of running them regardless of how fast the run is expected to be. Immediately after starting one, WAIT for it to actually finish before doing anything else or ending your turn (see the container-vs-GitHub rule above). How to wait: if the Monitor tool is available in this session, poll with it for the command's own completion string (see the Background Tasks and Monitor Tool rules in the AI instructions for safe poll strings and the 30-minute deadline). The Monitor tool is often NOT available in these sessions (the call fails with "No such tool available: Monitor") — that is expected, not a reason to stop. When it is unavailable or refused, do NOT fall back to a shell wait loop (until/while/for loops, sleep, timeout, pgrep): the hooks deny every one of them. Instead wait with one blocking call: cfwf task wait --output <the output file named in the run_in_background result> --timeout 570, run in the foreground with the Bash tool's timeout set to 600000. Exit 0 means the command has finished, and the end of its output is printed; exit 4 means it is still running, so run the same call again. Never wait by polling (ps or pgrep checks, or repeated Reads of the output file): every poll costs a full turn, and polling has used up whole sessions without a single commit. Only if cfwf is unavailable, read the command's output file (its path is in the run_in_background result) with the Read tool, and read it again until the output shows the command has finished or a task notification for it arrives. A long stretch with no new output is normal, not a hang; only a Monitor timeout or the 30-minute deadline firing is a valid reason to stop waiting. A killed run does not just fail — it skips the target process's own cleanup (a bash EXIT trap, .NET IDisposable teardown, etc.), leaving orphaned state behind that can silently corrupt later runs. git push and other bounded git operations are NOT covered by this rule and may run in the foreground as normal, with an explicit maximum timeout (e.g. 600000ms) rather than the tool's 2-minute default. If you use the Monitor tool, never construct the poll pattern from the branch name or branch-type prefix: branch names contain slashes (e.g. perf/my-branch produces git output [perf/my-branch abc1234], not [perf abc1234]), so a pattern like \[perf\] would never match and the loop would hang forever — use a branch-agnostic string from the command's actual output instead.
MANDATORY: in a .NET repository, build, test, restore, format, measure coverage and run the build checks through the build-dotnet MCP tools (mcp__build-dotnet__*), never with raw dotnet commands: dotnet build, test, restore, clean, format, cscleanup, buildcheck, reportgenerator and package search are denied in this container, as is dotnet tool run of those tools. A role that does not have the build-dotnet tools hands that work to the role that has them (the Code Tester for tests and coverage). If the build-dotnet server is not connected at all, stop and report it as the blocker instead of running dotnet directly. An MCP job is not a shell command: wait for it with job_status, then read job_result.
A tool call that is DENIED, whether by a PreToolUse hook (the result explains why, e.g. "Blocked: git commands must use \"git -C <dir>\" format") or by Claude Code's own permission system when it is active, never ran at all - there is nothing in flight and nothing will ever notify you about it. Fix the command per the stated reason and retry it immediately, in the same turn: a denial is not "started, now wait for it", it is "never started, try again correctly". Never end a turn saying you are "waiting for it to finish" or "waiting for a completion notification" for a command that was denied - a single-shot session gets no later turn for that notification to land in, so the work you have done so far (uncommitted changes included) is abandoned the moment you stop. The two most common denial causes on git commit specifically are missing "-C <dir>" and missing run_in_background: true - satisfy both at once in one call, e.g. git -C <dir> commit -m "..." with run_in_background: true set. Likewise, background a command using the tool's own run_in_background: true parameter, never a shell-level "&" or "nohup ... &" - those are blocked outright and have caused this same denial-misread-as-in-flight failure just as often as the git example above.
