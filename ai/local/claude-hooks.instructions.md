# Claude Hooks

[Back to Local Instructions Index](index.md)

Local guardrail hooks live in `containers/base/development-full/claude-hooks/` and are wired into `~/.claude/settings.json` as `Bash` `PreToolUse` hooks, run in this order: `reject-obfuscated-commands`, `enforce-allowed-dirs`, `block-no-verify`, `enforce-git-identity`, `enforce-git-dash-c`, `block-git-worktree`, `block-dotnet-tool-install`, `enforce-ssh-host-and-key`, `enforce-background-for-long-running-commands`, `cache-gh-lookups`. `block-git-worktree` is also wired to a second, separate `PreToolUse` entry matching the native `EnterWorktree` tool (own `"matcher": "EnterWorktree"`, not part of the `Bash` chain above) — see its own section below.

## Prefer auto-correction over blocking, when it's a genuine correction

`PreToolUse` hooks can rewrite the tool call instead of only allowing/denying it, via `hookSpecificOutput.updatedInput` alongside `permissionDecision: "allow"` in the hook's JSON stdout (see Claude Code hooks documentation). When a blocked command has an unambiguous, safe rewrite available - one that fixes the actual problem rather than merely satisfying the check's syntax - prefer emitting that rewrite over blocking-and-retrying. It cuts a round trip without weakening the guardrail.

This is not a blanket instruction to auto-fix every block. A rewrite is only valid when it adds real information the hook can't already infer risk-free. It is not valid when the only available substitution would make the check pass without verifying anything - that's equivalent to not enforcing the check at all, just with extra steps. A naive version of this trap: injecting the hook's own `$PWD` verbatim for a missing `-C <dir>` would be a no-op, since plain `git` already defaults to `$PWD` when `-C` is omitted - `git -C "$PWD" status` and bare `git status` behave identically, so unconditionally auto-injecting it would make `-C` effectively optional everywhere, defeating the whole point of forcing the target repo to be explicit in the tool call. `enforce-git-dash-c` (see its own section below) auto-corrects a missing `-C` since #1357, but only escapes this trap by adding two checks the naive version above lacks: no directory-changing call (`cd`/`pushd`/`popd`, plain, wrapped, or backslash-escaped) appears anywhere in the command (this hook parses statically and can't track such a call's effect otherwise), and `git rev-parse --show-toplevel` confirms the hook's own `$PWD` sits inside a real, writable git checkout before that same `$PWD` is what gets injected. Every case the hook cannot be confident about still blocks outright, exactly as before. Before adding auto-correction to any hook, check whether the "fix" is actually a no-op like the naive version above, or has a similar unambiguous-and-verifiable guard like this one. Whatever hook you're adding this to, build `updatedInput` by merging into the original `tool_input` (`(.tool_input // {}) + {...}`), never by constructing a fresh object from scratch (`jq -n`) - the latter replaces the whole `tool_input` the call actually executes with, silently dropping sibling fields like `run_in_background`/`timeout` back to their defaults (#1367 - see [Non-ASCII / Layer 0 block](#non-ascii--layer-0-block) below for the full mechanism and a live repro).

**A rewrite does not need the original *or* the rewritten command to match any `permissions.allow` entry** - `hookSpecificOutput.permissionDecision: "allow"` genuinely overrides the allow/deny classifier for that call, rather than merely signalling "this hook has no objection" and leaving the call subject to the normal classifier afterward. Claude Code's own hooks documentation is ambiguous on this specific point (it says the decision is "honored" and "takes effect" without stating whether that supersedes classifier evaluation), so this was confirmed empirically rather than by reading the docs, when `cache-gh-lookups` was added (#1380): with `install-claude-hooks` syncing that hook onto a live host `~/.claude` (`permissions.defaultMode: "dontAsk"`, the same mode the container agents run under via `--permission-mode dontAsk`), issuing `gh api user --jq '.login'` as a real Bash tool call - a command absent from `permissions.allow` on both sides, by design (#1344) - executed with no denial and no prompt, and the cache file's creation timestamp confirmed the *rewritten* command actually ran, not the literal original. This means a rewrite hook can safely target a command with no `permissions.allow` coverage at all, as `cache-gh-lookups` does; it does not need to first ensure the rewritten text would independently pass the classifier.

## reject-obfuscated-commands

Delegates parsing to `shfmt` and applies policy to the resulting AST rather than text-scanning. Blocks in layered order (all fail closed): non-ASCII/non-printable bytes anywhere in the command (after normalizing a small fixed table of known-benign Unicode punctuation - see below), unparseable shell, disallowed AST shapes (function defs, `declare`/`export`, non-literal command names), interpreters given an inline-code flag (`bash -c`, `python3 -c`, ...), `command-blocklist` names (`eval`, `sudo`, `env`, ...), then `command-allowlist` (anything not listed is rejected).

### Extending command-allowlist (MANDATORY process)

`command-allowlist` is a security control, not a convenience list - do not extend it unilaterally by default. When a command is blocked as "not on the known-good command allowlist":

* Default (including any autonomous/non-interactive run): do **not** edit `command-allowlist` yourself. Instead log the request in the tracking issue below - check its body and comments for the command name first and skip logging if it is already present, so requests do not get duplicated.
* Only edit `command-allowlist` directly when a human is present in the session and explicitly asks for that specific command to be added now. Still run the `reject-obfuscated-commands.bats` suite afterwards and commit/push per the normal workflow.

### Widen minimally, prefer read-only where possible (MANDATORY)

Whenever adding a `permissions.allow` (or `command-allowlist`) entry, start from what is actually confirmed needed - a genuine observed denial, a documented mandate elsewhere in `ai/global`/`ai/local`, or an existing test/workflow requirement - not from what a broader-looking existing entry might suggest is fine to copy. `Bash(gh pr *)`/`Bash(gh issue *)` being blanket wildcards is not license to add `Bash(gh api *)`/`Bash(gh project *)` the same way by default: each command's actual blast radius differs. Confirmed the hard way on #1344: a first pass at widening `gh api` went straight to a blanket `Bash(gh api *)`, mirroring the `gh pr`/`gh issue` precedent, and had to be walked back through several rounds of review down to a handful of specific patterns, then further down again once two of those (`gh api user*`, `gh api /rate_limit*`) turned out to have no real justification at all - `gh auth status*` already covered the one genuine need, and nothing in this repo documents an actual requirement to check GitHub's API rate limit from inside the container.

Two concrete techniques:

* Prefer the narrowest pattern that covers the confirmed need - a subcommand-scoped pattern (`Bash(gh api graphql*)`) over the bare noun (`Bash(gh api *)`), and a path/argument-scoped pattern (`Bash(gh api repos/*/pulls/*)`) over a broader one (`Bash(gh api repos/*)`) when the evidence only supports the narrower shape.
* A `Bash(<command>)` entry with **no trailing `*`** matches only that exact, argument-free invocation - the closest thing to an enforced read-only entry this permission system supports, since pattern matching is purely textual with no concept of HTTP method or read/write semantics (a trailing `Bash(gh api user*)` would match `gh api user` but also `gh api user -X PATCH ...`; the bare `Bash(gh api user)` matches only the former). Reach for this whenever the confirmed need is a single, fixed, no-argument invocation rather than a family of them.

If in doubt whether a wider pattern is actually needed, land the narrower one - a follow-up widening once a real need surfaces is a one-line PR; an accidentally-too-broad entry silently sits there granting more than intended until someone happens to notice.

### No blanket `Bash(<tool> *)` for a tool with subcommands (MANDATORY)

Standing rule from the repo owner (#1385, live session): for any tool that dispatches on a subcommand (`git`, `gh`, `dotnet`, `npm`, `bun`, `docker`, `podman`, `uv`, ...), never add a blanket `Bash(<tool> *)` to `permissions.allow`. Add one explicit entry per subcommand the workflow actually uses - `Bash(gh search code *)`, `Bash(dotnet build *)`, `Bash(npm ci *)` - and nothing for the subcommands it does not. `dotnet`, `gh`, `npm` and `bun` already follow this. `git` is the one deliberate exception: `claude-settings.json` still carries the blanket `Bash(git -C *)`, because `-C <dir>` is a mandatory leading option, so a per-subcommand settings pattern would take exactly the wildcard-before-suffix shape this rule exists to avoid. Worse, `permissions.allow` matching is plain text/wildcard matching, not a real shell parse - `Bash(git -C * add *)` would match any command containing the literal substring ` add ` anywhere in its arguments (a commit message, a `--grep` value, ...), regardless of the command's actual subcommand, so this pattern shape can't reliably identify "the real subcommand" for a tool whose subcommand follows a wildcarded `-C <dir>` the way it can for `gh`/`dotnet`/`npm` (subcommand is the literal first word, nothing wildcarded in front of it). The subcommand allowlist is enforced in the hook layer instead (`enforce-git-dash-c`'s `GIT_ALLOWED_SUBCOMMANDS`, #1387), which does a real AST parse and reads the actual subcommand token by position. Treat any other remaining blanket entry for a subcommand-dispatching tool as a gap to close, not as precedent.

### Deny destructive flags at every argument position (MANDATORY)

Second standing rule from the same session: any flag or operand that is destructive or turns a path argument into code execution gets an explicit `permissions.deny` entry, and the entry must cover **both** positions the flag can appear in, because `*` only matches one-or-more characters, not zero: `Bash(rm * --no-preserve-root*)` matches `rm -rf --no-preserve-root /` but not `rm --no-preserve-root -rf /`. Always add the pair - `Bash(<tool> <flag>*)` and `Bash(<tool> * <flag>*)` - and, where a whole operand is the danger, the exact spellings (`Bash(rm -rf /)`, `Bash(rm -fr /)`, `Bash(rm -r -f /)`, `Bash(rm -f -r /)`, `Bash(rm * /)`). Do not try to deny a *class* of operand with a wildcard (`Bash(rm * /*)` would also match every legitimate absolute path under the allowed roots); the class check is the hook's job (`enforce-allowed-dirs`), the deny list is the belt-and-braces for the exact strings. `test/install-claude-hooks.bats` pins the pairs.

Where the subcommand is the first word after the tool, the settings entry is the right place for the scope. `git`'s `-C <dir>` leading option is the deliberate exception - see the "No blanket `Bash(<tool> *)`" section above for why.

### Keep command-allowlist and claude-settings.json in sync

Enforced by `test/command-allowlist-parity.bats` on every PR (added after this exact drift shipped once - see `command-allowlist`'s own header comment for why the two files are separate layers in the first place): every `command-allowlist` name needs at least one matching `Bash(<name> ...)` entry in `claude-settings.json`'s `permissions.allow` - a blanket `Bash(<name> *)`, or one or more narrower subcommand-scoped patterns (as `git`/`gh`/`dotnet`/`bun`/`npm` deliberately use, on purpose, as least-privilege) - or CI fails. Whenever `command-allowlist` gains or loses a command, add or remove the matching entry in the same change - don't rely on the test to catch it after the fact; a tool missing an allow entry falls to the permission classifier, with no way to answer an "ask" in this unattended `--print` pipeline under `--permission-mode dontAsk` (#1331). Two exceptions the test also encodes:

* A name present in `command-allowlist` but also on `command-blocklist` (blocklist wins - e.g. `xargs`) is not actually usable and must **not** get a `claude-settings.json` allow entry; that would misrepresent it as permitted.
* A name with a *whole-command* deny in `claude-settings.json`'s own `permissions.deny` - `Bash(<name>)` or `Bash(<name> *)`, e.g. `sqlcmd` (denied to prevent reading `.database` credential files) - must not also get an allow entry for the same reason, even though `deny` already wins over `allow` for that specific pattern - a contradictory pair of entries is misleading regardless of which one takes effect. This does **not** apply to a narrow, args-scoped deny like `Bash(git config --add *)`: `git` still needs (and has) its own allow entries for its other, permitted invocations.

The same test file also asserts, in a second `@test`, that a fixed checked-in list of non-Bash tool names (`Monitor`, `Task`/`Agent`, `Edit`, `Read`, `Write`, `Glob`, `Grep`, `BashOutput`, `WebFetch`, `WebSearch`, `TodoWrite`, `NotebookEdit`, `KillShell`, `SlashCommand`) is present as a bare entry in `permissions.allow` (#1329) - independent of, and not derived from, `command-allowlist`, which only ever contains Bash subcommand names. `EnterWorktree` is deliberately excluded from that list: `block-git-worktree`'s `PreToolUse` hook already gates it directly, and an allow entry here would let the permission layer approve what the hook is meant to block. `Monitor` is the highest-stakes entry in that list - every long-running command this repo mandates (`git commit`, `pre-commit`/`pre-commit-check`, `dotnet build`/`test`, `npm`/`bun test`) is required to be backgrounded and then polled via `Monitor`, so a denied `Monitor` call would deadlock every build/test cycle by construction under `--permission-mode dontAsk` (#1331) if it were ever missing.

### Non-ASCII / Layer 0 block

Do **not** loosen the "reject any non-ASCII byte" check - it is a deliberate, hardened defence (8 code-review rounds; see the script's own header comment) against Unicode homoglyph/zero-width/bidi-override obfuscation, not an allowlist gap.

The hook itself now auto-corrects the common case: a small, fixed substitution table (em dash/en dash to hyphen, curly single/double quotes to straight quotes, non-breaking space to space, right/left arrow to `->`/`<-`, ellipsis to `...`) is applied before the ASCII check, and if that alone makes the command fully ASCII and it clears every other layer, the hook returns the normalized command via `hookSpecificOutput.updatedInput` instead of blocking - see [Prefer auto-correction over blocking](#prefer-auto-correction-over-blocking-when-its-a-genuine-correction) above. This was verified empirically against the live multi-hook `PreToolUse` chain (not just unit-tested against the script), since the chain runs hooks in parallel and the docs don't specify how competing decisions merge: a throwaway probe hook confirmed a rewrite from one hook in the chain does reach actual execution even when the other hooks in the same matcher return no decision.

`updatedInput` is merged with the original `tool_input`, not built fresh from just the rewritten command (#1367): both this hook and `enforce-git-dash-c` used to construct `updatedInput` as `{command: $cmd}` alone via `jq -n`, which silently dropped every sibling field the original Bash call had set - `run_in_background`, `timeout`, anything else - back to their defaults, since `updatedInput` replaces the whole `tool_input` used for actual execution. Concretely, a `git commit` sent with `run_in_background: true` that also hit `enforce-git-dash-c`'s missing-`-C` auto-correct below would silently run in the foreground with the default 120s timeout instead - no denial, no different exit code, just a downgrade `enforce-background-for-long-running-commands` (which evaluates the original, not the rewritten, input) never sees. Both hooks now pipe the already-captured request body through jq and merge it (`(.tool_input // {}) + {command: $cmd}`) instead of starting from `jq -n`, so every sibling field survives a rewrite. This is a different question from the still-unspecified one above - how *multiple hooks'* competing decisions merge - and only fixes what a *single* hook's own rewrite does to the fields it didn't touch.

This cannot loosen the check: the table is fixed, small, and applied unconditionally; anything left non-ASCII afterwards (control bytes, real homoglyphs, zero-width/bidi-override characters, or any character not in the table) still blocks exactly as before. When a command is blocked for this reason (i.e. normalization didn't fully resolve it):

* First choice: rewrite the command text in plain ASCII - this covers cases the fixed table doesn't (e.g. non-ASCII content that has to stay non-ASCII, or an editor-inserted character not on the list).
* If the content genuinely needs Unicode (e.g. an issue/PR body): write it to a file with the `Write` tool (not subject to this Bash hook) and pass it via a `--body-file`/equivalent flag so the actual Bash command line stays pure ASCII.

## enforce-allowed-dirs

Runs second, immediately after `reject-obfuscated-commands` (#1385). Restricts every directory- or path-taking argument of `cd`/`pushd`, `git -C`, `npm --prefix`, `find` (starting points) and `rm`/`mv`/`cp` (operands) to a configured allowlist of directory roots, and denies the flags on those same commands that turn a path argument into code execution: `git --exec-path`/`--git-dir`/`--work-tree`/`--namespace`/`--super-prefix`; every `git -c`/`--config-env` key except a short allowlist of inert display/behaviour keys (`color.*`, `advice.*`, `log.*`, `status.*`, `pull.*`, `push.*`, `fetch.*`, `rebase.*`, `init.*`, `diff.noprefix`, `diff.renames`, `core.quotepath`, `core.autocrlf`, and exactly `core.pager=cat`) - an allowlist rather than a denylist of dangerous keys, matching `enforce-git-dash-c`'s "git config is read-only for sessions" stance, because a denylist can never be complete and would let `-c commit.gpgsign=false` quietly defeat `enforce-git-identity`; `npm --script-shell`/`--userconfig`/`--globalconfig`; `find -exec`/`-execdir`/`-ok`/`-okdir`/`-delete`/`-fprint*`/`-fls`, plus `find -D`/`-O` (they take arguments and would hide where the starting points begin); and `rm --no-preserve-root`. `rm`/`mv` may not target an allowed root itself.

Why a hook and not `permissions.allow`: the permission-rule syntax has only literal text and `*`, with no typed placeholder for "a directory goes here", so every `git -C <dir> ...`/`npm --prefix <dir> ...`/`find <dir> ...` allow entry had to carry a `*` in the directory position - which also matched any option injected there (`git -C d -c core.hooksPath=/evil status`), exactly what Claude Code's own startup warning ("has a wildcard before the rest of the command, so it also matches any options inserted at that position") is about. With this hook doing the positional check, those per-subcommand wildcard entries were removed from `claude-settings.json`, leaving the bare tool-level entries (`Bash(git -C *)`, `Bash(find *)`, `Bash(npm ci *)`, ...) plus matching `permissions.deny` entries for the same code-execution flags as belt-and-braces. Those denies are plain substring patterns, and are a *real* second layer only because `reject-obfuscated-commands` has already rejected every quote-splice/substitution/non-ASCII form before either layer sees the command - do not reorder the chain so that this hook or the deny layer runs on an unnormalised command.

Path handling: each word is resolved with `realpath -m` (existing symlinks followed, so a symlink inside a root that points outside it fails; non-existent trailing components allowed) and must equal a root or sit beneath one. Relative paths resolve against the hook's own `$PWD`, or against the target of a single leading `cd <dir>`/`pushd <dir>` when that is the command's very first call; any other `cd`/`pushd`/`popd` arrangement (more than one, not first, nested in a substitution) makes the working directory unknowable to static parsing, so later *relative* paths block and absolute ones still work. A glob (`*`, `?`, `[`) in a path word is allowed - only the literal prefix before it is resolved, since pathname expansion can never match `..` - but brace, tilde and backslash are blocked outright (each can turn one literal into a different word at runtime), and a non-literal word in a path position blocks. Same shfmt AST walk and base64-per-word transport as `enforce-ssh-host-and-key`; fails closed on missing `jq`/`shfmt`/`realpath`, unparseable shell, or no usable roots. No auto-correct: a directory outside the roots is a fact about what the command would do, not a syntax slip.

Two consequences of removing the wildcard entries that are easy to trip over: `npm --prefix <dir> ci` no longer matches any allow entry (there is deliberately no `Bash(npm --prefix * ...)` replacement, that shape is the warning), so write it as `npm ci --prefix <dir>` - npm accepts the option after the subcommand, `Bash(npm ci *)` matches it, and the hook validates the directory wherever it appears (including npm's `-C` alias and nopt abbreviations such as `--prefi`). And `npm_config_*`/`NPM_CONFIG_*` environment prefixes are on `env-var-blocklist`, since npm reads every option from the environment too. Similarly, a bare `git <subcommand>` with no `-C` is auto-corrected to `-C "$PWD"` by `enforce-git-dash-c` and allowed via `updatedInput`, which this hook never sees, so this hook checks the hook's own working directory for a `-C`-less git call exactly as it would check `-C .`.

Five more rules from the #1386 security review, each a verified bypass before it was closed: a glob word may not contain a `..` component anywhere (`su*/../../etc` - the glob itself never matches `..`, but bash expands the literal `..` after it exactly as written, and only the pre-glob prefix is resolved); once a call that can create a symlink has appeared earlier in the same command (`ln`, `cp`, `mv`, `tar`, `unzip`, `rsync`, or a git subcommand that materialises repo content: checkout/switch/restore/clone/pull/merge/rebase/stash/apply/reset/...), every later checked path must already exist, because `realpath` resolves links as they are at hook time and `ln -s /etc root/l && rm -rf root/l/*` would otherwise pass - split such commands in two; `cp`/`mv` `--target-directory` is recognised in every getopt spelling (any unique abbreviation such as `--target=`, and `-t` inside a bundled cluster such as `-rt/etc`); npm long options are recognised with one dash as well as two (`-script-shell`, `-prefix` - nopt strips all leading dashes), and the `permissions.deny` pairs cover both; and `env-var-blocklist` matching in `reject-obfuscated-commands` is case-insensitive, since npm honours any case of `npm_config_`.

Configuration: `claude-hooks/allowed-dirs` next to the hook, one absolute path per line, `#` comments, a leading `~` expands to `$HOME` and a leading `$NAME` to that variable (a line whose variable is unset is skipped; a relative line is ignored). The shipped copy lists the agent container's three mounts (`/workspace/repo`, `/workspace/rules`, `/workspace/tmp`) and is baked root:root 0444; the Dockerfile sanity block asserts all three are present and that no `allowed-dirs.local` was baked in. On a host (via `install-claude-hooks`), those paths do not exist, so a hand-written `~/.claude/hooks/allowed-dirs.local` (never shipped, never symlinked; e.g. `~/work` and `$TMPDIR`) takes precedence when present - the installer says so if it is missing rather than inventing a host layout. Extending the checked-command set: add a `check_<name>` function and its dispatch case in the hook, and a matching `permissions.deny` entry for any new code-execution flag; widen roots only via the data file. Known limitation accepted for v1: `find` with a starting point outside the roots (e.g. `find /usr/lib -name x`) is blocked; a separate read-only roots list is the fix if that need ever materialises.

## enforce-git-identity

Runs after `block-no-verify`, before `enforce-git-dash-c`. Blocks git subcommands that create/rewrite commits, plus `fetch` (checked up front so a broken identity is caught before work starts, not after) - `commit`/`fetch`/`pull`/`rebase`/`merge`/`cherry-pick`/`revert`/`am` - unless git identity and GPG signing are correctly configured (`user.email` set and not the banned identity, `commit.gpgsign` true, a GPG secret key present for that email, `user.signingkey` set and matching a keyring entry for that email). No safe auto-correct: the problem is missing/misconfigured system state (git config, GPG keyring), not a fixable command string - nothing in the command text can be rewritten to make a signing key exist.

## enforce-git-dash-c

Parses each Bash command with `shfmt` and blocks any `git` invocation (including `sudo git ...` and other known wrapper prefixes) that isn't hardened with `git -C <dir>`. Also blocks `eval`/`source`/`.` outright, since their argument is a second command line this hook cannot verify. Fails closed if `shfmt` is missing or the command doesn't parse.

**Subcommand allowlist (#1387).** Every git call's subcommand (whatever follows `-C`, or the bare `git` token before the auto-correction below ever runs) is checked against the hardcoded `GIT_ALLOWED_SUBCOMMANDS` array near the top of the hook - not a data file like `command-allowlist`, since this hook is its only consumer and the actual enforcement is this hook's own AST-based parse (see the "No blanket `Bash(<tool> *)`" section above for why a `claude-settings.json` pattern can't do this job). A missing subcommand or one not on the list blocks outright, before the `config`/`clone`/auto-correct handling described below even runs, so a disallowed subcommand is never rewritten into an allowed-looking call by the missing-`-C` auto-correction. The shipped list: `add`, `branch`, `checkout`, `clone`, `commit`, `config`, `diff`, `fetch`, `log`, `ls-remote`, `merge`, `pull`, `push`, `rebase`, `reset`, `rev-list`, `rev-parse`, `show`, `stash`, `status`, `switch`, `worktree` - each entry has a confirmed use in this repo's own `ai/global`/`ai/local` instructions (widen-minimally: land only what's actually cited, not what the original issue's candidate list merely suggested might be fine). `config` and `clone` still need their own listed entries here even though they also get their own dedicated handling below, and `worktree`'s `add` vs non-`add` split is a separate, later concern for `block-git-worktree`. Notably absent despite being common git subcommands: `am`, `cherry-pick`, `mv`, `remote`, `restore`, `revert`, `rm`, `tag` - none has a confirmed need in this repo's documented workflow (`remote` was actively moved away from, in favour of `git config --local`, per a prior `CHANGELOG.md` entry); add any of them back only once a genuine need surfaces.

Since #1357, a missing `-C` auto-corrects instead of blocking when it is safe to: no directory-changing call (`cd`/`pushd`/`popd`, plain, wrapped, or backslash-escaped) appears anywhere in the command, and `git rev-parse --show-toplevel` confirms the hook's own `$PWD` sits inside a writable git checkout - `-C <$PWD>` (never the resolved toplevel, which can differ from `$PWD` when it runs from a subdirectory) is then spliced in after every bare `git` token and returned via `hookSpecificOutput.updatedInput`, merged with the original `tool_input` so sibling fields such as `run_in_background`/`timeout` survive the rewrite instead of being silently dropped to their defaults (#1367 - see the fuller explanation under [Non-ASCII / Layer 0 block](#non-ascii--layer-0-block) above, which hit the identical defect). Otherwise (a directory-changing call present, no enclosing repository, or an unwritable/foreign checkout) it blocks exactly as before - see [Prefer auto-correction over blocking](#prefer-auto-correction-over-blocking-when-its-a-genuine-correction) above for why this isn't the no-op that ruled out auto-correction here previously.

## block-git-worktree

Runs after `enforce-git-dash-c`. Blocks `git worktree add` (creating a new linked worktree) — a linked worktree splits repo state across multiple checkouts sharing one object store and one set of refs, which does not compose with this project's assumption of one checkout per repo directory. An errant `git worktree add` previously left a primary checkout registered as bare with no work tree of its own, breaking `git pull`/`git status` there until it was manually repaired. Other worktree subcommands (`list`/`remove`/`prune`/`lock`/`unlock`/`move`/`repair`/...) are inspection or cleanup of worktrees that already exist and remain allowed. Uses the same shfmt-parsed AST approach as `enforce-git-dash-c` and fails closed the same way. No safe auto-correct: `add` is a categorical policy block, not a syntax mistake, and there's no equivalent allowed command to substitute - the suggested alternative (a normal branch checkout) requires the agent to choose a branch name/target itself.

Also registered in `claude-settings.json` under its own `"matcher": "EnterWorktree"` `PreToolUse` entry, covering Claude Code's native `EnterWorktree` tool — a first-class tool that performs the equivalent of `git worktree add` directly, with no shell command string for the shfmt/AST parsing above to inspect (`EnterWorktree` was previously invisible to this hook entirely, since it was only wired to the `Bash` matcher; #1322). The same script dispatches on the hook payload's own `tool_name` field: an `EnterWorktree` call is allowed only when it is entering a worktree that already exists (a non-empty `path` and no `name`); every create-shaped combination is blocked (no `name`/`path` at all, `name` only, an empty `path`, or `name`+`path` both set — the last is malformed per the tool's own "mutually exclusive" contract and is failed closed rather than guessed at). `ExitWorktree` gets no equivalent guardrail: per its own tool description it is scoped to worktrees the *current session* created via `EnterWorktree`, is a documented no-op otherwise, and is inspection/cleanup-shaped like the already-allowed `git worktree` subcommands above.

## block-dotnet-tool-install

Runs before `enforce-background-for-long-running-commands`. Blocks `dotnet tool install` (local or global — any flag combination) and `dotnet new tool-manifest`. This container's .NET global tools are pinned and baked into the image at build time (see the "dotnet tools" sanity check in `containers/base/development-full/Dockerfile`, which asserts an exact set of tool names via `dotnet tool list -g`); either command would add an unpinned, unreviewed tool outside that set, bypassing the dependency-selection review the pinned set went through. Other `dotnet tool` subcommands (`list`/`restore`/`uninstall`/`update`/`run`/`search`) and other `dotnet new` templates remain allowed. Uses the same shfmt-parsed AST approach as `block-git-worktree`/`enforce-git-dash-c` and fails closed the same way. No safe auto-correct: there's no pinned-tool substitute the hook could infer and inject on the agent's behalf - adding a new pinned tool is a reviewed image-build change, not something a command rewrite can do.

## enforce-ssh-host-and-key

Runs after `block-dotnet-tool-install`, before `enforce-background-for-long-running-commands`. Restricts `ssh` to exactly the form `ssh user@host command...`, added because `claude-settings.json`'s `Bash(ssh *)` allow entry is blanket - the danger ssh poses is in the *destination*, not the verb, which a `permissions.allow` prefix pattern cannot scope (see [issue #1315](https://github.com/credfeto/credfeto-orchestrator/issues/1315)). Two conditions, both fail closed:

* **Grammar + host allowlist**: no flags of any kind are permitted - a word starting with `-` where the target is expected is rejected outright, not classified. `user@` is mandatory, and the host must end in the `.lan` private-network suffix (e.g. `user@dns-01.lan`, `user@dns-01.dns.lan`), validated against a strict positive-charset regex (alphanumerics, `.`, `-`, `_`, `@` only) rather than a blocklist of dangerous characters - after three review rounds each finding one more escaping/expansion mechanism (backslash, then ANSI-C quoting, then brace/tilde/glob expansion) that could make shfmt's raw source text differ from what bash actually executes, a positive allowlist closes that whole class in one step instead of one mechanism at a time. The target word and the single word immediately after it are the only ones content-inspected: real ssh doesn't stop parsing its own options at the destination, it keeps consuming immediately-following words as flags (`-o`, `-J`, `-F`, ...) until the first non-option word (round 7 code review - a flag re-injected there was a live local-command-execution/host-redirection bypass, confirmed via `ssh -G`), so that one word is checked the same way the target is (leading `-`, or non-literal, both blocked). Everything beyond that word is genuinely the remote command and is not restricted at all - the boundary this hook enforces is "which host, as which user", not what runs once connected to an already-authorised host.
* **Key precondition**: a usable SSH key must be loaded in the forwarded ssh-agent (`ssh-add -l` exits 0 against `SSH_AUTH_SOCK`) before a genuinely valid `ssh user@host.lan` call is allowed - this container never mounts raw private key files (agent-socket forwarding only), so a call can never silently fall back to interactive password auth.

`scp` was originally covered by this same hook too (as `enforce-ssh-scp-host-and-key`); removed entirely - from this hook, `command-allowlist`, and `permissions.allow` - rather than fixed further, since there is no legitimate need for the agent's own Bash tool to transfer files directly (file movement in this repo's workflow goes through git) and scp's own `[user@]host:path`/`scp://` grammar was the source of two of the confirmed parsing bugs found during this hook's review. `scp` is simply not on `command-allowlist` any more, so `reject-obfuscated-commands` blocks it outright before this hook would ever see it.

Uses the same shfmt-parsed AST approach as `enforce-git-dash-c`/`block-git-worktree`/`block-dotnet-tool-install` and fails closed the same way, plus a delimiter-collision-free (base64-per-word) transport between the `jq` AST walk and the bash validation logic - an earlier tab/newline-joined transport could be desynced by a real tab or newline byte inside a legitimately quoted word, which was found to be a complete, unauthenticated bypass before being replaced. See the hook's own header for the full multi-round history. No safe auto-correct: neither condition has a rewrite the hook could inject on the agent's behalf - a wrong host or a missing key are facts about the world, not something a command edit can fix.

`gpg` is deliberately **not** on `command-allowlist`/`permissions.allow` at all (removed alongside this hook, also from #1315): the agent's own Bash tool has no legitimate reason to invoke it directly - commit signing goes through git's own internal `gpg` invocation (`user.signingkey`/`commit.gpgsign`), and the only direct `gpg` calls in this repo are the `enforce-git-identity` hook's own subprocess check and `entrypoint.sh`'s container-startup validation, neither of which is gated by `permissions.allow` in the first place.

## enforce-background-for-long-running-commands

Runs after `enforce-ssh-host-and-key`, before `cache-gh-lookups`. Enforces the `credfeto-long-running-commands` rule that `git commit` (whose `pre-commit` hook run has no bounded duration), a directly-invoked `pre-commit`, this repo's own `pre-commit-check` wrapper (runs `pre-commit` against the existing checked-out repo, so it shares the same unbounded duration), `dotnet build`, `dotnet test`, `npm test`, and `bun test` must always be run with `run_in_background: true` on the Bash tool call. If `run_in_background` is `true`, allows immediately with no further check; a Bash call that omits the field entirely (the common case when a caller simply forgets it) is treated the same as an explicit `false` - it blocks. Otherwise parses the command with the same shfmt AST approach as `enforce-git-dash-c`/`block-git-worktree`/`block-dotnet-tool-install` and blocks if `git`/`.../git` in the command-name position (after skipping any `-c <k>=<v>`/`-C <dir>` pairs) is followed by subcommand `commit`, or `pre-commit`/`.../pre-commit` or `pre-commit-check`/`.../pre-commit-check` appears directly in the command-name position, or `dotnet`/`.../dotnet` is followed by `build` or `test`, or `npm`/`.../npm` or `bun`/`.../bun` is followed by `test`. Fails closed if `shfmt` is missing or the command doesn't parse. No safe auto-correct: the hook cannot inject `run_in_background: true` itself - that field lives in the tool call the hook is inspecting, not in the command string it could rewrite.

## cache-gh-lookups

Runs last in the chain (#1380). Unlike every other hook above, it never blocks - a parse failure, missing `shfmt`, or a non-matching command all just mean "no rewrite this time" and fall through to the normal permission check (today's behaviour), never a denial; this is a convenience optimisation, not a security control. Matches only when the *entire* Bash command is a single bare call, with no pipes/redirects/backgrounding/negation/surrounding statements, to `gh api user --jq '.login'` (single/double/unquoted `.login`, `gh` or a path-qualified `.../gh`) - the exact command `lib/github`'s `resolve_gh_me` runs on the host side, which the agent's own Bash tool sometimes reaches for too. On a match, rewrites it (via `hookSpecificOutput.updatedInput`, merged into the original `tool_input` the same way `enforce-git-dash-c`'s auto-correct does) into a one-liner that creates `${XDG_CACHE_HOME:-$HOME/.cache}/orchestrator/global`, populates `global/user.json` via a real `gh api user` call only if it isn't already there, then `cat`s it - byte-identical to `containers/agent/entrypoint.sh`'s own `seed_orchestrator_cache`, which eagerly seeds the same file at container start (non-fatal on failure, matching `resolve_gh_me`'s own #1086 precedent), so the rewritten command's `gh api user` fallback is normally a no-op and exists only to self-heal a cache entrypoint.sh failed to seed.

This does not reopen [issue #1344](https://github.com/credfeto/credfeto-orchestrator/issues/1344), which explicitly rejected a blanket `gh api user*` `permissions.allow` entry for the agent's own Bash tool ("no real justification"): the agent's literal call is never executed as written, so the underlying live API call happens at most once per fresh copy of the cache file, not once per agent attempt.

Adding another cached lookup later (the hook is named for this - `cache-gh-lookups`, plural): extend its own AST match to recognise the new call shape and give it its own cache filename under `global/` (or `local/`, for something that should not persist across container invocations) alongside `user.json`.

### Tracking allowlist requests

Every allowlist-block is logged in [credfeto/credfeto-orchestrator#1167](https://github.com/credfeto/credfeto-orchestrator/issues/1167) (labelled `Blocked`, `never-close`) for human review, unless a human in-session already approved and applied that specific addition (see above). Before logging a new request there, check the issue body and comments for the command name first - do not create duplicate entries.
