# Claude Hooks Instructions

[Back to Local Instructions Index](index.md)

> Load when: a Bash hook blocks a command, or when working on `containers/base/development-full/claude-hooks/`, `claude-managed-mcp.json` or `claude-mcp/`.

Local guardrail hooks live in `containers/base/development-full/claude-hooks/` and are wired into `claude-managed-settings.json` (installed as `/etc/claude-code/managed-settings.json`) as `Bash` `PreToolUse` hooks, run in this order: `reject-obfuscated-commands`, `enforce-allowed-dirs`, `block-secret-file-reads`, `enforce-git-identity`, `enforce-git-policy`, `block-git-worktree`, `block-dotnet-tool-install`, `enforce-ssh-host-and-key`, `enforce-curl-host`, `enforce-background-for-long-running-commands`, `cache-gh-lookups`. `block-git-worktree` is also wired to a second, separate `PreToolUse` entry matching the native `EnterWorktree` tool (own `"matcher": "EnterWorktree"`, not part of the `Bash` chain above) - see its own section below. `block-github-mcp-write-tools` is wired to a third, separate `PreToolUse` entry matching `mcp__github__.*` (also not part of the `Bash` chain) - see its own section below. Every hook command is an absolute `/etc/claude-code/hooks/<name>` path vendored from `claude-hooks/`; never wire in a bare command looked up on `PATH` (such as an npm-installed tool), since whatever comes first on `PATH` would then run as a guardrail. `enforce-allowed-dirs` is also wired to a separate `PreToolUse` entry matching `Edit|Write|NotebookEdit` (see its own section below), `block-secret-file-reads` to the same `Edit|Write|NotebookEdit` entry (after `enforce-allowed-dirs`) and to its own entry matching `Read`, and `block-config-skills` to one matching `Skill`.

## Prefer auto-correction over blocking, when it's a genuine correction

`PreToolUse` hooks can rewrite the tool call instead of only allowing/denying it, via `hookSpecificOutput.updatedInput` alongside `permissionDecision: "allow"` in the hook's JSON stdout (see Claude Code hooks documentation). When a blocked command has an unambiguous, safe rewrite available - one that fixes the actual problem rather than merely satisfying the check's syntax - prefer emitting that rewrite over blocking-and-retrying. It cuts a round trip without weakening the guardrail.

This is not a blanket instruction to auto-fix every block. A rewrite is only valid when it adds real information the hook can't already infer risk-free. It is not valid when the only available substitution would make the check pass without verifying anything - that's equivalent to not enforcing the check at all, just with extra steps. A naive version of this trap: injecting the hook's own `$PWD` verbatim for a missing `-C <dir>` would be a no-op, since plain `git` already defaults to `$PWD` when `-C` is omitted - `git -C "$PWD" status` and bare `git status` behave identically, so unconditionally auto-injecting it would make `-C` effectively optional everywhere, defeating the whole point of forcing the target repo to be explicit in the tool call. `enforce-git-policy` (see its own section below) auto-corrects a missing `-C`, but only escapes this trap by adding two checks the naive version above lacks: no directory-changing call (`cd`/`pushd`/`popd`, plain, wrapped, or backslash-escaped) appears anywhere in the command (this hook parses statically and can't track such a call's effect otherwise), and `git rev-parse --show-toplevel` confirms the hook's own `$PWD` sits inside a real, writable git checkout before that same `$PWD` is what gets injected. Every case the hook cannot be confident about still blocks outright, exactly as before. Before adding auto-correction to any hook, check whether the "fix" is actually a no-op like the naive version above, or has a similar unambiguous-and-verifiable guard like this one. Whatever hook you're adding this to, build `updatedInput` by merging into the original `tool_input` (`(.tool_input // {}) + {...}`), never by constructing a fresh object from scratch (`jq -n`) - the latter replaces the whole `tool_input` the call actually executes with, silently dropping sibling fields like `run_in_background`/`timeout` back to their defaults (see [Non-ASCII / Layer 0 block](#non-ascii--layer-0-block) below for the full mechanism and a live repro).

**A rewrite does not need the original *or* the rewritten command to match any `permissions.allow` entry** - `hookSpecificOutput.permissionDecision: "allow"` genuinely overrides the allow/deny classifier for that call, rather than merely signalling "this hook has no objection" and leaving the call subject to the normal classifier afterward. Claude Code's own hooks documentation is ambiguous on this specific point (it says the decision is "honored" and "takes effect" without stating whether that supersedes classifier evaluation), but it has been confirmed empirically: with `cache-gh-lookups` synced onto a live host `~/.claude` (`permissions.defaultMode: "dontAsk"`, the same mode the container agents run under via `--permission-mode dontAsk`), `gh api user --jq '.login'` as a real Bash tool call - a command absent from `permissions.allow` on both sides, by design - executes with no denial and no prompt, and the cache file's creation timestamp shows the *rewritten* command ran, not the literal original. This means a rewrite hook can safely target a command with no `permissions.allow` coverage at all, as `cache-gh-lookups` does; it does not need to first ensure the rewritten text would independently pass the classifier.

## reject-obfuscated-commands

Delegates parsing to `shfmt` and applies policy to the resulting AST rather than text-scanning. Blocks in layered order (all fail closed): non-ASCII/non-printable bytes anywhere in the command (after normalizing a small fixed table of known-benign Unicode punctuation - see below), unparseable shell, disallowed AST shapes (function defs, `declare`/`export`, non-literal command names, and an assignment to an `env-var-blocklist` name or to a non-literal name), interpreters given an inline-code flag (`bash -c`, `python3 -c`, ...), `command-blocklist` names (`eval`, `sudo`, `env`, ...), then `command-allowlist` (anything not listed is rejected).

Container execution is banned outright: `podman` and `docker` are not on `command-allowlist` or `permissions.allow`, and `podman`, `docker` and `nerdctl` are on `command-blocklist` (`nerdctl` is not on the allowlist either, but its own blocklist line gives a named message instead of the generic "not on the known-good command allowlist" one, as `scp`/`gpg`/`wget` do). Running a script or shell inside a container gets around the sub-shell and inline-code bans above. Do not replace the ban with a closed-grammar allowlist hook in the style of `enforce-curl-host`: the owner rejected that, because the mount-source/entrypoint-literal parsing needed to keep a "legitimate tool-validation" pattern working is more machinery than the problem warrants, and no documented in-session Bash workflow needs container execution (`ai/local/docker-images.instructions.md` relies on CI for build verification; see its "Build Verification Before Any Change" section). The `podman run` references in `ai/local/debugging.instructions.md` and `tasks/healthcheck.md` are host-side orchestration, not agent Bash calls, and are unaffected. The ban covers every subcommand, `build`/`play kube`/`compose` included.

`env-var-blocklist` applies to every bash form that assigns a variable, not only `NAME=value` statements and prefixes: `printf -v`, `read`, `mapfile`/`readarray`, `getopts`, `unset`, `let`, arithmetic assignment (`((NAME=..))`, compound operators, `++`/`--`, `$((..))`, C-style `for ((..))`), `for`/`select` loop variables and `${NAME:=..}`/`${NAME=..}`. When adding a new assignment-capable builtin or syntax to `command-allowlist` or to the hook, add it to this target extraction too, or it becomes a blocklist bypass. A target whose name is not a plain literal (a variable, substitution, backslash escape, `$'...'` string, `${!name:=..}`, or a non-literal `printf` first argument that may start with `-`) blocks, failing closed, because its real name cannot be checked. The `read`/`mapfile`/`getopts`/`unset` extraction deliberately treats every argument (and each short-option-cluster tail) as a possible target rather than parsing each builtin's option table, so it over-blocks an option value that spells a blocklisted name; keep that trade-off.

### Extending command-allowlist (MANDATORY process)

`command-allowlist` is a security control, not a convenience list - do not extend it unilaterally by default. When a command is blocked as "not on the known-good command allowlist":

- Default (including any autonomous/non-interactive run): do **not** edit `command-allowlist` yourself. Instead log the request in the tracking issue below - check its body and comments for the command name first and skip logging if it is already present, so requests do not get duplicated.
- Only edit `command-allowlist` directly when a human is present in the session and explicitly asks for that specific command to be added now. Still run the `reject-obfuscated-commands.bats` suite afterwards and commit/push per the normal workflow.

### Classify every command-allowlist entry (MANDATORY)

Every `command-allowlist` line is the command name followed by exactly one classification, `writer` or `read-only`, and `enforce-allowed-dirs` blocks any call whose command has no valid classification. The classification decides whether the command's arguments are checked as write targets, so a wrong `read-only` silently exempts a command that writes; an unclassified entry fails closed instead. Classify as `writer` any command that can create, replace, remove or re-mode a file named by its arguments, and any command that runs code which can (an interpreter, a package runner, a build tool, a linter with a fix or report-file option). Classify as `read-only` only a command with no way to write a named file. When in doubt, use `writer`: the cost is a false positive on an argument that only looks like a path outside the roots, never a silent write. `test/command-allowlist-parity.bats` fails on an entry without a valid classification.

### Widen minimally, prefer read-only where possible (MANDATORY)

Whenever adding a `permissions.allow` (or `command-allowlist`) entry, start from what is actually confirmed needed - a genuine observed denial, a documented mandate elsewhere in `ai/global`/`ai/local`, or an existing test/workflow requirement - not from what a broader-looking existing entry might suggest is fine to copy. `Bash(gh pr *)`/`Bash(gh issue *)` being blanket wildcards is not license to add `Bash(gh api *)`/`Bash(gh project *)` the same way by default: each command's actual blast radius differs. For example, `gh api` needs only a handful of specific patterns, not a blanket `Bash(gh api *)`; `gh api user*` and `gh api /rate_limit*` have no justification at all, because `gh auth status*` covers the one genuine need and nothing in this repo requires checking GitHub's API rate limit from inside the container.

Two concrete techniques:

- Prefer the narrowest pattern that covers the confirmed need - a subcommand-scoped pattern (`Bash(gh api graphql*)`) over the bare noun (`Bash(gh api *)`), and a path/argument-scoped pattern (`Bash(gh api repos/*/pulls/*)`) over a broader one (`Bash(gh api repos/*)`) when the evidence only supports the narrower shape.
- A `Bash(<command>)` entry with **no trailing `*`** matches only that exact, argument-free invocation - the closest thing to an enforced read-only entry this permission system supports, since pattern matching is purely textual with no concept of HTTP method or read/write semantics (a trailing `Bash(gh api user*)` would match `gh api user` but also `gh api user -X PATCH ...`; the bare `Bash(gh api user)` matches only the former). Reach for this whenever the confirmed need is a single, fixed, no-argument invocation rather than a family of them.

If in doubt whether a wider pattern is actually needed, land the narrower one - a follow-up widening once a real need surfaces is a one-line PR; an accidentally-too-broad entry silently sits there granting more than intended until someone happens to notice.

### No blanket `Bash(<tool> *)` for a tool with subcommands (MANDATORY)

For any tool that dispatches on a subcommand (`git`, `gh`, `dotnet`, `npm`, `bun`, `uv`, ...; `docker`/`podman` are banned outright via `command-blocklist`), never add a blanket `Bash(<tool> *)` to `permissions.allow`. Add one explicit entry per subcommand the workflow actually uses - `Bash(gh search code *)`, `Bash(dotnet build *)`, `Bash(npm ci *)` - and nothing for the subcommands it does not. `dotnet`, `gh`, `npm` and `bun` already follow this. `git` is the one deliberate exception: `claude-managed-settings.json` still carries the blanket `Bash(git -C *)`, because `-C <dir>` is a mandatory leading option, so a per-subcommand settings pattern would take exactly the wildcard-before-suffix shape this rule exists to avoid. Worse, `permissions.allow` matching is plain text/wildcard matching, not a real shell parse - `Bash(git -C * add *)` would match any command containing the literal substring ` add ` anywhere in its arguments (a commit message, a `--grep` value, ...), regardless of the command's actual subcommand, so this pattern shape can't reliably identify "the real subcommand" for a tool whose subcommand follows a wildcarded `-C <dir>` the way it can for `gh`/`dotnet`/`npm` (subcommand is the literal first word, nothing wildcarded in front of it). The subcommand allowlist is enforced in the hook layer instead (`enforce-git-policy`'s `GIT_ALLOWED_SUBCOMMANDS`), which does a real AST parse and reads the actual subcommand token by position. Treat any other remaining blanket entry for a subcommand-dispatching tool as a gap to close, not as precedent.

### Deny destructive flags at every argument position (MANDATORY)

Any flag or operand that is destructive or turns a path argument into code execution gets an explicit `permissions.deny` entry, and the entry must cover **both** positions the flag can appear in, because `*` only matches one-or-more characters, not zero: `Bash(rm * --no-preserve-root*)` matches `rm -rf --no-preserve-root /` but not `rm --no-preserve-root -rf /`. Always add the pair - `Bash(<tool> <flag>*)` and `Bash(<tool> * <flag>*)` - and, where a whole operand is the danger, the exact spellings (`Bash(rm -rf /)`, `Bash(rm -fr /)`, `Bash(rm -r -f /)`, `Bash(rm -f -r /)`, `Bash(rm * /)`). Do not try to deny a *class* of operand with a wildcard (`Bash(rm * /*)` would also match every legitimate absolute path under the allowed roots); the class check is the hook's job (`enforce-allowed-dirs`), the deny list is the belt-and-braces for the exact strings. `test/install-claude-hooks.bats` pins the pairs.

Where the subcommand is the first word after the tool, the settings entry is the right place for the scope. `git`'s `-C <dir>` leading option is the deliberate exception - see the "No blanket `Bash(<tool> *)`" section above for why.

### Keep command-allowlist and claude-managed-settings.json in sync

Enforced by `test/command-allowlist-parity.bats` on every PR (see `command-allowlist`'s own header comment for why the two files are separate layers in the first place): every `command-allowlist` name needs at least one matching `Bash(<name> ...)` entry in `claude-managed-settings.json`'s `permissions.allow` - a blanket `Bash(<name> *)`, or one or more narrower subcommand-scoped patterns (as `git`/`gh`/`dotnet`/`bun`/`npm` deliberately use, on purpose, as least-privilege) - or CI fails. Whenever `command-allowlist` gains or loses a command, add or remove the matching entry in the same change - don't rely on the test to catch it after the fact; a tool missing an allow entry falls to the permission classifier, with no way to answer an "ask" in this unattended `--print` pipeline under `--permission-mode dontAsk`. Two exceptions the test also encodes:

- A name present in `command-allowlist` but also on `command-blocklist` (blocklist wins) is not actually usable and must **not** get a `claude-managed-settings.json` allow entry; that would misrepresent it as permitted.
- A name with a *whole-command* deny in `claude-managed-settings.json`'s own `permissions.deny` - `Bash(<name>)` or `Bash(<name> *)`, e.g. `sqlcmd` (denied to prevent reading `.database` credential files) - must not also get an allow entry for the same reason, even though `deny` already wins over `allow` for that specific pattern - a contradictory pair of entries is misleading regardless of which one takes effect. This does **not** apply to a narrow, args-scoped deny like `Bash(git config --add *)`: `git` still needs (and has) its own allow entries for its other, permitted invocations.
- Never add a `Read(**/<name>)` or `Edit(**/<name>)` deny entry. The permission checker models any Bash command that names a directory (`grep -r … <dir>`, `find <dir>`, `cd <dir>; …`) as a read of the whole tree, and a `**` deny that *could* match a path under it cannot be proven inapplicable, so every directory-wide search escalates to the user - dozens of prompts in one session. Protect a known secret file by its actual path (`Read(~/.database)`), and make the Bash text-match denies require a slash before the name (`Bash(cat */.database*)`, not `Bash(cat *.database*)`): `~/.database`, `$HOME/.database` and `/home/<user>/.database` all still match, while the cs-template search rule's mandated `--exclude='.database'` / `-not -name '.database'` does not trip a hard deny. The slash-anchored text denies cover only the path-literal form: `cd ~ && cat .database`, `find ~ -name .database -exec cat {} +` and `grep -r --include=.database x ~` do not match them; for those, rely on `enforce-allowed-dirs` (which keeps `cd` and `find` starting points under `/workspace`) and on the checker modelling `grep -r x ~` as a read of `~/.database`. Per-file protection for names that can appear in any repo (`.env`, repo-local `.database`), and for the host file reached through a symlink or a copy under another name, is a job for a path-aware hook and container-side masking, not a glob: see [block-secret-file-reads](#block-secret-file-reads) below.

The same test file also asserts, in a second `@test`, that a fixed checked-in list of non-Bash tool names (`Monitor`, `Task`/`Agent`, `Edit`, `Read`, `Write`, `Glob`, `Grep`, `BashOutput`, `WebFetch`, `WebSearch`, `TodoWrite`, `NotebookEdit`, `KillShell`, `SlashCommand`) is present as a bare entry in `permissions.allow` - independent of, and not derived from, `command-allowlist`, which only ever contains Bash subcommand names. `EnterWorktree` is deliberately excluded from that list: `block-git-worktree`'s `PreToolUse` hook already gates it directly, and an allow entry here would let the permission layer approve what the hook is meant to block. `Monitor` is the highest-stakes entry in that list - every long-running command this repo mandates (`git commit`, `pre-commit`/`pre-commit-check`, `buildtest`, `dotnet build`/`test`, `npm`/`bun test`) is required to be backgrounded and then polled via `Monitor`, so a denied `Monitor` call would deadlock every build/test cycle by construction under `--permission-mode dontAsk` if it were ever missing.

### Non-ASCII / Layer 0 block

Do **not** loosen the "reject any non-ASCII byte" check - it is a deliberate, hardened defence (see the script's own header comment) against Unicode homoglyph/zero-width/bidi-override obfuscation, not an allowlist gap.

The hook itself auto-corrects the common case: a small, fixed substitution table (em dash/en dash to hyphen, curly single/double quotes to straight quotes, non-breaking space to space, right/left arrow to `->`/`<-`, ellipsis to `...`) is applied before the ASCII check, and if that alone makes the command fully ASCII and it clears every other layer, the hook returns the normalized command via `hookSpecificOutput.updatedInput` instead of blocking - see [Prefer auto-correction over blocking](#prefer-auto-correction-over-blocking-when-its-a-genuine-correction) above. This was verified empirically against the live multi-hook `PreToolUse` chain (not just unit-tested against the script), since the chain runs hooks in parallel and the docs don't specify how competing decisions merge: a throwaway probe hook confirmed a rewrite from one hook in the chain does reach actual execution even when the other hooks in the same matcher return no decision.

Merge `updatedInput` into the original `tool_input`; never build it fresh from just the rewritten command. `updatedInput` replaces the whole `tool_input` used for actual execution, so constructing it as `{command: $cmd}` alone via `jq -n` silently drops every sibling field the original Bash call set - `run_in_background`, `timeout`, anything else - back to their defaults. Concretely, a `git commit` sent with `run_in_background: true` that also hits `enforce-git-policy`'s missing-`-C` auto-correct below would silently run in the foreground with the default 120s timeout - no denial, no different exit code, just a downgrade `enforce-background-for-long-running-commands` (which evaluates the original, not the rewritten, input) never sees. Both this hook and `enforce-git-policy` pipe the already-captured request body through jq and merge it (`(.tool_input // {}) + {command: $cmd}`), so every sibling field survives a rewrite. This is a different question from the still-unspecified one above - how *multiple hooks'* competing decisions merge - and only fixes what a *single* hook's own rewrite does to the fields it didn't touch.

This cannot loosen the check: the table is fixed, small, and applied unconditionally; anything left non-ASCII afterwards (control bytes, real homoglyphs, zero-width/bidi-override characters, or any character not in the table) still blocks exactly as before. When a command is blocked for this reason (i.e. normalization didn't fully resolve it):

- First choice: rewrite the command text in plain ASCII - this covers cases the fixed table doesn't (e.g. non-ASCII content that has to stay non-ASCII, or an editor-inserted character not on the list).
- If the content genuinely needs Unicode (e.g. an issue/PR body): write it to a file with the `Write` tool (not subject to this Bash hook) and pass it via a `--body-file`/equivalent flag so the actual Bash command line stays pure ASCII.

### node

`node` is on `command-allowlist`, scoped narrowly in `claude-managed-settings.json`'s `permissions.allow` to `node --check`/running a `.js` file directly under `.github/actions/<action>/` (`--check` bare, the run form bare and with trailing arguments), so GitHub Actions JS scripts can be syntax-checked or run locally without waiting on CI. `--check` is scoped to `.github/actions/*/*.js` the same as the run form, never left unscoped: `node --check` fully parses any readable file and echoes a source-line snippet in its `SyntaxError` for anything that isn't valid JS, so an unscoped pattern would leak the content of a secret-bearing file. `reject-obfuscated-commands` keeps two inline-code flag sets: `INLINE_CODE_FLAGS` (`-c`/`-e`/`--eval`/`--command`/`-ne`/`-pe`), checked for every interpreter, and `NODE_ONLY_INLINE_FLAGS` (`-p`/`--print`/`-i`/`--interactive`), matched exactly only when the interpreter is `node`/`nodejs` (the glued short-flag match described below still applies `-p?*` to every interpreter), so `node -p`/`node -e`/`node -i` are rejected as interpreter re-invocation the same way `python3 -c` is; `-i`/`--interactive` covers node's REPL, exactly as dangerous as inline code. The node-only flags are kept out of the shared set because they mean something harmless for other interpreters (`-p` is a shell's privileged mode, `-i` an interactive shell, `python3 -i` runs a script then drops into its REPL), so checking them everywhere misreports those as inline code; when adding an inline-code flag, put it in the shared set only if it runs a code string for virtually every interpreter listed. `node -c` is also blocked, even though it is node's own `--check` alias, because `-c` is in the shared set; use `--check`. `reject-obfuscated-commands` resolves each argument from its AST parts (literal/single/double-quoted pieces only, folding to the opaque marker for anything genuinely dynamic) before this check runs, and `is_inline_code_flag()` matches a long flag glued to its value with `=` (`node --eval="code"`) and a short flag glued with no separator (`node -e"code"`) as well as the exact flag, so quoted and glued forms are caught the same as the plain one. This is the same resolution technique `enforce-git-policy` uses for its `--no-verify` bypass check, trimmed to the literal/quoted-concatenation case.

The `permissions.allow` patterns above are plain text/wildcard matching, same limitation as every other path-taking `Bash()` pattern in this file (see [Widen minimally](#widen-minimally-prefer-read-only-where-possible-mandatory) above) - they cannot themselves stop `node`'s own code-loading flags (`-r`/`--require`, `--import`, `--loader`/`--experimental-loader`, `--inspect`), which `reject-obfuscated-commands` does not check either, since `INLINE_CODE_FLAGS` only covers the flags that hand an interpreter a literal string of code, not a module path. `enforce-allowed-dirs` closes both gaps: its `node` check resolves the script path (with `realpath -m`, so neither `..` nor a symlink hides where it lands) and requires it under a root and under `<cwd>/.github/actions/` (the cwd, or a single leading `cd`), and it denies every option before the script except a single leading `--check`, as well as `node -` (a program read from stdin), a missing script and a script word that is not literal or is a glob. Script arguments after the script are not checked, because node stops parsing its own options there. `permissions.deny` keeps a first-position deny for each code-loading flag (`Bash(node --require*)` etc.) as defence in depth. Unlike npm's `--script-shell`, these flags get no later-position (`Bash(node * --require*)`) form: every allowed shape puts the `.github/actions` script path as node's first positional argument (at most after `--check`), and node stops parsing its own options at the first positional, so a later `-r`/`--require` is a script argument, not a node flag, and a later-position deny would block legitimate script arguments such as `-refresh` for no gain. Add a later-position form only if an allow pattern ever lets a node option follow another argument. Script arguments do not all pass, though: `reject-obfuscated-commands` checks every argument after the interpreter name, not just the positions where the interpreter still parses its own options, so a script argument that looks like an inline-code flag is rejected. That covers exact matches (`-e`, `-c`, `-p`, `-i`, `--print`, `--eval=...`) and anything starting `-c`, `-e` or `-p` (`-config`, `-env`, `-port`, `-pno:cacheprovider`), for every interpreter. This is an accepted fail-closed limitation. Do not fix it by stopping the scan at the first non-dash argument, because that reopens `python3 -W ignore -c code`, where an option's value comes before the real flag. A correct fix needs per-interpreter tracking of which options take a value and where option parsing ends.

## enforce-allowed-dirs

Runs second, immediately after `reject-obfuscated-commands`, and is the single write-target policy: a path a Bash command writes must sit inside the configured roots and outside Claude Code's own configuration. Keep one write-target hook: separate parsers per concern drift apart, and their disagreement is where bypasses and false positives come from. Add any new write-target rule to this hook, not to a new one.

It also restricts every directory- or path-taking argument of `cd`/`pushd`, `git -C`, `npm --prefix`, `find` (starting points), `rm`/`mv`/`cp` (operands) and the `node` script (which must also be under `.github/actions/`, see [node](#node) above) to the same roots, and denies the flags on those same commands that turn a path argument into code execution: `git --exec-path`/`--git-dir`/`--work-tree`/`--namespace`/`--super-prefix`; every `git -c` key except a short allowlist of inert display/behaviour keys (`color.*`, `advice.*`, `log.*`, `status.*`, `pull.*`, `push.*`, `fetch.*`, `rebase.*`, `init.defaultBranch` (not `init.*`, because `init.templateDir` can plant hooks), `diff.noprefix`, `diff.renames`, `core.quotepath`, `core.autocrlf`, and exactly `core.pager=cat`) - an allowlist rather than a denylist of dangerous keys, matching `enforce-git-policy`'s "git config is read-only for sessions" stance, because a denylist can never be complete and would let `-c commit.gpgsign=false` quietly defeat `enforce-git-identity`. The allowlist matches the key case-insensitively and the value exactly, because git folds the case of a config key but not of its value (`-c CORE.PAGER=cat` is allowed, `-c core.pager=CAT` is not); `git --config-env`, in both its `--config-env <k>=<env>` and `--config-env=<k>=<env>` spellings, is denied outright whatever its key, because git reads its value from an environment variable when it runs, so no hook can see the value that will be applied; `npm --script-shell`/`--userconfig`/`--globalconfig`; `find -exec`/`-execdir`/`-ok`/`-okdir`/`-delete`/`-fprint*`/`-fls`, plus `find -D`/`-O` (they take arguments and would hide where the starting points begin); and `rm --no-preserve-root`. `rm`/`mv` may not target an allowed root itself.

Write targets are deny by default. Every call's command must carry a `writer` or `read-only` classification in `command-allowlist` (see [Classify every command-allowlist entry](#classify-every-command-allowlist-entry-mandatory) above); an unclassified command is blocked, and exactly `set -e` counts as read-only. The write targets are the words of the writing redirections (`>`, `>>`, `>|`, `&>`, `&>>`, `<>`, and `>&` to anything but a file descriptor or `-`) and, for a writer, its arguments: by default every non-option argument, the value of every `--option=value` and every tail of a short-option word, because a value glued to a short option (`-o/etc/x`) cannot be told from a flag cluster without each tool's own option table. A few writers have a dedicated rule in the hook, to keep text that is not a path out of the check: `rm`/`mv`/`cp`; `ln -s` (the link it creates as a path, and every target it points to, in every form - `ln -s T L`, several targets into a directory, `-t DIR`, `--symbolic`, a cluster such as `-sf` - as text against the protected names, the user's git, gh and curl configuration names among them, and also anywhere inside a `.claude` tree, a `.git` tree, `.config`, `$XDG_CONFIG_HOME`, `.local` or `$XDG_DATA_HOME`, or the `claude-code` directory itself, like `sed`/`awk` program text: a target is text until something is written through the link, and a later writer's own text, such as a sed `w` name, is never resolved, so a link pointing at configuration, or into a tree from where a `..` reaches it (`ln -s ~/.claude/projects p`, then `w p/../settings.json`), would let it reach it; an unquoted brace expansion blocks and every current match of an unquoted glob is checked as a path, anywhere inside a `.claude` tree or `/etc/claude-code` as for the text, since bash rewrites each before `ln` sees it; a target that is not fully literal (a variable, substitution or other expansion, as in `ln -s "$HOME/.claude" c`) blocks, because it could name configuration that a later write through the link reaches); a hard `ln` checks every operand, its targets included, as a write target (text and path); for `cp`, `mv` and `ln` alike, what each source becomes inside a destination directory (a `--target-directory`, else the last of two or more operands, else for a lone `ln` operand the working directory) is also checked as a path - the destination joined with the source's last component, using every current match of an unquoted glob - whenever the destination may be a directory, since `cp x/.gitconfig ~/` writes `~/.gitconfig` with neither word naming it (this can only over-check), and with no `--target-directory` a last operand that is an unquoted glob matching more than one name blocks, since bash then chooses the destination (`mv ~/.local/[gs]*`) - a `--target-directory` that is an unquoted glob matching more than one name also blocks, since bash uses the first match as the directory and passes the others as sources; `cp --parents` (any abbreviation from `--pa`) blocks, since it recreates each source's whole path under the destination; and backups are not available on `cp`, `mv` or `ln` - `-b`, `-S` (anywhere in a short cluster before a `-t`) and any spelling or abbreviation of `--backup` or `--suffix`, with or without a value, block, and `SIMPLE_BACKUP_SUFFIX` and `VERSION_CONTROL` are on `env-var-blocklist` - because a backup renames an existing file to its name plus a suffix, which can create a protected path no word names (`cp -b -S fig x ~/.gitcon` turns an existing `~/.gitcon` into `~/.gitconfig`); `git` (only `checkout`, `restore`, `mv`, `rm`, `clone` or a call with an `--o...` option, relative to the last `-C`, plus the directory `clone` names after the repository when none is given); `gh` (every call except a command on the hook's read-only table of commands that write no local file (`GH_READ_ONLY_COMMANDS`, each checked against `gh <command> --help`), whose arguments are issue and PR text; `pr merge`/`close` are on it only without `-d`; an unknown command, alias, extension or non-literal command word is a writer, `repo clone`/`fork`/`create` also check the directory named after the repository, a gh writer counts as able to create symlinks, and `gh alias set`/`import` block, since an alias's writes appear on no command line, as do `gh extension install`/`upgrade`/`remove` (alias `uninstall`)/`browse` under `extension`, `extensions` or `ext`, since they write gh's data directory (`~/.local/share/gh`, `$XDG_DATA_HOME/gh`), where the extensions gh runs live, without naming it; `gh extension list`/`ls` is read-only, `create` is an ordinary writer of the directory it names, and `exec` or running an installed extension by name is an accepted gap; gh finds its command by skipping option words and a lone `-`, so the hook locates it the same way: an option or a lone `-` before the group or subcommand (`gh extension --force=true install x`, `gh --clobber=true alias set ...`, `gh alias - import`) cannot hide a blocked command, a call with one is never read-only, and when such an option has no `=` (so it may take the next word as its value) any ordered pair of later words naming a blocked command blocks, failing closed); `dotnet changelog` (its `-m`/`--message` is text); `mktemp` (also `$TMPDIR` when no template is given); and `sed`/`awk`, whose program text is checked against the protected names only - the Claude Code names, the user's git, gh and curl configuration names, and a `.git` entry or anything under `config`, `hooks` or `commondir` in a `.git` tree - (that text is never resolved, so the match allows anything between `.claude/` and the protected name, and a `//`, `/./` or `x/../` detour cannot hide one; anything after `claude-code/` matches wherever it sits, not only after `etc/`, because a link to `/etc` or a system symlink to a directory under it reaches `/etc/claude-code` without naming `etc`) and whose files are write targets only when editing in place; an `awk` option outside its known non-writing set (gawk's `-d`/`-o`/`-p`, `-W`, an abbreviated long option) makes every argument a write target under the default rule. Each write target must be fully literal: a variable or substitution blocks, because its value is unknowable. It then must not resolve (with `realpath -ms`, so `..` cannot hide a name, and `realpath -m`, so a symlink cannot) to a protected path - a `.claude` directory, `.claude/settings*.json*`, anything under `.claude/hooks`, `.claude/agents`, `.claude/skills`, `.claude/commands`, `.claude/plugins`, `.claude/rules`, `.claude/output-styles` or `.claude/sessions`, `.claude/CLAUDE.md`, `.claude/.credentials.json`, `.claude/history.jsonl`, `.claude.json`, `.mcp.json` or `/etc/claude-code`, or, under the user's own `$HOME` only, `~/.curlrc`, `~/.gitconfig`, `curlrc` (which curl reads before `~/.curlrc`) or anything under `git` or `gh` in `~/.config` or `$XDG_CONFIG_HOME`, or anything under gh's data directory `gh` in `~/.local/share` or `$XDG_DATA_HOME` (its installed extensions) - and must resolve under a root. A repo's own `.gitconfig` or `.curlrc` fixture is not a protected path, but `sed`/`awk` program text and `ln -s` targets match those names, a `git`, `gh` or `curlrc` entry under `.config/` or `$XDG_CONFIG_HOME`, and a `gh` entry under `.local/share/` or `$XDG_DATA_HOME`, as text wherever they point, since that text is never resolved. A repository's git configuration and hooks are protected wherever its `.git` directory sits (any repo, any depth), because git runs code named there on its next command (`core.hooksPath`, `core.fsmonitor`, `core.pager`, aliases, filter drivers, `include.path`, every hook): the `.git` entry itself (a submodule's or worktree's `gitdir:` pointer file), `.git/config`, `.git/config.worktree`, `.git/commondir`, `.git/hooks` and everything under it, and the whole `.git/modules` and `.git/worktrees` trees, which hold each submodule's and linked worktree's own config, commondir and hooks. The match is anchored on `/.git`, so `.github/`, `.gitignore`, `.gitmodules` and a bare repository named `x.git` stay writable, as do `.git/info/exclude` and `.git/info/attributes` (attributes only select a filter, diff or merge driver whose command lives in the protected config, and the work tree's own `.gitattributes` selects them already). `sed`/`awk` program text matches `.git/` followed by `config`, `hooks` or `commondir`, and the `.git` entry itself, as text, unanchored, since sed reads `w.git/config` as a `w` command; an `ln -s` target anywhere inside a `.git` tree, and a writer's working directory anywhere inside a `.git` directory, block. git's own commands still write inside `.git` (`git -C . commit`, `fetch`, `checkout`, `submodule update`, `worktree add`), since they are not write targets, and `git config` writes are already blocked at every scope by `enforce-git-policy`. `/dev/null`, `/dev/stdout` and `/dev/stderr` are always allowed. An unquoted glob is expanded and every match is checked against the protected paths too. A writer (`git` and `gh` only when they write) can also write into its working directory without naming a path (`curl -O`, `gh release download`), so it is blocked when that directory is anywhere inside a `.claude` tree, `/etc/claude-code`, a `.git` directory, `~/.config`, `$XDG_CONFIG_HOME`, `~/.local` or `$XDG_DATA_HOME` (from there a `..` in a sed `w` name reaches a protected entry): such a `$PWD`, leading `cd` or `git -C` target, or a `cd` into one anywhere in the same command. A `cd` there to read, with no writer, stays allowed.

The `Edit|Write|NotebookEdit` registration checks only the file tool's path against the protected paths, with no roots check and no shell parsing, so the protected list and the resolver exist in one place. The tracked sources under `containers/base/development-full/` carry no `.claude/` path segment, so hook development is unaffected.

Accepted gaps, each held instead by the managed-settings locks, the root-owned `/etc/claude-code` and the agent entrypoint's refusal to start on a repo checkout whose `.claude/settings*.json` or `.mcp.json` differs from `origin/main`: code run by a writer (an interpreter, npm/bun scripts, `dotnet run`, pre-commit hooks) and files a tool writes implicitly (caches, `node_modules`) are not visible on the command line, and such code can replace the root-owned `~/.claude` wholesale (`developer` owns `/home/developer`, so it can rename the directory away and recreate it, adding skills or agents), so a root-owned `~/.claude` only stops direct writes and is not the guarantee: that is `/etc/claude-code`, root-owned with root-owned ancestors, whose locks still stop permissions, hooks and MCP servers being added; an `awk` or `sed` program can build a file name at run time, and a program file given with `-f` is not read; and git subcommands that write the working tree from commit content (`merge`, `cherry-pick`, `reset --hard`, `stash`, `pull`, `switch`, `checkout <branch>`, `rebase`) can write a protected path with nothing protected on the command line; a git directory that is not under a `.git` path (a bare repository such as `x.git`, or a `--separate-git-dir` target outside every `.git` directory) is not protected, and a recursive copy of a directory whose contents include a `.git` tree or another protected name (`cp -r /tmp/d/. .`) names nothing protected, since only what is created directly inside the destination is checked. Blocking those git subcommands would break normal branch, rebase and update work, so do not add such a block without the owner's agreement. A repo settings file's `env` keys are not covered by the managed locks and are out of this hook's scope. Accepted false positive: a writer argument or `sed`/`awk` program that merely mentions a protected path is blocked; make that text edit with the Edit tool. That includes text naming anything under any `claude-code` directory (`node_modules/@anthropic-ai/claude-code/cli.js`, a file in a checkout of a repo named `claude-code`) and an `ln -s` target anywhere inside a `.claude` tree; a bare `claude-code` (`npm install @anthropic-ai/claude-code`, `gh repo clone anthropics/claude-code`) stays allowed outside an `ln -s` target. Every word reaches these checks as bash passes it to the command: quoting removed, and with it each backslash bash removes (every unquoted one, and inside double quotes one before `$`, `` ` ``, `"` or `\`), so a text check (program text, an `ln -s` target, an option or subcommand name such as `find -\exec` or `git -\C`) sees what the command receives, while a single-quoted backslash, which the command does receive, is kept, so `sed 's/\.claude\.json/x/'` stays allowed. A command that decodes the backslash escapes it receives before using the text as a file name is also checked with them decoded: `awk` in its string literals and `-v`/`name=value` values (an unknown escape is the plain letter, so `".c\laude"` is `.claude`; octal is masked to a byte; `\x` is checked reading two hex digits, as gawk 4.2+ does, and every digit, since gawk before 4.2 kept consuming hex digits; a NUL ends the name; a backslash-newline is removed; a `\u` escape followed by a hex digit blocks outright, because gawk 5.3+ and `sqlite3` decode it as a code point and gawk reads no fixed number of digits, so `\u002e2c` and `\u0000002e2c` both give `.2c`), and `sqlite3` in a double-quoted dot-command argument (`.once "\056claude/..."`), checked for every writer argument in `queue_write_target`. GNU `sed` reads a `w` or `s///w` file name literally and `sqlite3` a single-quoted or unquoted one, so `sed` text is not decoded. Accepted false positive of the decoded check: awk text or a writer argument that only mentions an escaped spelling of a protected name (`awk '/\.claude\/settings\.json/'`) is blocked, as is a writer's literal argument that decodes to one (`awk -i inplace 1 '.c\laude/settings.json'`), and so is any such text or argument with a `\u` escape (`awk '{print "\u00e9"}'`). A path word written with a backslash outside single quotes still blocks.

Why a hook and not `permissions.allow`: the permission-rule syntax has only literal text and `*`, with no typed placeholder for "a directory goes here", so every `git -C <dir> ...`/`npm --prefix <dir> ...`/`find <dir> ...` allow entry had to carry a `*` in the directory position - which also matched any option injected there (`git -C d -c core.hooksPath=/evil status`), exactly what Claude Code's own startup warning ("has a wildcard before the rest of the command, so it also matches any options inserted at that position") is about. With this hook doing the positional check, those per-subcommand wildcard entries were removed from `claude-managed-settings.json`, leaving the bare tool-level entries (`Bash(git -C *)`, `Bash(find *)`, `Bash(npm ci *)`, ...) plus matching `permissions.deny` entries for the same code-execution flags as belt-and-braces. Those denies are plain substring patterns, and are a *real* second layer only because `reject-obfuscated-commands` has already rejected every quote-splice/substitution/non-ASCII form before either layer sees the command - do not reorder the chain so that this hook or the deny layer runs on an unnormalised command.

Path handling: each word is resolved with `realpath -m` (existing symlinks followed, so a symlink inside a root that points outside it fails; non-existent trailing components allowed) and must equal a root or sit beneath one. Relative paths resolve against the hook's own `$PWD`, or against the directory a single leading `cd <dir>`/`pushd <dir>` lands in when that is the command's very first call. A `cd`/`pushd` target is where bash's logical `cd` lands: the path with `..` removed as text (`realpath -ms`), then resolved (`realpath -m`), so `cd .claude/link/..` is checked as `.claude` wherever `link` points, and a `cd ..` from inside a symlinked directory is checked as the directory it really reaches; that landing must sit under a root, is what the in-a-`.claude`-tree writer rule checks, and must be an existing directory the shell can enter with every component before a `..` a directory, because otherwise bash falls back to a physical `cd` of the words as given, which the hook does not follow; any other `cd`/`pushd`/`popd` arrangement (more than one, not first, nested in a substitution) makes the working directory unknowable to static parsing, so later *relative* paths block and absolute ones still work, and a `cd` to a glob blocks outright. An unquoted glob (`*`, `?`, `[`) in a path word is allowed - only the literal prefix before it is resolved, since pathname expansion can never match `..` - but an unquoted brace expansion (a `{` with a `,` or `..`), a tilde bash would expand (leading, or after an unquoted `=` or `:`) and a backslash outside single quotes are blocked outright (each can turn one literal into a different word at runtime); quoted characters are literal. A non-literal word in a path position blocks, and so does a non-literal command name. Same shfmt AST walk and base64-per-word transport as `enforce-ssh-host-and-key`; fails closed on missing `jq`/`shfmt`/`realpath`, unparseable shell, an unreadable `command-allowlist` or no usable roots. No auto-correct: a path outside the roots is a fact about what the command would do, not a syntax slip.

Two consequences of having no wildcard entries that are easy to trip over: `npm --prefix <dir> ci` matches no allow entry (there is deliberately no `Bash(npm --prefix * ...)` replacement, that shape is the warning), so write it as `npm ci --prefix <dir>` - npm accepts the option after the subcommand, `Bash(npm ci *)` matches it, and the hook validates the directory wherever it appears (including npm's `-C` alias and nopt abbreviations such as `--prefi`). And `npm_config_*`/`NPM_CONFIG_*` environment prefixes are on `env-var-blocklist`, since npm reads every option from the environment too. Similarly, a bare `git <subcommand>` with no `-C` is auto-corrected to `-C "$PWD"` by `enforce-git-policy` and allowed via `updatedInput`, which this hook never sees, so this hook checks the hook's own working directory for a `-C`-less git call exactly as it would check `-C .`.

Five more rules, each closing a verified bypass: a glob word may not contain a `..` component anywhere (`su*/../../etc` - the glob itself never matches `..`, but bash expands the literal `..` after it exactly as written, and only the pre-glob prefix is resolved); once a call that can create a symlink has appeared earlier in the same command (`ln`, `cp`, `mv`, `tar`, `unzip`, `rsync`, or a git subcommand that materialises repo content: checkout/switch/restore/clone/pull/merge/rebase/stash/apply/reset/...), every later checked path must already exist, because `realpath` resolves links as they are at hook time and `ln -s /etc root/l && rm -rf root/l/*` would otherwise pass - split such commands in two; `cp`/`mv` `--target-directory` is recognised in every getopt spelling (any unique abbreviation such as `--target=`, and `-t` inside a bundled cluster such as `-rt/etc`); npm long options are recognised with one dash as well as two (`-script-shell`, `-prefix` - nopt strips all leading dashes), and the `permissions.deny` pairs cover both; and `env-var-blocklist` matching in `reject-obfuscated-commands` is case-insensitive, since npm honours any case of `npm_config_`.

Configuration: `claude-hooks/allowed-dirs` next to the hook, one absolute path per line, `#` comments, a leading `~` expands to `$HOME` and a leading `$NAME` to that variable (a line whose variable is unset is skipped; a relative line is ignored). The shipped copy lists the agent container's three mounts (`/workspace/repo`, `/workspace/rules`, `/workspace/tmp`) and is baked root:root 0444; the Dockerfile sanity block asserts all three are present and that no `allowed-dirs.local` was baked in. On a host (via `install-claude-hooks`), those paths do not exist, so an `allowed-dirs.local` installed root-owned next to the hooks from the installer's path argument (never shipped; e.g. `~/work` and `$TMPDIR`) takes precedence when present - the installer says so if it is missing rather than inventing a host layout. Extending the checked-command set: add a `check_<name>` function and its dispatch case in the hook, and a matching `permissions.deny` entry for any new code-execution flag; give a writer whose arguments routinely carry text a dedicated target rule in `queue_writer_targets` rather than reclassifying it `read-only`; widen roots only via the data file. Known limitation accepted for v1: `find` with a starting point outside the roots (e.g. `find /usr/lib -name x`) is blocked; a separate read-only roots list is the fix if that need ever materialises.

## block-secret-file-reads

Runs third in the `Bash` chain, after `enforce-allowed-dirs`, and is also wired to the `Edit|Write|NotebookEdit` entry (after `enforce-allowed-dirs`) and to its own `Read` entry. It is the second of two layers that keep secret-bearing files (`.env`, `.env.*`, `*.env`, `.database`) out of the agent's reach; the first is container-side masking.

- **Layer 1, masking.** `add_secret_mask_podman_args` in `lib/podman`, called from `prepare_claude_container_args`, finds every regular file under the repository whose basename matches a pattern (pruning `.git`, never following symlinks) and adds `--volume /dev/null:/workspace/repo/<path>:ro` for it, so the container sees an empty, read-only file. It warns with the list of masked files, and dies if the pattern file is missing, unreadable or lists no pattern.
- **Layer 2, this hook.** For `Bash` it parses the command with `shfmt --tojson` and checks every literal word and every redirection target that is not a heredoc, after glob expansion and symlink resolution, against the patterns; a match denies the call. The value of an exclusion option (`--exclude=.env`, `-not -name .database`) passes, so the mandated search exclusions keep working. A word containing whitespace is prose (a commit message, a comment body) and blocks only when it names an existing file. A here-string word is blocked when it matches, without trying to tell data from a path. For `Read`, `Edit`, `Write` and `NotebookEdit` it checks the resolved file path. Any parse or lookup failure denies (fail closed).

Configuration: `claude-hooks/secret-files` next to the hook, one basename glob per line, `#` comments. It is baked root:root 0444; a `secret-files.local` next to it takes precedence when present. The Dockerfile sanity block fails the build if a `secret-files.local` was baked in, and `install-claude-hooks` never installs one.

Accepted gaps: Layer 1 does not mask a symlink to a secret file, but the hook resolves symlinks and blocks it; a prose word is checked only when it names an existing file; a name built at run time (`cat "$(printf .en)v"`) or opened by interpreter code is not visible to either the hook or the permission checker, and only Layer 1 covers it; `config.env.example` does not match any pattern and is not masked; masking `.database` inside the container means any tool there that needs it sees an empty file.

## enforce-git-identity

Runs after `block-secret-file-reads`, before `enforce-git-policy`. Blocks git subcommands that create/rewrite commits, plus `fetch` (checked up front so a broken identity is caught before work starts, not after) - `commit`/`fetch`/`pull`/`rebase`/`merge`/`cherry-pick`/`revert`/`am` - unless git identity and GPG signing are correctly configured (`user.email` set and not the banned identity, `commit.gpgsign` true, a GPG secret key present for that email, `user.signingkey` set and matching a keyring entry for that email). No safe auto-correct: the problem is missing/misconfigured system state (git config, GPG keyring), not a fixable command string - nothing in the command text can be rewritten to make a signing key exist.

## enforce-git-policy

Parses each Bash command with `shfmt` and blocks any `git` invocation (including `sudo git ...` and other known wrapper prefixes) that isn't hardened with `git -C <dir>`. Also blocks `eval`/`source`/`.` outright, since their argument is a second command line this hook cannot verify. Fails closed if `shfmt` is missing or the command doesn't parse.

**Subcommand allowlist.** Every git call's subcommand (whatever follows `-C`, or the bare `git` token before the auto-correction below ever runs) is checked against the hardcoded `GIT_ALLOWED_SUBCOMMANDS` array near the top of the hook - not a data file like `command-allowlist`, since this hook is its only consumer and the actual enforcement is this hook's own AST-based parse (see the "No blanket `Bash(<tool> *)`" section above for why a `claude-managed-settings.json` pattern can't do this job). A missing subcommand or one not on the list blocks outright, before the `config`/`clone`/auto-correct handling described below even runs, so a disallowed subcommand is never rewritten into an allowed-looking call by the missing-`-C` auto-correction. The shipped list: `add`, `branch`, `checkout`, `cherry-pick`, `clone`, `commit`, `config`, `diff`, `fetch`, `log`, `ls-files`, `ls-remote`, `ls-tree`, `merge`, `pull`, `push`, `rebase`, `reset`, `rev-list`, `rev-parse`, `show`, `stash`, `status`, `switch`, `worktree` - each entry has a confirmed use in this repo's own `ai/global`/`ai/local` instructions or a confirmed live need raised directly by the repo owner (widen minimally: add only what is actually cited or asked for). `config` and `clone` still need their own listed entries here even though they also get their own dedicated handling below, and `worktree`'s `add` vs non-`add` split is a separate, later concern for `block-git-worktree`. `cherry-pick` is listed because the owner has a live need for it. `ls-files` and `ls-tree` are read-only and carry no flag restriction. Notably absent despite being common git subcommands: `am`, `mv`, `remote`, `restore`, `revert`, `rm`, `tag` - none has a confirmed need in this repo's documented workflow (use `git config --local` instead of `remote`); add any of them back only once a genuine need surfaces.

A missing `-C` auto-corrects instead of blocking when it is safe to: no directory-changing call (`cd`/`pushd`/`popd`, plain, wrapped, or backslash-escaped) appears anywhere in the command, and `git rev-parse --show-toplevel` confirms the hook's own `$PWD` sits inside a writable git checkout - `-C <$PWD>` (never the resolved toplevel, which can differ from `$PWD` when it runs from a subdirectory) is then spliced in after every bare `git` token and returned via `hookSpecificOutput.updatedInput`, merged with the original `tool_input` so sibling fields such as `run_in_background`/`timeout` survive the rewrite instead of being silently dropped to their defaults (see the fuller explanation under [Non-ASCII / Layer 0 block](#non-ascii--layer-0-block) above). Otherwise (a directory-changing call present, no enclosing repository, or an unwritable/foreign checkout) it blocks - see [Prefer auto-correction over blocking](#prefer-auto-correction-over-blocking-when-its-a-genuine-correction) above for why this auto-correction is a genuine correction rather than a no-op.

**Hook-bypass flags and overrides.** This is the only guard against git hook-bypass flags (no external npm tool is wired in as a hook), and it uses this hook's existing AST parse rather than a second hand-rolled tokenizer. `check_hook_bypass_flags()`, called from the per-call loop for every subcommand in `GIT_SUBCOMMANDS_HOOK_BYPASS_CHECK` (`cherry-pick`, `commit`, `merge`, `pull`, `push`, `rebase` - each one reachable, i.e. present in `GIT_ALLOWED_SUBCOMMANDS`, since a subcommand this hook already blocks outright never reaches this check, as `am` below illustrates), independently of whether `-C` is present or auto-corrected, since a hardened commit can still carry a bypass flag: the long-form `--no-verify` blocks on all six (`pull` has a real `--no-verify` too - it controls the pre-merge-commit/commit-msg hooks on the merge `pull` performs internally); the short form `-n`, or a short-flag bundle containing it (e.g. `-vn`), blocks only when the subcommand is `commit` - on `push`/`merge`/`pull`/etc the same letter means something else entirely (dry-run/no-stat). The short-form scan is restricted to a genuine single-dash word (`-[!-]*`, second character not itself a dash) so a real GNU-style long flag that merely contains the letter n (`--no-color`, `--no-edit`, `--annotate`, ...) is never misread as a bundle. A standalone or value-attached `-F`/`-c`/`-C`, and a standalone or value-attached `-m` on `commit`/`merge`/`cherry-pick` only (commit's own value-consuming flags, distinct from the global `-c`/`-C` options handled earlier in the same call) has its value skipped entirely - attached (`-mwip-new`) or as the following word (`-F -n`, where `-n` is `-F`'s filename argument) - so a commit message or filename can never be mistaken for a flag. `-m` takes a value only on those three: on `rebase` it is a bare `--merge` flag with no argument (unlike `commit -m <msg>`, `merge -m <msg>`, or `cherry-pick -m <parent-number>`, where it takes one), so treating it as value-consuming there would swallow a following `--no-verify` unseen (`git rebase -m --no-verify`); `push` has no `-m` flag at all, so treating it as value-consuming there has the same effect (`git push -m --no-verify`) - the check only consumes `-m`'s value on `commit`/`merge`/`cherry-pick` and leaves `-m` alone (next token scanned normally) everywhere else, including `rebase` and `push`. `am` is deliberately not in `GIT_SUBCOMMANDS_HOOK_BYPASS_CHECK` even though it also has a `--no-verify` flag: it has no confirmed use in this repo and is already blocked outright by the subcommand allowlist above, so a call with that subcommand never reaches this check - adding it would be unreachable dead code. `-c core.hooksPath=...` is deliberately NOT duplicated here either: `enforce-allowed-dirs` (earlier in the `PreToolUse` chain) already denies any `git -c` key outside its small inert allowlist, for every subcommand, not only the six above - see that hook's own section below. `git --config-env` (both spellings) is the exception: this hook blocks it too, in its single walk over the global options before the subcommand, as a second layer, because its value is read from an environment variable when git runs and so can never be checked, and blocking it here keeps it blocked if `enforce-allowed-dirs` is ever not installed. The same walk blocks an empty `-C` argument (git reads `-C ""` as the current directory, so it would satisfy the must-have-`-C` rule without naming a directory) and stops at a second `-C`, leaving it as the subcommand for the allowlist above to reject. Separately, `HUSKY=0` (plain, or quoted as `HUSKY="0"`/`HUSKY='0'`) is blocked via a plain regex over the raw command text rather than the AST - it is an env-var assignment, not a git argv token - anchored to a real assignment boundary (start-of-input or a `;`/`&`/`|`/whitespace separator immediately before it, end-of-input or another separator immediately after) so an unrelated word merely containing the substring (`MYHUSKY=0`, `HUSKY=01`) does not match, and checked unconditionally, independent of whether the command contains a git call at all - mirroring the `hasHuskySkip` semantics of the npm `block-no-verify` tool this check replaced. This retains one residual false-positive class the AST approach elsewhere in this hook exists to avoid: a quoted commit message that happens to contain " HUSKY=0 " surrounded by spaces would still match, since the regex has no visibility into quoting; this is a deliberate, scoped trade-off (matching that npm tool's known behaviour for this one check), not an oversight.

**Abbreviated, quoted and ANSI-C `--no-verify` spellings.** `check_hook_bypass_flags()` must catch three spellings beyond the flag's canonical, unquoted form. (1) git's own option parser accepts any unambiguous prefix of a long option, so an exact-only `--no-verify` case arm would let a shorter, still-working spelling straight through. The case arm also matches `--no-v`/`--no-ve`/`--no-ver`/`--no-veri`/`--no-verif`, applied uniformly across all six subcommands in `GIT_SUBCOMMANDS_HOOK_BYPASS_CHECK` rather than picking one cutoff per subcommand; the reasons split into two cases. `--no-v`/`--no-ve`/`--no-ver` are ambiguous with `--no-verbose` on `commit`/`push`/`merge`/`pull`/`rebase` (each has `-v`/`--verbose`; confirmed live: `git push --no-ver` reports "ambiguous option: no-ver (could be --no-verbose or --no-verify)"), so pre-blocking those three shorter spellings on those five only swaps git's own ambiguous-option error for this hook's, with no functional difference. `--no-veri`/`--no-verif` are narrower: only `merge` and `pull` also carry `--[no-]verify-signatures` (confirmed live on `merge`; `git pull -h` lists the same colliding flag), so those two stay ambiguous down to the full spelling and pre-blocking them there is likewise just a duplicate error - but `commit`/`push`/`rebase` have no such collision, so `--no-veri`/`--no-verif` are genuine, unambiguous, working bypass spellings on those three and would otherwise slip through unblocked. `cherry-pick` has neither colliding flag, so `--no-v`/`--no-ve`/`--no-ver` are genuine, unambiguous, working spellings of `--no-verify` there too (confirmed live: `git cherry-pick --no-v <bad-revision>` reaches git's "bad revision" error, not an option error) and would otherwise slip through unblocked. (`git cherry-pick -h` lists no `--no-verify`/`--verify` flag at all, unlike the other five subcommands here - the "bad revision" observation above is consistent with cherry-pick's unknown-option pass-through rather than a real flag it acts on; blocking it regardless is fail-safe either way.) (2) The scan must not read each word from the same conservative `words` array the command-name/-C gate uses, where any quoted or split-quoted text (`"--no-verify"`, `--no-ver"ify"`) is opaque (the words line's own marker byte, documented in the "calls" extraction comment further up) by design - safe for the command-name gate, since `reject-obfuscated-commands` already handles obfuscated names upstream, but wrong for an argument-value scan: the shell strips quoting before git ever sees the argument, so a quoted `--no-verify` is exactly as effective a bypass as an unquoted one. `check_hook_bypass_flags()` reads a separate `resolved` array instead (populated by a third jq output line, `resolve_parts`, alongside the existing `words`/`ends` lines), which concatenates a word's `Lit`/`SglQuoted`/`DblQuoted`-of-only-those-parts into its real literal value and falls back to the same marker value only for a genuine expansion (`$VAR`, `$(...)`) whose value cannot be known statically. A resolved value that itself contains a raw tab or newline (a multi-line quoted commit message, say) is folded back to the opaque marker rather than emitted as-is: either byte fractures the tab/newline-joined transport between jq and bash and trips the desync guard on every later call in the same command (without the fold, `git -C . commit -m "<two lines>" && git -C . push` is blocked as a desync). No flag this scan matches contains whitespace, so nothing is lost. This is deliberately a second, parallel array rather than a change to the `words` line itself: the "an obfuscated git name is opaque to this hook" test relies on the command-name/-C gate staying conservative about adjacent-quoted-literal splicing there, delegating it to `reject-obfuscated-commands` upstream - only the hook-bypass argument scan needed the richer resolution. (3) An ANSI-C quoted word (`$'...'`) with a backslash escape (e.g. a hex or octal escape spelling out the flag without the literal substring `--no-verify` ever appearing in the source text) is a third quoting form `resolve_parts` cannot safely fold into either of the above: shfmt's AST stores its *source* text verbatim, backslashes included, not the value bash actually substitutes at runtime, so naively treating that source text as the literal value would silently trust unparsed escape syntax as if it were already-decoded, and this hook does not implement bash's ANSI-C decoding rules to compute the real value instead. Rather than either resolving it wrongly or folding it into the ordinary opaque marker (silently allowed through, appropriate for a genuinely dynamic `$VAR` whose value truly cannot be known here, but this one is fully static and just not decoded), a word containing a backslash-bearing `$'...'` part resolves to a third, distinct sentinel (`ANSI_C_ESCAPE_MARKER`, a different codepoint from the opaque marker so the two can never collide) that `check_hook_bypass_flags()` blocks on outright with its own message, asking for the flag to be spelled plainly - failing closed on the one quoting form this hook cannot evaluate. A `$'...'` with no backslash - its source text already is its value - is unaffected and resolves normally like any other quoting. The words line spells its opaque marker as a unicode escape in the jq source; the resolved line builds the identical codepoint via `[1] | implode`, so both lines agree on what opaque means. `ANSI_C_ESCAPE_MARKER` is `[2] | implode`, a different codepoint, so the two resolved-line sentinels can never collide.

**Unquoted backslash escapes.** A fourth quoting mechanism `resolve_parts` must cover: a bare backslash before an ordinary character in an *unquoted* word, e.g. `--no-\verify` - decodes to `--no-verify` when bash actually runs the command (confirmed live: `printf '%s\n' --no-\verify` prints `--no-verify`), since outside any quoting bash's rule is simply "drop the backslash, keep the next character" for any character, not only shell metacharacters. shfmt's AST keeps this form's raw source text (confirmed live via `shfmt --tojson`: `Lit.Value` for that word is literally `--no-\verify`, backslash and all), so unwrapping it verbatim like `Lit`/`SglQuoted`/`DblQuoted` would produce a resolved value that matches no `check_hook_bypass_flags()` case arm and the flag would slip through unblocked - a real bypass, since (unlike the `-c`/`-C`/`-F` over-skip cases discussed elsewhere) git's own parser genuinely receives `--no-verify` here rather than an unrecognised option it would otherwise reject. Unlike the ANSI-C case above, there is nothing to reimplement: the decode is a trivial `\X → X` for a top-level `Lit` part, so `resolve_parts` takes an `unquoted` parameter, true only for the call directly on an arg's own top-level `Parts` and false for a `Lit` nested inside a `DblQuoted`, since backslash inside double quotes is special only before `$`, `` ` ``, `"`, `\` and newline - not before an arbitrary letter - so a quoted `"--no-\verify"` genuinely stays `--no-\verify` at runtime and decoding it the same way would be wrong, not merely redundant.

**`HUSKY=0` subshell boundaries.** The `HUSKY=0` raw-text regex's assignment-boundary character classes (`^|[;&|[:space:]]` leading, mirrored trailing) must include `(` and `)`, so `(HUSKY=0 git -C . commit -m x)` is caught: `reject-obfuscated-commands` walks into a parenthesised subshell rather than rejecting it outright and does not add `HUSKY` to `env-var-blocklist`, so this hook is the only layer that looks at `HUSKY` at all. `HUSKY` only affects the npm `husky` tool, not this repo's `pre-commit`-based hooks, so the check exists to keep the `hasHuskySkip` coverage of the npm `block-no-verify` tool it replaced rather than as a load-bearing gate - but a subshell gap would break that parity, unlike the intentional quoted-commit-message trade-off described above.

**`HUSKY=0` ANSI-C and unquoted-backslash spellings.** Beyond the plain/double-quoted/single-quoted spellings (`0`, `"0"`, `'0'`), the `HUSKY=0` value alternation must match two more spellings that decode to the identical literal `0` at real bash runtime: a no-escape ANSI-C quote (`HUSKY=$'0'`, confirmed live via `shfmt --tojson` - `Dollar: true` with decoded `Value: "0"`, the same "source text already is its value" case the ANSI-C paragraph above already treats as safe to resolve when there is no backslash escape) and a bare unquoted backslash before an ordinary character (`HUSKY=\0`, the identical "drop the backslash, keep the next character" rule the unquoted-backslash paragraph above already implements for `resolve_parts`, applied here to this separate raw-text check). An escaped ANSI-C form (`$'\060'`, `$'\x30'`, ...) is deliberately out of scope, for the same reason the AST-side `ANSI_C_ESCAPE_MARKER` case fails closed rather than decoding: it would mean reimplementing bash's whole escape-sequence table for this one raw-text regex, not resolving text that is already its own value.

**A bundle-trailing value-consuming letter.** The `-[!-]*` short-flag-bundle arm must not only check its token's own text for the letter `n`; it must account for git's own bundling rule that when the *last* letter of a bundle is itself value-consuming (`m` on `commit`/`merge`/`cherry-pick`, or `F`/`c`/`C` anywhere) and nothing is attached after it in the same token, git takes that value from the *next* word - exactly like the bare `-m`/`-F`/`-c`/`-C` arms already handle, just one bundling layer deeper. Without this, `git commit -am -m --no-verify` would slip through unblocked: git's own parser consumes the second `-m` word as `-am`'s trailing `-m`'s message value (a commit message that happens to read `-m`), leaving `--no-verify` as the next, unconsumed, genuinely-live flag - while a scan that never learned `-am`'s value was the following word would walk into that same following word (`-m`) as if it were a fresh flag of its own, match the bare `-m` arm, and skip `--no-verify` in turn, believing it was `-m`'s value instead. The check inspects the bundle's trailing character (`${tk: -1}`) the same way the bare-flag arms already do, consuming the next word whenever that letter is value-consuming for the current subcommand.

**A non-leading value-consuming letter inside a bundle.** Inspecting the bundle's own text as a whole (a substring test for the letter `n`, plus the trailing-character check above) is not enough: the bundle must be walked one character at a time, because git's bundling rule applies the instant a value-consuming letter (`F`/`c`/`C` anywhere, `m` only on `commit`/`merge`/`cherry-pick`) is hit, not only when that letter is trailing: every character remaining in the token becomes its attached value, regardless of position - confirmed live, `git commit --dry-run -aCbogusrev123` and `git commit --dry-run -Cbogusrev123` fail identically, both resolving `bogusrev123` as `-C`'s value. `git commit -aFnotes.txt` is therefore `-a -F notes.txt` with no `-n` flag anywhere, yet a whole-token substring test for `n` would match the letter inside `notes.txt`'s own filename and falsely block a fully legitimate commit. Walk the bundle one character at a time: continue past bare flags, block immediately on a bare `n` when `sub` is `commit`, and the instant a value-consuming letter is hit, stop scanning the token - consuming the *next* word only if nothing remains after that letter in the same token (the trailing case above), otherwise treating the remainder as its already-attached value, exactly like git's own parser.

**An opaque-marker fallthrough for dynamic expansions.** `resolve_parts` folds any argument containing a genuine dynamic expansion (`$VAR`, `$(...)`, ...) to the same opaque marker the words line uses, on the reasoning that a truly dynamic value cannot be checked here and letting it through is no worse than letting the words line's own opaque values through elsewhere. But `check_hook_bypass_flags`'s `case` statement needs an arm for that marker, otherwise it falls through as a silent no-op rather than failing closed - and an argument built by splicing a dynamic expansion against adjacent literal text is not actually unpredictable: `-${x}n` or `-$(true)n` each expand to an empty string at real bash runtime, leaving a plain `-n` once git parses it, confirmed live via `shfmt --tojson` (the composite argument's `Parts` contain a `ParamExp`/`CmdSubst` alongside `Lit` pieces, so `resolve_parts`' `reduce` hits its `else null` branch and the whole argument folds to the opaque marker like any other non-literal value) - a real, working `-n` bypass. A dedicated `OPAQUE_MARKER` bash variable (matching the jq-side codepoint via the same construction as `ANSI_C_ESCAPE_MARKER`) and a catch-all case arm fail closed on it, exactly mirroring the existing `ANSI_C_ESCAPE_MARKER` arm: an argument this hook cannot statically resolve is never silently skipped, whether the reason is an undecoded escape or a genuine expansion.

**The end-of-options marker (`--`).** `check_hook_bypass_flags` honours git's own `--` end-of-options marker: every argument after the first literal `--` is an operand/pathspec to git, never a flag, regardless of spelling. A `--` token matches none of the case arms, so a scan that walked straight past it and kept scanning what followed would falsely block a fully legitimate `git commit -- --no-verify` (referencing a path literally named `--no-verify`, the canonical use of `--`) as if `--no-verify` were a live flag. This is a false-positive/usability gap, not a bypass in the other direction: a real `--no-verify` appearing before the first `--` is still caught positionally, and git itself would never treat anything after `--` as an option either, so there is nothing to smuggle past this hook by placing it after `--`. It returns from `check_hook_bypass_flags` outright the instant a literal `--` token is seen, matching git's own behaviour that only the first `--` matters.

**One `-m`-consumes-a-value subcommand set.** Keep the subcommand set (`commit`/`merge`/`cherry-pick`) for the whole-token `-m` arm and the bundle-walk's per-character `m` arm in `GIT_SUBCOMMANDS_M_CONSUMES_VALUE`, alongside the other `GIT_SUBCOMMANDS_*` arrays at the top of the file; both arms test membership via the existing `in_list` helper, so a change to that set (e.g. matching a change to `am`'s exclusion above) cannot update one call site and silently miss the other.

## block-git-worktree

Runs after `enforce-git-policy`. Blocks `git worktree add` (creating a new linked worktree) - a linked worktree splits repo state across multiple checkouts sharing one object store and one set of refs, which does not compose with this project's assumption of one checkout per repo directory. An errant `git worktree add` can leave a primary checkout registered as bare with no work tree of its own, breaking `git pull`/`git status` there until it is manually repaired. It also blocks `git worktree move`, which relocates a linked worktree and so keeps that layout in use. A quoted literal word (`"add"`, `'move'`, or a double-quoted word with no expansion inside) counts the same as the bare word, since it runs the same; a word with an expansion or ANSI-C/locale quoting stays opaque. Other worktree subcommands (`list`/`remove`/`prune`/`lock`/`unlock`/`repair`/...) are inspection or cleanup of worktrees that already exist and remain allowed. The subcommand is found by skipping the `-c <k>=<v>`/`-C <dir>`/`--config-env <k>=<env>` global option pairs and the one-word `--config-env=<k>=<env>` form, in any order, so the block holds on its own whichever other hooks are installed. Uses the same shfmt-parsed AST approach as `enforce-git-policy` and fails closed the same way. No safe auto-correct: `add` is a categorical policy block, not a syntax mistake, and there's no equivalent allowed command to substitute - the suggested alternative (a normal branch checkout) requires the agent to choose a branch name/target itself.

Word extraction uses the same delimiter-collision-free, base64-per-word, JSON-array-per-call transport as `enforce-ssh-host-and-key` (see that hook's section below), not a plain tab/newline text-join, because a text-join transport has two independent desync bugs: a `Lit` word containing a real embedded tab byte (via backslash-tab escaping) desyncs `IFS=$'\t' read -ra`, and a non-literal word emitted as an empty string rather than a `\x01` marker is silently dropped by tab's IFS-whitespace collapsing, shifting later words (including `worktree`/`add` itself) out of the position being checked - each a complete bypass (the command is allowed instead of blocked). Literal recognition stays narrower than `enforce-ssh-host-and-key`'s (`Lit` only, not `SglQuoted`/single-part `DblQuoted`) - the transport choice is about desync, not widening detection.

Also registered in `claude-managed-settings.json` under its own `"matcher": "EnterWorktree"` `PreToolUse` entry, covering Claude Code's native `EnterWorktree` tool, a first-class tool that performs the equivalent of `git worktree add` directly, with no shell command string for the shfmt/AST parsing above to inspect (a hook wired only to the `Bash` matcher never sees it). The same script dispatches on the hook payload's own `tool_name` field: `"EnterWorktree"` goes to the dedicated check below; `"Bash"` or empty/absent (every Bash-shaped payload, including every existing test) goes to the shell-command path; any other value is an unrecognised tool identity and is blocked outright, fail closed. An `EnterWorktree` call is allowed only when it is entering a worktree that already exists (a non-empty `path` and no `name` **present at all**; an explicit empty-string `name` is blocked too, not treated the same as an absent one); every create-shaped combination is blocked (no `name`/`path` at all, `name` only, an empty `path`, or `name`+`path` both set: the last is malformed per the tool's own "mutually exclusive" contract and is failed closed rather than guessed at). `ExitWorktree` gets no equivalent guardrail: per its own tool description it is scoped to worktrees the *current session* created via `EnterWorktree`, is a documented no-op otherwise, and is inspection/cleanup-shaped like the already-allowed `git worktree` subcommands above.

Every `jq` call in this hook (`tool_name` extraction, the `EnterWorktree` `allowed` check, `raw_cmd` extraction, and both stages of the per-call word decode) is guarded with `|| block '...'`, same as `enforce-ssh-host-and-key` - an unguarded `jq` failure would silently disable both the `EnterWorktree` guardrail and the shell-command `git worktree add` block in the same call. `base64` - the decode half of the word-extraction transport above - is guarded the same way: a missing `command -v base64` blocks up front, and the per-word `base64 -d` is chained with `&&` into the same command substitution so a decode failure propagates to `|| block` rather than silently decoding to an empty string (which would make `tok` never equal `git` and let the command through). An empty/absent `raw_cmd` on the shell-command path blocks: on this dual-registered hook, "no command" is indistinguishable from a mis-dispatched `EnterWorktree`-shaped payload (`tool_name` absent/empty, no `command` key, only `name`/`path`).

## block-dotnet-tool-install

Runs before `enforce-background-for-long-running-commands`. Blocks `dotnet tool install` (local or global - any flag combination) and `dotnet new tool-manifest`. This container's .NET global tools are pinned and baked into the image at build time (see the "dotnet tools" sanity check in `containers/base/development-full/Dockerfile`, which asserts an exact set of tool names via `dotnet tool list -g`); either command would add an unpinned, unreviewed tool outside that set, bypassing the dependency-selection review the pinned set went through. Other `dotnet tool` subcommands (`list`/`restore`/`uninstall`/`update`/`run`/`search`) and other `dotnet new` templates remain allowed. Uses the same shfmt-parsed AST approach as `block-git-worktree`/`enforce-git-policy` and fails closed the same way. No safe auto-correct: there's no pinned-tool substitute the hook could infer and inject on the agent's behalf - adding a new pinned tool is a reviewed image-build change, not something a command rewrite can do.

## block-github-mcp-write-tools

Registered against a separate `"matcher": "mcp__github__.*"` `PreToolUse` entry, not the `Bash` chain above (an MCP tool call has no shell command string to parse). Reads only `.tool_name` from the hook payload and blocks it outright, exact match, when it is one of the five GitHub MCP write tools that go through the GitHub API directly: `mcp__github__create_or_update_file`, `mcp__github__delete_file`, `mcp__github__push_files`, `mcp__github__merge_pull_request`, `mcp__github__update_pull_request_branch`. Every other `mcp__github__*` tool name (read-only ones, e.g. `mcp__github__get_pull_request`) is allowed. This protection is vendored here rather than relying on the npm `block-no-verify` tool, so it does not depend on a separately-installed global npm package being present. Fails closed: a missing `jq`, a payload that does not parse as JSON, or a missing/empty `tool_name` (this hook is only ever invoked for the `mcp__github__.*` matcher, so an empty `tool_name` means a malformed payload, not a read-only tool) all block rather than allow. No AST parsing is needed, unlike the Bash-command hooks above - this is a plain string match against a fixed, non-obfuscatable tool identity.

## The cfwf MCP server (managed-mcp.json)

`claude-managed-mcp.json` (installed as `/etc/claude-code/managed-mcp.json`, root:root 0444) is the only source of MCP servers: while it exists Claude Code loads no user, project, plugin or `--mcp-config` server. The container ships exactly one server, `cfwf`, an `http` server at `https://workflow-mcp.markridgwell.com/mcp`, and `mcp__cfwf__*` in `permissions.allow` gives every agent all of its tools.

- Never put a token, an `Authorization` header or any other secret in `managed-mcp.json`, as a literal `headers` or `env` value or otherwise: the file is world-readable. The `cfwf` header comes only from its `headersHelper`, the root-owned `/etc/claude-code/mcp/cfwf-mcp-headers` (from `claude-mcp/cfwf-mcp-headers`), which prints `{"Authorization":"Bearer <token>"}` from `GH_ENTERPRISE_TOKEN`, then `GH_TOKEN`, then `gh auth token`. That way the token already in the environment is reused and is never written to the image or to disk.
- Keep `${VAR}` expansion out of the `cfwf` entry. A managed server that uses one outside `env` is checked against `allowedMcpServers` and can be silently dropped.
- The helper must exit non-zero with nothing on stdout when it has no token, never print `{}` (an output without `Authorization` lets Claude Code fall back to OAuth discovery), never write the token to stderr or a file, and refuse a token outside the RFC 6750 token68 characters. `test/cfwf-mcp-headers.bats` holds these, and runs it under `env -i` so no token on the test host can leak in.
- Leave `enforce-curl-host` blocking the server's host. Only the MCP client may send the token there, never an agent's `curl`.
- The Dockerfile sanity block pins the file to exactly that one server, URL and helper, with no `headers`, `env` or `Authorization` text, the helper to root:root 0755, and the `mcp__cfwf__*` allow rule. Change those checks in the same change as the file.
- On a host, `install-claude-hooks` installs a `managed-mcp.json` that merges `cfwf` with the servers in `~/.claude.json` (user scope and every project scope), because the file would otherwise hide them. A server at `cfwf`'s URL is left out as a duplicate. A server whose `headers` or `env` value holds anything but `${VAR}` references (plus an optional `Bearer`/`Basic`/`Token` word), whose `url` carries userinfo or a query string, or whose `command` or `args` look like a credential (a `KEY=value` or `--flag=value` with a token/secret/password/api-key/auth/bearer name, a `ghp_`/`github_pat_`/`sk-`/`xox?-`/`AKIA` token, or a literal value after such a flag; `${VAR}` references are allowed) is refused by name and never copied, and only server names are ever printed. A name used for two different servers is fatal before anything is written. The merge is a snapshot, so a server added to `~/.claude.json` later needs the script re-run. Keep every one of these rules when changing the merge.

## enforce-ssh-host-and-key

Runs after `block-dotnet-tool-install`, before `enforce-background-for-long-running-commands`. Restricts `ssh` to exactly the form `ssh user@host command...`, added because `claude-managed-settings.json`'s `Bash(ssh *)` allow entry is blanket - the danger ssh poses is in the *destination*, not the verb, which a `permissions.allow` prefix pattern cannot scope. Two conditions, both fail closed:

- **Grammar + host allowlist**: no flags of any kind are permitted - a word starting with `-` where the target is expected is rejected outright, not classified. `user@` is mandatory, and the host must end in the `.lan` private-network suffix (e.g. `user@dns-01.lan`, `user@dns-01.dns.lan`), validated against a strict positive-charset regex (alphanumerics, `.`, `-`, `_`, `@` only) rather than a blocklist of dangerous characters - because several escaping/expansion mechanisms (backslash, ANSI-C quoting, brace/tilde/glob expansion) can make shfmt's raw source text differ from what bash actually executes, a positive allowlist closes that whole class in one step instead of one mechanism at a time. The target word and the single word immediately after it are the only ones content-inspected: real ssh doesn't stop parsing its own options at the destination, it keeps consuming immediately-following words as flags (`-o`, `-J`, `-F`, ...) until the first non-option word (a flag re-injected there is a live local-command-execution/host-redirection bypass, confirmed via `ssh -G`), so that one word is checked the same way the target is (leading `-`, or non-literal, both blocked). Everything beyond that word is genuinely the remote command and is not restricted at all - the boundary this hook enforces is "which host, as which user", not what runs once connected to an already-authorised host.
- **Key precondition**: a usable SSH key must be loaded in the forwarded ssh-agent (`ssh-add -l` exits 0 against `SSH_AUTH_SOCK`) before a genuinely valid `ssh user@host.lan` call is allowed - this container never mounts raw private key files (agent-socket forwarding only), so a call can never silently fall back to interactive password auth.

`scp` is not on `command-allowlist` or `permissions.allow` at all: there is no legitimate need for the agent's own Bash tool to transfer files directly (file movement in this repo's workflow goes through git), and scp's own `[user@]host:path`/`scp://` grammar is hard to parse safely. `reject-obfuscated-commands` blocks it outright before this hook would ever see it.

Uses the same shfmt-parsed AST approach as `enforce-git-policy`/`block-git-worktree`/`block-dotnet-tool-install` and fails closed the same way, plus a delimiter-collision-free (base64-per-word) transport between the `jq` AST walk and the bash validation logic - a tab/newline-joined transport can be desynced by a real tab or newline byte inside a legitimately quoted word, a complete, unauthenticated bypass. See the hook's own header for details. No safe auto-correct: neither condition has a rewrite the hook could inject on the agent's behalf - a wrong host or a missing key are facts about the world, not something a command edit can fix.

`gpg` is deliberately **not** on `command-allowlist`/`permissions.allow` at all: the agent's own Bash tool has no legitimate reason to invoke it directly - commit signing goes through git's own internal `gpg` invocation (`user.signingkey`/`commit.gpgsign`), and the only direct `gpg` calls in this repo are the `enforce-git-identity` hook's own subprocess check and `entrypoint.sh`'s container-startup validation, neither of which is gated by `permissions.allow` in the first place.

## enforce-curl-host

Runs after `enforce-ssh-host-and-key`, before `enforce-background-for-long-running-commands`. Restricts `curl` to a closed grammar, added because `claude-managed-settings.json`'s `Bash(curl *)` allow entry is blanket - the danger curl poses is in the *destination*, not the verb. A destination-only approach that keeps curl's flag grammar open (a denylist of specific dangerous flags, every non-flag word host-checked regardless of position) does not work: it admits bypasses (`-x<value>` glued short options, `env VAR=x curl ...`, a value-flag's own value hiding a denied host via brace expansion, quote-adjacent concatenation hiding the command name or a flag) and false positives (`curl -o github.com ...`, `curl -d '{"a":1}' ...`) from the same root cause: curl's grammar is too open for a position-blind, per-word scanner to check safely, since a word's role (flag, flag-value, or URL) depends on which flag precedes it. Closing the grammar - the same choice `enforce-ssh-host-and-key` made for ssh - removes the ambiguity instead of chasing it: this hook is a positive **allowlist** of exact flag spellings (`ALLOWED_NOARG_FLAGS`: `-fsSL`, `-sf`, `-f`, `-s`, `-S`, `-L`, `-v`, `--fail`/`--silent`/`--show-error`/`--location`; `ALLOWED_ARG_FLAGS`: `-o`/`--output`, `-w`/`--write-out`, `-m`/`--max-time` - `-fsSL`/`-sf`/`-f`/`-s`/`-S`/`-L` confirmed via a repo-wide grep of this repo's Dockerfiles, the rest confirmed by scanning this repo's own past interactive session transcripts for real curl invocations the allowlist would otherwise have blocked) plus exactly one literal `http://`/`https://` URL argument, whose host is checked against exactly the domains `claude-managed-settings.json` already denies to `WebFetch`: `api.github.com`, `github.com`, `registry.npmjs.org`, `raw.githubusercontent.com`, `api.nuget.org` (case-insensitive exact match, trailing FQDN dot stripped, subdomains not caught).

Every word must be a fully literal, statically-known string with no `$`-expansion/substitution anywhere (any non-literal word, `$URL` included, is blocked outright) - anything not on the allowlist, or any second URL-shaped word once one has already been found, is rejected outright rather than skipped or best-effort-classified. A word is also rejected if it contains a brace/tilde/glob/backslash character bash itself would act on given how that word is quoted - quote-aware (`word_risky` in the hook itself), not a blanket "these characters are never permitted" rule: an unquoted occurrence is always risky, a singly-quoted one never is, and a doubly-quoted one is only risky for the four escape pairs bash still honours inside `"..."` (`\$`, `` \` ``, `\"`, `\\` - not a bare backslash, which is meaningful only to curl's own `--write-out` format codes like `%{http_code}\n`, not to bash). This closes the same class of bypass as the fail-closed rule above: shfmt's static AST does not perform brace/tilde/glob expansion, so a literal, unquoted word like `https://api.github.com{,}` is exactly what this hook sees while real bash expands it into two argv words at runtime (confirmed live). The URL argument specifically is additionally rejected if it contains a bare `{`/`}`/`[`/`]` regardless of quoting, even a quoted one `word_risky` would otherwise allow: curl performs its own URL-globbing on those characters independent of shell quoting entirely (`man curl`, "URL GLOBBING"), so a quoted `'https://{safe.example,api.github.com}/x'` is just as glob-expanded by curl as an unquoted one (confirmed live) - `-g`/`--globoff` is not on the allowlist, so there is no way to opt back in to using either character legitimately. `literal_value`'s word-folding (concatenating a word's several literal/quoted AST Parts into one string, rather than requiring exactly one Part) still matters even under this fail-closed design: without it, a fully static quote-adjacent word like `https://example.com''` would be wrongly rejected as "non-literal" even though it has zero runtime unpredictability.

`wget` is not on `command-allowlist` or `permissions.allow` at all: it has zero real usage anywhere in this repo's own scripts/Dockerfiles/instructions, the same treatment as `scp` above. `reject-obfuscated-commands` blocks it outright before any hook would ever see it.

No Claude Code sandbox `network.allowedDomains` config is used alongside this hook: the sandbox does not work on this repo's Arch Linux development host, so the restriction lives entirely in this `PreToolUse` hook.

Uses the same shfmt-parsed AST approach and base64-per-word transport as `enforce-ssh-host-and-key`, for the same reasons documented in that hook's own header. Fails closed on missing `jq`/`shfmt` or an unparseable command. No safe auto-correct: a denied destination, an unrecognised flag, or a non-literal argument are each facts about what the command would do, not a syntax slip.

## enforce-background-for-long-running-commands

Runs after `enforce-ssh-host-and-key`, before `cache-gh-lookups`. Enforces the `credfeto-long-running-commands` rule that `git commit` (whose `pre-commit` hook run has no bounded duration), a directly-invoked `pre-commit`, this repo's own `pre-commit-check` wrapper (runs `pre-commit` against the existing checked-out repo, so it shares the same unbounded duration), `buildtest` (runs the full build and test suite, so its duration is unbounded too), `dotnet build`, `dotnet test`, `npm test`, and `bun test` must always be run with `run_in_background: true` on the Bash tool call. If `run_in_background` is `true`, allows immediately with no further check; a Bash call that omits the field entirely (the common case when a caller simply forgets it) is treated the same as an explicit `false` - it blocks. Otherwise parses the command with the same shfmt AST approach as `enforce-git-policy`/`block-git-worktree`/`block-dotnet-tool-install` and blocks if `git`/`.../git` in the command-name position (after skipping any `-c <k>=<v>`/`-C <dir>`/`--config-env <k>=<env>` pairs and any one-word `--config-env=<k>=<env>`, so the check holds on its own whichever other hooks are installed) is followed by subcommand `commit`, or `pre-commit`/`.../pre-commit`, `pre-commit-check`/`.../pre-commit-check` or `buildtest`/`.../buildtest` appears directly in the command-name position, or `dotnet`/`.../dotnet` is followed by `build` or `test`, or `npm`/`.../npm` or `bun`/`.../bun` is followed by `test`. A non-literal word (a substitution, expansion or other dynamic content) in the checked subcommand position is opaque to the AST walk and is represented internally as a sentinel marker; the git/dotnet/npm/bun checks all fail closed on that marker too, alongside their literal subcommand names, since it could resolve to `commit`/`build`/`test` at runtime and the word extraction cannot tell. Fails closed if `shfmt` is missing or the command doesn't parse. No safe auto-correct: the hook cannot inject `run_in_background: true` itself - that field lives in the tool call the hook is inspecting, not in the command string it could rewrite.

## cache-gh-lookups

Runs last in the chain. Unlike every other hook above, it never blocks - a parse failure, missing `shfmt`, or a non-matching command all just mean "no rewrite this time" and fall through to the normal permission check, never a denial; this is a convenience optimisation, not a security control. Matches only when the *entire* Bash command is a single bare call, with no pipes/redirects/backgrounding/negation/surrounding statements, to `gh api user --jq '.login'` (single/double/unquoted `.login`, `gh` or a path-qualified `.../gh`) - the exact command `lib/github`'s `resolve_gh_me` runs on the host side, which the agent's own Bash tool sometimes reaches for too. On a match, rewrites it (via `hookSpecificOutput.updatedInput`, merged into the original `tool_input` the same way `enforce-git-policy`'s auto-correct does) into a one-liner that creates `${XDG_CACHE_HOME:-$HOME/.cache}/orchestrator/global`, populates `global/user.json` via a real `gh api user` call only if it isn't already there, then `cat`s it - byte-identical to `containers/agent/entrypoint.sh`'s own `seed_orchestrator_cache`, which eagerly seeds the same file at container start (non-fatal on failure, matching `resolve_gh_me`), so the rewritten command's `gh api user` fallback is normally a no-op and exists only to self-heal a cache entrypoint.sh failed to seed.

This does not conflict with the rule against a blanket `gh api user*` `permissions.allow` entry for the agent's own Bash tool: the agent's literal call is never executed as written, so the underlying live API call happens at most once per fresh copy of the cache file, not once per agent attempt.

Adding another cached lookup later (the hook is named for this - `cache-gh-lookups`, plural): extend its own AST match to recognise the new call shape and give it its own cache filename under `global/` (or `local/`, for something that should not persist across container invocations) alongside `user.json`.

### Tracking allowlist requests

Every allowlist-block is logged in [credfeto/credfeto-orchestrator#1167](https://github.com/credfeto/credfeto-orchestrator/issues/1167) (labelled `Blocked`, `never-close`) for human review, unless a human in-session already approved and applied that specific addition (see above). Before logging a new request there, check the issue body and comments for the command name first - do not create duplicate entries.
