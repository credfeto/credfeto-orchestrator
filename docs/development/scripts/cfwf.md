# cfwf

A bash helper (Credfeto WorkFlow) that gives each recurring multi-step `gh` pattern one flat command.

Back to the [development guide](../README.md).

## Purpose

Agents used to re-derive the same multi-statement `gh` scripts every session. `cfwf` replaces them with single commands, so one `command-allowlist` entry and one `Bash(cfwf *)` permission cover them. The commands are listed under [Running it](#running-it), and each is described in [How it works](#how-it-works).

The board, the field that carries its workflow (the project's built-in `Status` field) and the option ids are all looked up from `--repo` and `--status`, so callers never handle project, field or option ids. The board itself is described in `docs/workflow-board.md`.

## Running it

```bash
cfwf workflow-status --set   --repo <owner/repo> (--pr <n> | --issue <n>) --status <name>
cfwf workflow-status --check --repo <owner/repo> (--pr <n> | --issue <n>)
cfwf closing-issue-labels    --repo <owner/repo> --pr <n>
cfwf issue create            --repo <owner/repo> --priority <priority> --title <title> --body-file <file|-> [--label <label> ...]
cfwf body check              --repo <owner/repo> --body-file <file|->
cfwf comment add             --repo <owner/repo> (--pr <n> | --issue <n>) --body-file <file|->
cfwf help [command]
```

Options, all validated before `gh` is called (test "--set rejects values that could alter a jq filter or a URL, without calling gh"):

- `--repo` must match `owner/repo` (`A-Za-z0-9_.-` on each side).
- `--pr` and `--issue` are digits only and mutually exclusive; one is required for both `--set` and `--check`. `assign_option` keeps the number without its leading zeros (`without_leading_zeros`; all zeros becomes `0`), for every command that takes them, because `gh` reads `0123` as `123` and answers with the URL of `123`. So the item URL `--set` adds to the board, the `n` field and the listing filter of `--check`, the `gh pr view` of `closing-issue-labels`, the `gh pr comment`/`gh issue comment` of `comment add` and every message name the number the same way (tests "--set builds the item URL from a number given with leading zeros as that number, without them", "--check reads a number given with leading zeros as that number, directly and from the listing", "closing-issue-labels reads a PR number given with leading zeros as that number, without them" and "comment add posts on a number given with leading zeros as that number, without them").
- `--status` is any text without control characters, and must be one of the ten workflow states (`WORKFLOW_STATES`): Not Started, Planning, Approved, Development, AI Simplify, AI Review, AI Security Review, AI Coverage, Human Review or Complete. It is matched without regard to case and never put into a filter. Any other name, including one the board has as an option (such as Todo), is `unknown --status` before the fields are read, so nothing is written (tests "--set refuses an option the board has that is not a workflow state, and writes nothing (#1519)" and "--set refuses a built-in option that is not a workflow state, such as Todo, before calling gh (#1519)"). `--set` needs it; `--check` rejects it (`--status is only valid with --set`).
- `--set` and `--check` are mutually exclusive. `-h`/`--help` prints the usage of the current command and exits 0 without calling `gh`.
- The old id options (`--owner`, `--project-number`, `--project-id`, `--field-id`, `--option-id`, `--url`) no longer exist and are rejected as unknown (test "the board ids and the URL are not options any more").
- `closing-issue-labels` accepts only `--repo` and `--pr` (`closing-issue-labels takes only --repo and --pr`).
- `issue create` has its own parser (`parse_issue_options`, which like `body check`'s `parse_body_options` is `parse_body_command_options` given its own list of flags), so `--priority`, `--title`, `--body-file` and `--label` are unknown options to the other commands, and `--pr`, `--issue`, `--status`, `--set` and `--check` are unknown options to `issue create`. `--repo` is always required and is never taken from the current directory.
- `--repo`, `--priority`, `--title` and `--body-file` may each be given once only. `--priority` is required, and one of `Security`, `Urgent`, `High`, `Medium` or `Low`, matched without regard to case and applied in its canonical spelling. `--label` may be repeated, may not contain a comma (`gh` splits on commas) or a control character, and may not be a priority label (the error says `use --priority <Priority>, not --label`). `--title` must not be blank and is at most 256 characters, and a `--label` must not be blank and is at most 50 (GitHub's limits), so a value it would refuse is caught before anything is created. Lengths are counted in characters, in a UTF-8 locale (`LC_ALL=C.UTF-8`), because bash counts bytes in the C locale a container usually has. A locale that is not installed is silently ignored, so `issue create` checks that `C.UTF-8` works (`require_utf8_locale`) just before it counts a title, a label or the body, and refuses to go on without it (`--help` and usage errors do not need it), and the image build fails if it is missing. The body's length is checked by the [body leak check](#body-leak-check) (`too long`). `--body-file` is a file, or `-` for stdin, and an empty or blank body is an error (exit 1). There is no `--status`: a new issue is always `Not Started`.
- `issue create`, `body check` and `comment add` compare each argument with their flags as a whole word (`is_one_of`), so one argument holding two flags and a space, such as `"--title --body-file"`, is `unknown option` (test "issue create refuses one argument that holds two of its flags as an unknown option").
- An argument cfwf does not know, whether a command, a subcommand or an option, is refused by `unknown_argument` (exit 2) as `unknown command`, `unknown <command> subcommand` or `unknown option`, followed by `(argument <n>; its value is not shown)`, where `<n>` is its position on the command line (`ARGUMENT_COUNT`, set in `main`). The argument itself is never printed: a stray value, such as the rest of an unquoted title the shell split into words, can hold a token, and the usage error comes before the leak check (test "a token-shaped stray argument is named by its position, never echoed, as a command, a subcommand or an option").
- `body check` accepts only `--repo` and `--body-file` (both required, each once, validated as for `issue create`) and `-h`/`--help`. There is no option to skip the check: `--force` or `--skip-leak-check` is an unknown option (test "body check help and usage errors, none of which call gh").
- `comment add` accepts only `--repo`, exactly one of `--pr` or `--issue` (digits only), `--body-file` and `-h`/`--help`, each option once (`--pr` or `--issue` a second time, or both, is `--pr or --issue can only be given once, and not both`). `--body`, `--edit-last`, `--json` and `--jq` are unknown options, so a comment is only ever taken from `--body-file` and only ever added, never edited (test "comment add usage errors exit 2 with the usage on stderr and never call gh").

Environment variables: `CFWF_PRIVATE_OWNERS`, a space-separated list of owner logins whose repositories are all private (empty by default), read by the [body leak check](#body-leak-check) once per run (`load_private_owners`, which the body, the title and each label share). A value that is not an owner login is a runtime failure, which does not echo the value. `gh` reads its own (for example `GH_TOKEN`), and `mktemp` honours `TMPDIR`. `CFWF_BIN_DIR` belongs to `install-claude-hooks`, not to `cfwf`.

Output and exit codes:

- `--set` prints `Set <url> to <status>` (the canonical option name, so `ai security review` prints `AI Security Review`) and exits 0. The URL is `https://github.com/<repo>/pull/<n>` or `.../issues/<n>`.
- `--check` prints one line, the state name alone, for example `Development` (test "--check prints only the status name, with no parenthetical (#1519)"). It prints `(unset)` when the item has no workflow state. It exits 1 with `<repo>#<n> is not on project <number>` when the item is not on the board.
- `closing-issue-labels` prints the sorted, de-duplicated labels, one per line, leaving out exactly `Blocked` and `On-Hold` (`Blocked-by-upstream` is kept).
- `issue create` prints the issue URL and nothing else on stdout when it succeeds. If the issue was created but a later step failed, stderr ends with `the issue was already created: <url>`, so the issue is never lost; a failure before the issue exists never says that.
- `body check` prints nothing and exits 0 when the body passes.
- `comment add` prints the comment URL and nothing else on stdout when it succeeds.
- Exit 0 is success and help; 1 is a runtime failure (`die`, prefixed `cfwf:`), including a repository visibility lookup or a leak-check scan that fails; 2 is a usage error, printed with the usage text on stderr; an error about an option's value names the option and the rule it broke (`invalid value for --title: it must not contain a control character`, `unknown --priority`, and the runtime failure `unknown --status`) and never the value, and an unknown argument is named only by its position, because a free-text value such as a title can hold a token and these checks run before the leak check (test "a usage error names the option and the rule but never echoes the value, which could hold a token"); 8 is a body refused by the leak check (`BODY_REFUSED_EXIT`), from `issue create`, `body check` or `comment add`, or by `comment add`'s `approval keyword` rule, with `cfwf: body refused: <rule>` and `(line <n>)` where there is one on stderr. A bare `cfwf` prints the usage to stderr and exits 2.

## How it works

`workflow-status --set` (`workflow_status_set`):

1. `require` and `require_target` check the options (`--pr` becomes type `PullRequest`, URL kind `pull`; `--issue` becomes `Issue`, `issues`), and `require_gh` checks `gh` is installed.
2. `resolve_project` runs `gh repo view <repo> --json projectsV2` and keeps the one open project titled `Workflow` (a closed one is ignored; none or two is a `die`). The owner is taken from the project's own `resourcePath` (`/users/...` or `/orgs/...`), not assumed to be the repository owner.
3. `resolve_status` first checks `--status` with `canonical_workflow_state` and rewrites `STATUS` to its canonical spelling; an unknown name dies listing the ten states. It then runs `gh project field-list <n> --owner <owner> -L 100` and looks for an option with that name on the `Status` field and on a `Workflow Status` field. It uses the `Workflow Status` field whenever the board still has one, whatever `Status` holds, so `--set`, `--check` and the conversion agree on which value is the real one even on a board whose conversion stopped part way; on a converted board it uses `Status`. It dies naming the field it chose when that field has no such option. A field named `Status` that has no options is ignored. It sets `FIELD_ID`, `FIELD_NAME` and `OPTION_ID`.
4. `gh project item-add ... --format json --jq .id` adds the item (the help text says adding is idempotent), and the id is checked against `^[A-Za-z0-9_=-]+$` before use.
5. One `gh project item-edit` sets the chosen field; a failure dies naming that field (`could not set the <field> of <url>`). There is no read-back and no other `gh` call after that: the script prints `Set <url> to <status>`.

`workflow-status --check` (`workflow_status_check`) calls `resolve_project` and then `read_target_status`:

1. `graphql_query` runs `gh api graphql` with a read-only query for the one issue (`issue(number:)`) or pull request (`pullRequest(number:)`), asking for `projectItems(first:100)` with `legacy:fieldValueByName(name:"Workflow Status")` and `status:fieldValueByName(name:"Status")` in the one query. The `--jq` filter keeps only the item whose `project.id` is the Workflow project's, then picks the value: the Workflow Status value when the board still has that field, otherwise the Status value when it is one of the ten states, otherwise `(unset)`. So on a board not yet converted a built-in Todo, In Progress or Done reads as `(unset)`. stdout goes to `GRAPHQL_OUTPUT` and stderr to a temp file read into `GRAPHQL_ERROR`, so gh's stderr chatter can never end up in a value.
2. If GitHub answers `Could not resolve to an Issue with the number` (or `... a PullRequest ...`) that means not found, not failure.
3. Any other failure calls `fall_back_to_listing`: a warning on stderr (`graphql_failure_text` quotes the first line only, printable characters only, at most 200 characters) and then `gh project item-list <n> --owner <owner> --format json -L 10000` (`ITEM_LIMIT`), filtered by repository (case-insensitive), number and type, with the same choice between the two values.
4. If both fail, `cfwf` dies with `both the direct query and the listing of project <n> failed`.

`closing-issue-labels` (`cmd_closing_issue_labels`) reads `gh pr view --json closingIssuesReferences`, then `gh issue view <n> --repo <that issue's own repo> --json labels` for each (a PR can close an issue in another repository), filters out `Blocked` and `On-Hold`, and runs `sort -u`. An unreadable issue or a malformed reference produces a warning, still prints the other labels, and makes the exit status 1, so a partial list is never mistaken for a complete one.

`comment add` (`comment_add`), in this order, so a bad call posts nothing:

1. `parse_body_command_options "--repo --pr --issue --body-file"`, `require REPO`, `require_target` and `require BODY_FILE` (exit 2), then `require_gh`.
2. `resolve_body`, as for `issue create`: the private copy, refused with exit 1 when it cannot be read or is blank, then `check_body_for_leaks` on that copy for `--repo` (exit 8). A missing, unreadable or blank body is a runtime failure (exit 1), as it is for `issue create` and `body check`, not a usage error (test "comment add refuses a missing, unreadable, empty or blank body as a runtime failure, without calling gh").
3. `check_comment_for_approval_keywords`: a copy of the body with every Markdown quote line (optional whitespace, then `>`) blanked, so line numbers are kept, is scanned with `refuse_first_match ... -iw` for `APPROVAL_KEYWORD_PATTERN`, the two plan-approval keywords. `-w` in the C locale treats letters, digits and `_` as word characters, so a longer word that holds the letters passes, while one after or before punctuation (`(word)`, `word,`) is refused. A refusal is `cfwf: body refused: approval keyword (line <n>)`, exit 8. The rule exists because a comment an agent posts under a trusted human's account would otherwise read as that human approving a plan; quoting the human's own words on a `>` line is how the plan-approval rules say to mirror a real approval, so it passes (tests "comment add refuses a plan-approval keyword outside a quote with exit 8, in any case, naming only the line" and "comment add posts a plan-approval keyword inside a Markdown quote, and a longer word holding the letters"). The rule runs after the leak check, and `body check` does not apply it (test "body check does not apply the plan-approval keyword rule"), so a body that passes `body check` can still be refused here. A quote inside a list item (`- > ...`) is not a quote line and is refused.
4. `gh pr comment <n>` (for `--pr`) or `gh issue comment <n>` (for `--issue`), where `<n>` is the number without its leading zeros (see [Running it](#running-it)), with `--repo` and `--body-file <copy>`, stdin from `/dev/null` so `gh` can never wait on it. A failure dies with `could not post the comment on <repo>#<n>`.
5. The last line of `gh`'s output must look like `https://<host>/<owner>/<repo>/(pull|issues)/<n>#issuecomment-<digits>`, where `<n>` is that same number, otherwise it dies saying the comment may have been posted, without echoing the answer. As for `issue create`, the host, owner and repository are not compared (a proxy answers with its own host, a renamed repository with its new name), and `pull` and `issues` are both accepted whichever option was given, because GitHub answers a comment made on a pull request through its issue number with the pull request URL (tests "comment add accepts a comment URL from another host, and a pull URL for an issue number" and "comment add exits 1, printing nothing on stdout, when the result is not the comment URL of the target"). The URL is then printed.

`issue create` (`issue_create`), in this order, so a bad call leaves no issue behind:

1. `parse_issue_options` and the required-option checks (exit 2), then `collect_issue_labels`: the priority label first, then each `--label`, with a standard label written in its standard spelling and a repeat in any case dropped, and any priority among them refused.
2. `require_gh`, then `resolve_body`: a file must be a readable regular file, or `-` for stdin; one that is not dies with `cannot read the --body-file`, which never names the path, because it is usually a host path (a temporary or runtime directory) that the leak check would refuse to post (tests "issue create refuses a missing, unreadable, empty or blank body, without calling gh" and "body check refuses a missing or blank body as a runtime failure, without calling gh"); either is copied to a private temporary file (`BODY_PATH_TMP`), which must contain a non-blank character. `resolve_body` then runs `check_body_for_leaks` on that copy, the one `gh` is given, so a body file rewritten after the check, by a writer that has not finished or between the check and the post, is never posted unchecked (test "issue create hands gh the private copy it checked, so a body file rewritten after the check is never posted") (see [Body leak check](#body-leak-check)), so a refused body exits 8 before the board is read or anything is written (test "issue create refuses a body naming a private repository before any board read or write"). `check_value_for_leaks` then checks the `--title` and each `--label` as given, the same way (tests "issue create refuses a title or a label with a token or a host path, naming only the rule, before calling gh" and "issue create refuses a title or a label naming a private repository on a public target, before any write").
3. `resolve_project` and `resolve_status "Not Started"`, the same reads as `--set`, so a repository with no Workflow board, or a board with no `Not Started` option, fails here.
4. `ensure_labels_exist` lists the repository's labels once (`gh label list --limit 1000`, matched without regard to case) and runs `gh label create` for each missing one: with `--color` and `--description` from `STANDARD_LABELS` for a standard label, and with neither for any other, so `gh` picks the colour. The name comes after `--`, so a name that starts with a dash is not read as a flag. An `already exists` answer is not an error (the label appeared after the listing); any other failure dies before the issue exists.
5. `gh issue create --repo ... --title ... --body-file <path> --label ...` for every label. The last line of its output must look like `https://<host>/<owner>/<repo>/issues/<n>`, otherwise it dies saying the issue may have been created and naming what `gh` answered with. Neither the host nor the owner and repository are compared with anything: `gh` may be reached through a proxy that answers with its own host, and a renamed or transferred repository answers with its new name.
6. `CREATED_URL` is set, which makes the `EXIT` trap report the URL if the run then fails. `put_item_on_board` (the code `--set` uses) adds the item and sets it to `Not Started` on the field `resolve_status` chose (the Workflow Status field on a board not yet converted, test "issue create sets Not Started on the Workflow Status field of a board not converted yet (#1519)"), and the URL is printed.

### Body leak check

`check_body_for_leaks <body-path> <owner/repo>` is the one check every command that posts a body runs before `gh` is called. `resolve_body` runs it as its last step, so resolving a body always checks it; today that is `issue create`, `comment add` and `body check` (`body_check`), which stops there, so an agent can test a body first. It runs on the exact file `gh` is given: the private temporary copy `resolve_body` makes of the body file or of stdin. The rules apply in this order and the first that matches wins (test "the first rule that matches wins, in the order token, host path, control character, invalid UTF-8, too long"):

1. `token` (`TOKEN_PATTERN`): `ghp_`, `gho_`, `ghs_`, `ghu_`, `ghr_` (GitHub's personal, OAuth, server, user-to-server and refresh tokens), `glpat-`, `sk-ant-` (an Anthropic key), `sk-proj-` (an OpenAI project key), or `xoxa-`, `xoxb-`, `xoxp-`, `xoxr-` or `xoxs-` (Slack; the same forms `notify-unit-failure` redacts) at a word start followed by a token character, `github_pat_` followed by one, `AKIA` and 16 upper-case letters or digits, a `-----BEGIN ... PRIVATE KEY-----` line, a Discord webhook URL (`DISCORD_WEBHOOK_PATTERN`: `discord.com` or `discordapp.com`, then `/api/webhooks/`, a numeric id, `/` and a token character, since the URL itself is the credential), a bearer token (`BEARER_PATTERN`), or a secret assignment (`SECRET_ASSIGNMENT_PATTERN`). A prefix on its own (`ghp_` or `sk-ant-` with nothing after) passes. A bearer token is an `Authorization` header (in any of the spellings `Authorization`, `authorization` or `AUTHORIZATION`, followed by `:` or `=`, optionally quoted as in JSON) whose `Bearer` value starts with a token character, or `Bearer` anywhere followed by 20 or more token characters with at least one digit among them (`bearer_value_pattern`, which builds that as an alternation on where the first digit is, because ERE has no lookahead); so `Authorization: Bearer <token>`, `Authorization: Bearer $GH_TOKEN`, a `${{ ... }}` reference and prose such as "a Bearer token" or "Bearer authentication-mechanism-description" pass, since words joined by hyphens hold no digit, while a real token, which almost always holds one, is refused wherever its first digit is; as does a webhook URL with `<id>` or `<token>` placeholders (test "body check passes a token prefix, a Bearer placeholder or a webhook placeholder with no secret after it"). A secret assignment is `NAME=value` where `NAME` is upper case and is `TOKEN`, `SECRET`, `KEY` or `PASSWORD`, or ends in one of them after an underscore (`GH_TOKEN`, `DB_PASSWORD`), so a name that merely ends in the letters, such as `MONKEY=banana`, passes; and where the value is not empty and, after an optional opening quote, does not start with `$`, so a variable or secret reference (`${GH_TOKEN}`, `${{ secrets.GITHUB_TOKEN }}`, `$API_KEY`, `"${GH_TOKEN}"`) passes (tests "issue create refuses a body with any token form with exit 8, naming the rule and line only, before calling gh" and "body check passes a NAME=value whose name only ends in the letters, or whose value is a reference"). Lower-case names (`api_key=...`) and the `NAME: value` and `NAME = value` forms are not checked: they are common in ordinary prose and configuration examples, and matching them would refuse far more harmless text than it would catch.
2. `host path` (`HOST_PATH_PATTERN`): `/home/`, `/Users/` (a macOS home), `/root/`, `/run/user/` (which holds the Claude scratchpad) or `/tmp/` at the start of a path: the start of a line, or after any byte but a letter, a digit, `.`, `~` or `-`. The boundary is a negative one so that whatever can come before a path in prose, markdown or a URL starts one: whitespace, quotes, a backtick, brackets, `=`, `:` (`PATH=/usr/bin:/home/...`), `,`, `*` and `_` (markdown emphasis), `<`, `|`, and `/` (so `file:///home/...` is caught by its third slash). A byte that can continue a word or a relative path does not, so `./tmp/x`, `../home/x`, `example.com/home/x` and the relative `tmp/x` pass. Nor does a boundary byte other than `/` that itself follows a `/`: it is a segment of a URL path, so `https://example.com/_/home/x` passes, while a slash always starts one (`///home/x`, `//home/x` after a word) and the same byte at a line start or after anything else still does (`_/home/x_`, `a,/run/user/...`; tests "body check passes a body with no leaks, printing nothing and calling gh for nothing" and "body check still refuses a host path after punctuation that does not follow a slash, at a line start, or after a run of slashes"). A home, root's home, a user runtime directory or tmp deeper inside an absolute path is a host path too, the same directories as at the start of a path (`/mnt/c/Users/...` under WSL, `/var/home/...` on Fedora Atomic, `/var/root/...` and `/private/tmp/...` on macOS, and `/var/tmp/...`), because each still names a user or a host temporary file. For that shape the path must not follow a `/` (unless as `file://`), so the path of a URL, whose host follows `//`, passes: `https://example.com/home/x` and `http://h/tmp/x` are not host paths. The third shape is a Windows drive path under `Users` (`C:\Users\...`, `C:/Users/...` or an escaped `C:\\Users\\...`, in any case), after a byte that is not a letter or digit (test "body check refuses a home, a user runtime directory or tmp deeper inside an absolute path, and a Windows drive path under Users"). `~/` is not a host path: a home-relative path names no user and is common in documentation, and the rule lists absolute paths only; `~/tmp/x` passes for the same reason. Upper-case `/Users/` is matched exactly, so the API path `/users/` passes.
3. `control character` (`CONTROL_PATTERN`): a C0 control other than tab and newline (carriage return included, so a body with CRLF line endings is refused at its first line), DEL, or a C1 control (U+0080 to U+009F, which UTF-8 writes as the byte 0xC2 followed by 0x80 to 0x9F). Nothing else is refused: other invisible or formatting characters, such as the bidi overrides, pass (test "body check passes a body with no leaks, printing nothing and calling gh for nothing" includes U+202E). The scan is byte by byte in the C locale, which finds exactly these in UTF-8 text because every byte of a multi-byte character is 0x80 or above, and 0xC2 only ever starts a character; NUL is mapped to 0x01 with `tr` first, since no pattern can hold a NUL; `write_nul_free_copy` writes that copy to a temporary file (`SCAN_TMP`, removed by the `EXIT` trap) rather than piping it, so a failed copy stops the check.
4. `invalid UTF-8` (`UTF8_LINE_PATTERN`): a line that is not valid UTF-8 as a whole, matched with `grep -xv` (`refuse_first_match` takes extra `grep` options for this) against the RFC 3629 table of ASCII (but NUL) and two, three and four byte sequences, with no overlong form, no surrogate and nothing above U+10FFFF, byte by byte in the C locale on the NUL-free copy, so it gives the same answer under any `grep` locale. It refuses a raw byte from another encoding, such as a lone 0x85 from Latin-1 or CP1252 text (the C1 scan above sees a C1 control only in its UTF-8 form), and a broken sequence. It runs before `too long` because `wc -m` does not count a byte that is not valid UTF-8, so such a body could pass the length check and be turned away by GitHub after labels were created (test "a body, a title or a label that is not valid UTF-8 is refused with exit 8, naming only the line, before calling gh"). Like the rules before it, it applies to a title and a label too.
5. `too long`: more than `BODY_LIMIT` (65536) characters, counted with `wc -m` in `C.UTF-8` after `require_utf8_locale`. A count that fails, or that is not a number, dies with `cfwf: could not count the characters of the body` (exit 1) rather than being reported as `too long` (test "a character count that fails or is not a number is a runtime failure (exit 1), never too long or a pass").
6. `private repository` (`check_repository_references`), only when the target repository is public. `repository_references` collects, with line numbers and with any trailing full stops, then `.git`, then `.wiki` (in any case, so a link to a wiki or its clone URL names the repository it belongs to; test "a link to the target's own wiki passes with no lookup, and another repository's wiki is looked up as that repository") dropped by `print_reference` (which skips a link left with no repository name, such as `github.com/<owner>/...`), links (`REPOSITORY_LINK_PREFIX`): `github.com/<owner>/<repo>` (with or without `www.`), `api.github.com/repos/<owner>/<repo>`, `raw.githubusercontent.com/<owner>/<repo>` and `codeload.github.com/<owner>/<repo>` (archive downloads), and `git@github.com:<owner>/<repo>` SSH remotes, with the owner taken as the segment after the last `/` or `:` before the repository. A link must not follow a letter, digit, `.` or `-`, so a host that only ends in the same letters (`notgithub.com`) and GitHub's other hosts (`docs.github.com`, and `gist.github.com`, whose paths are gists, not repositories) are not links; dots after such a boundary, or two dots anywhere (an ellipsis, as in `see...github.com/<owner>/<repo>`), are punctuation and do not stop a link (test "a gist, another GitHub host or a host that only ends in github.com is not a repository link, and passes with no lookup"). It also collects standalone `<owner>/<repo>#<n>` cross-references and `<owner>/<repo>@<sha>` commit autolinks (`<sha>` 7 to 40 hex digits; test "a public target refuses a codeload link or an owner/repo@sha autolink to a private repository"), and bare `<owner>/<repo>` words whose owner is in `CFWF_PRIVATE_OWNERS`. A bare `owner/repo` of any other owner is never looked at, because a relative path such as `test/cfwf.bats` has the same shape. A bare word preceded by a letter, digit, `_`, `.`, `/` or `-` (`REFERENCE_BOUNDARY`) is part of a longer path or host name and is skipped, except that underscores which open Markdown emphasis are passed over when the byte before them is a boundary, so `_<owner>/<repo>#5_` and `__<owner>/<repo>__` are read as the reference inside them (`*`, as in `*<owner>/<repo>#5*`, is a boundary byte itself), while `my_<owner>/<repo>#5` is not a reference (test "a reference in Markdown emphasis is still checked, and an underscore inside a word is not a boundary"). A cross-reference must also be standalone: `is_cross_reference` refuses one whose preceding byte is in `URL_PATH_BYTES` (`~`, `@`, `#`, `%`, `?`, `&`, `=` or `+`), which put it inside a URL, a query or another path, or when it is a `:` and the "owner" after it is all digits (a port, as in `localhost:8080/api#1`), while a reference straight after any other colon is still one (`Related:<owner>/<repo>#5`, as with `Fixes: <owner>/<repo>#5`; the `://` of a URL leaves a slash, not a colon, before its path), and a bare word of a listed private owner after one of those bytes (`REPO=<owner>/<repo>`) is still checked. A `#<n>` or `@<sha>` is a reference only when no letter, digit, `_` or `-` follows the digits, other than the underscores that close Markdown emphasis at the end of the word (`<owner>/<repo>#5_` is one, `<owner>/<repo>#5_x` is not) (so `owner/action@v4` and a 41-digit `@` value are not; test "an @ that is not followed by a commit SHA alone, or a host that only ends in codeload.github.com, passes with no lookup"), so a heading anchor such as `docs/setup.md#1-prerequisites`, a branch such as `fix/foo#12abc`, and `owner/repo#1` inside a query string are not looked up (test "a #n inside a longer word, or an owner/repo#n inside a path or a URL, is not a cross-reference, and passes with no lookup"). `grep` cannot look ahead, so the scan takes in every word character and `-` after a `#` or `@` and `repository_references` keeps only a `#` followed by digits alone or an `@` followed by a SHA alone; none of those characters can start the next reference, so references side by side are each still found (test "standalone cross-references side by side are each checked, so a private one after a public one is refused"). A `#<n>` on a word that looks like a file and ends there, such as `src/app.ts#12`, is still a cross-reference and is looked up. They are checked in line order. A reference to the target itself (compared without regard to case) passes, and so does a link whose first segment is one of GitHub's own pages (`GITHUB_RESERVED_PATHS`, for example `orgs`, `settings`, `advisories`, `stars`, `copilot` or `team`; test "links to GitHub's other pages, such as starred lists, Copilot and the team plan, pass with no lookup"). That list includes `user-attachments`, where GitHub stores every pasted image or file (`github.com/user-attachments/assets/<id>` and `.../files/<id>/<name>`), so a pasted screenshot passes on a public target; `assets` is not listed, because it is a real account, and an attachment under `<owner>/<repo>/assets/` is that repository's link like any other. GitHub's image hosts (`user-images.githubusercontent.com`, `private-user-images.githubusercontent.com`) are not repository links at all (test "a pasted image or file, or one on GitHub's image hosts, passes on a public target with no lookup"). The target's visibility is looked up only when the text names some other repository, so text that names none costs no `gh` call, and a `--repo` GitHub does not show the caller (a typo, a renamed repository, no access) is only a runtime failure once the text names another repository: text that names no other repository passes with no lookup of the target at all (test "a target repository GitHub does not show the caller is never looked up when the text names no other repository"). `cfwf help body` says the same. An owner in `CFWF_PRIVATE_OWNERS` is refused with no lookup. Any other repository is looked up with `gh repo view <repo> --json visibility` by `repository_is_public`, once per repository per run (`REPOSITORY_VISIBILITY`, keyed in lower case). `PUBLIC` passes; `PRIVATE` and `INTERNAL` are private; a lookup that fails with `Could not resolve to a Repository` or `HTTP 404` means the caller cannot see it, which counts as private for a repository the text names; any other failure, or an answer that is none of those, dies (exit 1). That includes `HTTP 403` (access denied, for example by an organisation that enforces SAML SSO, or by a proxy): it fails closed as a runtime failure, so nothing is posted, rather than counting as private (test "a visibility lookup that fails is a runtime failure (exit 1), never a pass or a refusal"). `look_up_visibility` records each answer (`public`, `private` or `missing`); `repository_is_public` reads it for a named repository and `target_is_public` for the target, where `missing` dies with `cfwf: the repository <owner/repo> was not found, or the caller cannot see it` (exit 1), because counting an unresolvable target (a typo, a renamed repository, no access) as private would skip every private repository check and pass the text (test "a target repository GitHub does not show the caller is a runtime failure (exit 1), never a pass").

Every scan fails closed. `refuse_first_match` hands `grep` the file path (not a redirection, which would turn an unreadable file into "no match") and `repository_references` takes each `grep`'s output whole and checks its status rather than reading it through a process substitution, so a `grep` that fails (status 2) dies with `cfwf: could not scan the body` (exit 1) and never counts as a pass (test "a grep that fails while scanning the body is a runtime failure (exit 1), never a pass").

`check_value_for_leaks <value> <owner/repo> <title|label>` applies the same rules to a `--title` or a `--label` (`check_text_patterns` for token, host path, control character and invalid UTF-8, then `check_repository_references`), all but `too long`, since `validate_visible_text` has already limited its length. It writes the value to a temporary file (`VALUE_TMP`, removed by the `EXIT` trap), because the rules read a file and the reference scan reads it twice. A visibility lookup that fails for a repository a title or label names says `named in the title` or `named in the label` rather than a line.

`refuse_text` prints `cfwf: <subject> refused: <rule>`, where the subject is `body`, `title` or `label`. A body's refusal ends with `(line <n>)`, except for `too long` (every other rule has a line); a title or label is one line and has none. It exits 8. It never prints the matched text or the repository it named, because echoing a token into a transcript is itself the leak. A failed lookup of a referenced repository names only its line for the same reason.

External tools: `bash` 4+ (associative arrays and `${var,,}`; it is not POSIX sh), `gh` (authenticated), `mktemp`, `grep`, `sort`, `tr` and `wc`. The script runs `main` only when executed (`BASH_SOURCE[0] = $0`), so `test/status-mapping-parity.bats` can `source` it to reach `WORKFLOW_STATES`.

Shipping: the Dockerfile copies it to `/usr/local/bin/cfwf` (root:root, 0755) and checks presence and the executable bit. It is on `claude-hooks/command-allowlist` and `Bash(cfwf *)` is in `claude-settings.json`, kept in step by `test/command-allowlist-parity.bats`. On a host, `install-claude-hooks` runs `install_cfwf`: `install -m 0755` into `${CFWF_BIN_DIR:-/usr/local/bin}`, retried under `sudo` as root:root if that fails, and otherwise it prints the exact command to run. It is a copy, not a symlink, so re-run the installer after changing `cfwf`. The installer refuses to run inside a Claude Code session. Tests: `test/install-claude-hooks.bats` ("main installs cfwf into the shared bin directory, executable by everyone", "re-running main replaces an older installed cfwf", the sudo tests and "dies when the source cfwf script is missing").

### Why it is built this way

GitHub's project API lags behind writes, and `gh project` has no command that reads a single item. Those facts drive every design decision (issue #1491; the `--set` and `--check` help text and the comments in the script say the same):

- No read-back after `--set`. A read straight after a write cannot tell a lost write from lag: `gh project item-list` can leave out a newly added item for minutes, and a change to an existing item can take seconds to show even on a direct read. An earlier version read the value back and reported a false "did not persist" for writes that had persisted. Now `--set` trusts `gh project item-edit`'s exit status and prints `Set <url> to <status>`. This is the shared rule ([GitHub State Lags Behind Writes](../../../ai/global/github-cli.instructions.md#github-state-lags-behind-writes-mandatory)): a write whose call succeeded is done, so it is not re-read to confirm and not polled.
- `--check` reads one item directly. `gh project item-list` is a listing of the whole board: it is paged, capped (`-L`), can be slow, and is slow to show a new item. A single-item GraphQL query avoids the paging and the cap. This is the only `gh api graphql` use in `cfwf` and the query contains no mutation (test "no gh api graphql call ever carries a mutation"); every write is a native `gh project` command.
- A fallback to listing exists, with a visible warning, so a GraphQL failure does not make `--check` useless. The listing asks for 10000 items (`ITEM_LIMIT`) rather than accept a default page; the field listing asks for 100 (`FIELD_LIMIT`, test "--set reads the project's fields with a limit above the default page size of 30").
- The list of workflow states is duplicated. `cfwf` is copied alone into the image and cannot source `lib/`, so `WORKFLOW_STATES` is a copy of the states in `lib/project-status`. `test/status-mapping-parity.bats` is the only thing stopping them drifting apart.
- Both fields are read and written while boards are converted one repository at a time. A converted board has only `Status`; a board not yet converted keeps its workflow in `Workflow Status`, and its `Status` holds Todo, In Progress or Done, which are not workflow states. Preferring `Status` when it has the state, and the Workflow Status value when that field exists, means `cfwf` gives the right answer on either kind of board without knowing which it is.
- The standard labels are hard-coded too. `cfwf` is installed standalone and cannot read `.github/labels.yml`, so `STANDARD_LABELS` is a copy of every label in that file (`name|colour|description` per line), used to give a label that `issue create` has to create its standard colour and description. `test/standard-labels-parity.bats` compares the copy with the file in both directions, so adding, removing or editing a label in `.github/labels.yml` fails that test until `STANDARD_LABELS` is updated to match.
- `issue create` validates and resolves everything before it writes anything. The board is resolved before the labels or the issue, because a half-done create (labels made, no issue; or an issue with no board item) is what the command exists to prevent. The one write that can still fail afterwards is the board write, and the `EXIT` trap in `cleanup` then names the issue URL on any non-zero exit after the issue was created.
- The body, from a file or from stdin, goes to a private temporary file and `gh` is handed that copy, never the path or `-` it came from: the body has to be checked before anything is created, stdin can only be read once, and a file could be rewritten between the check and the post, which several network calls separate. One `cleanup` function, installed as the `EXIT` trap in `main`, removes every temporary file and prints the created-issue notice. Each temporary file is made on first use by `ensure_temp_file <variable>`, which stores the path in the named global, at most once per run: `GH_ERR_FILE` (the one file `gh`'s stderr is captured in, shared by the GraphQL query and the visibility lookup), `BODY_PATH_TMP` (the body copy), `SCAN_TMP` and `VALUE_TMP` (see [Body leak check](#body-leak-check)).
- Labels are created rather than left to fail. `gh issue create --label` refuses a label the repository does not have, so `ensure_labels_exist` creates it first. It never edits or deletes an existing label. A repository with more labels than `LABEL_LIMIT` (1000) would look as if it lacked one, which is why an `already exists` answer to a create is tolerated.
- The body leak check has no bypass option. A bypass flag would be used whenever the check got in the way, which is exactly when it matters; a body that has to discuss a path shape should use a placeholder instead (`<repo>/...` rather than a real `/home/...` path). Its refusal has its own exit code (8) so a caller can tell "fix the body" apart from a runtime failure (1) or a bad call (2).
- `issue create` never rewrites an existing item's status: it always sets `Not Started`, because a new issue can only be at the start, so it has no `--status`. `docs/workflow-board.md` describes the board.

## Tests

`test/cfwf.bats` covers help and usage, `--set`, `--check`, `closing-issue-labels`, `issue create`, `comment add` and the body leak check (`body check`, and `issue create` refusing a leaking body before any write). `test/standard-labels-parity.bats` sources `cfwf` in a subshell and compares `STANDARD_LABELS` with `.github/labels.yml` (parsed with `awk`; the file is a flat list of name/colour/description triples), and checks that all five priorities are standard labels. `test/status-mapping-parity.bats` sources `cfwf` in a subshell and checks that `WORKFLOW_STATES`, `project_status_names` (lib/project-status) and `_WF_STATUS_ORDER` list the same ten states in the same order (tests "there are ten workflow states", "cfwf lists the same workflow states as lib/project-status, in the same order (#1519)" and "_WF_STATUS_ORDER lists the same workflow states as lib/project-status, in the same order (#1519)").

How `gh` is faked: `setup` builds a `gh` PATH stub with `make_stub_multiline gh`. The stub logs every call's arguments to `GH_LOG`, then routes on the first two words (`repo view`, `project field-list`, `project item-add`, `project item-edit`, `project item-list`, `api graphql`, `pr view`, `issue view`, `label list`, `label create`, `issue create`, `pr comment`, `issue comment`). For every call except `project item-edit` and `label create` (which only succeed or fail), `issue create` (which prints the contents of `issue-create.out`) and the two comment calls (which print `comment.out`) it applies the call's own `--jq` filter to a fixture file in `GH_FIXTURES` (`issue-view-<n>.json` for `issue view`), using the real `jq`, so the filters `cfwf` sends are run against real-shaped JSON and not merely recorded. Any other call exits 99 with `gh stub: unexpected call`.

- Failure switches are marker files in `GH_FIXTURES`: `repo-view.fail`, `item-add.fail`, `item-edit.fail`, `item-edit.failfield` (fails only the edit for the field id it contains), `item-list.fail`, `graphql.fail` (stderr text and exit 1), `graphql.failout` (stdout text and exit 1) and `graphql.stderr` (stderr noise on success), `label-list.fail`, `label-list.rewrite` (its content is a path, which the label listing overwrites, so a test can rewrite the body file after the check), `label-create.fail` (its content is the stderr text) and `issue-create.fail`. `issue create` also copies the file it is given with `--body-file` to `issue-body.txt`, so a test can check the body gh received.
- `repo view ... --json visibility` is routed on its own: it applies the filter to `visibility-<owner>_<repo>.json` (lower-cased, the path given by `visibility_fixture` and written by `write_visibility`), fails with an `HTTP 502` text when `visibility-<owner>_<repo>.fail` exists (`fail_visibility`), and with no fixture at all answers `Could not resolve to a Repository`, as GitHub does for a repository the caller cannot see.
- Fixture helpers for the leak check: `write_leak_body` (the leak on line 3), `run_body_check`, `run_issue_create_leak` (`issue create` on that body), `assert_refused` (given the run's status, stdout and stderr as arguments, so the helper never reads bats' run globals: exit 8, the rule and line 3 on stderr, nothing on stdout, the matched text absent), `visibility_lookups` and `leak_tokens`, which builds every token form from pieces so that no secret scanner flags the test file.
- `pr comment` and `issue comment` share a route: the stub copies the `--body-file` it is given to `comment-body.txt`, writes where its stdin points (`readlink /proc/self/fd/0`, which never reads stdin and so can never block on it) to `comment-stdin.txt`, which is `/dev/null` when `cfwf` closes it, fails when `comment.fail` exists and otherwise prints `comment.out`. `prepare_comment [url]` writes a body to `comment.md` and the URL (the PR comment URL by default; an empty argument writes an empty answer) to `comment.out`; `run_comment_add` runs `comment add --repo <repo>` with the given arguments.
- Fixture helpers for `issue create`: `prepare_issue_create` (a body file, the repository's existing labels in `label-list.json`, and the URL in `issue-create.out`; the board comes from `setup`), `create_args` and `assert_nothing_created`.
- Fixture helpers: `workflow_states` (the ten states, one per line), `write_repo_view`, `write_field_list` (a converted board: `Status` carries the ten states, written by `setup`), `write_legacy_field_list` (a board not yet converted: `Status` has Todo, In Progress and Done, and a `Workflow Status` field carries the ten states), `write_item_list`, `write_graphql_target`, `write_graphql_item` (one item's Workflow Status and Status values), `write_pr_view`, `use_fallback` (makes every `api graphql` call fail), `set_args`, `gh_call_count` and `gh_line_of` (line order in `GH_LOG`).
- The stub needs the real `jq` on the test host (`cfwf` itself never calls `jq`; it hands filters to `gh --jq`).
- `setup_isolated_env` and `cleanup_stubs` come from `test/test_helper.bash`; tests use `run --separate-stderr` when they need stderr on its own.

## Changing it safely

- Run `shellcheck containers/base/development-full/scripts/cfwf` and keep it clean.
- Run `bats test/cfwf.bats`, and `bats test/status-mapping-parity.bats` if the state list or the sourcing guard changed.
- Mutation-check any new test: break the code (for example swap `pullRequest` and `issue`, drop the `project.id` filter, or add a read-back after `--set`) and confirm the test fails, then restore it.
- A new command that posts a body must take it only from `--body-file <file|->`, call `resolve_body` (which runs `check_body_for_leaks`) before its first `gh` write, say so and mention exit 8 in its help text, and have a test proving the check runs before any write. Any other text it sends to GitHub, such as a title or a label, goes through `check_value_for_leaks` at the same point.
- Update the help text (`usage_workflow_status`, `usage_general`, `usage_closing_issue_labels`, `usage_issue`, `usage_body`, `usage_comment`) and the test that pins it ("the workflow-status help states that --set does not read back, ...").
- Update `containers/base/development-full/README.md` (the `cfwf` bullet), `docs/workflow-board.md` (the Status field section) and the `Dockerfile` comment when the surface changes. If the name or install path changes, also update `command-allowlist`, `claude-settings.json` and `install-claude-hooks`, then run `test/command-allowlist-parity.bats` and `test/install-claude-hooks.bats`.
- A label added to, removed from or edited in `.github/labels.yml` needs the same change to `STANDARD_LABELS` in `cfwf`; `test/standard-labels-parity.bats` fails until it is made. A new priority also needs `PRIORITIES` and `PRIORITY_LIST` changed.
- A new workflow state needs `WORKFLOW_STATES` in `cfwf`, `PROJECT_STATUS_OPTIONS` in `lib/project-status`, `_WF_STATUS_ORDER` in `lib/globals` and `coarse_status_for_substatus` in `lib/workflow-board` changed; the "there are ten workflow states" parity test will fail until the count is updated on purpose.
- Add a changelog entry with `dotnet changelog -f CHANGELOG.md -a <Type> -m "<message>"`. Never edit `CHANGELOG.md` by hand.
- The pre-commit hooks run the whole bats suite, so commits and pushes take minutes. Run them in the background.

## Gotchas

GitHub API behaviour `cfwf` has to allow for, and what it does:

- Lagging reads after a write. `--check` straight after `--set` may still show the old value, even from the direct query. `--set` therefore never verifies. A `--check` that disagrees with a write just made is lag, not a failed write: do not poll `--check` or repeat the write; if a later step needs the value, check again at that step (and repeat the write only if the value is still wrong then). `--check` itself does not retry.
- Listing omits new items. Only the fallback path lists the board, so the fallback can report `is not on project` for an item that was just added. The direct query does not depend on the listing.
- Listing paging and cap. The fallback reads at most 10000 items (`ITEM_LIMIT`), so on a bigger board it can miss an item. The direct query is not capped in this way. Field lists ask for 100 (`FIELD_LIMIT`).
- No single-item read in `gh project`. That is why `--check` uses GraphQL; `projectItems(first:100)` in that query is itself a limit on how many projects one issue can be on.
- `gh` may print to stderr even on success (test "anything gh writes to stderr on a successful read never ends up in the value"), and with `--jq` it can put an error body on stdout, which is why `graphql_failure_text` falls back to stdout.
- The test stub does not run the GraphQL query text on a server, so a wrong field name in the query would not be caught by the tests. The tests assert on the logged query text and the filter only.

Other things that bite:

- `--issue` with a pull request number (or the reverse) is "not on project", not an error, because `issue(number:)` resolves only issues and `pullRequest(number:)` only PRs.
- While a board still has a Workflow Status field (not converted yet, or a conversion that stopped part way), `--set` writes only that field and `--check` reads it, whatever `Status` holds. The two fields can therefore disagree until the board is converted; the Workflow Status value is the one that counts.
- `--status` is matched only against the ten workflow states, so `--status Todo` is `unknown --status` even on a board whose `Status` field still has a Todo option.
- Two open projects titled `Workflow` linked to a repository make `cfwf` refuse to guess. Close the old one.
- The item-listing JSON key used by the fallback for a Workflow Status field is `"workflow Status"` (with a lower-case `w`) as `gh` emits it, and `status` for the built-in field. If `gh` changes the first key, the fallback on a board not yet converted will read the built-in value, and so report `(unset)` for a Todo, In Progress or Done.
- Unknown options exit 2 before any `gh` call, so a typo never reaches `gh`; options after `--help` are never looked at.
- The leak check refuses a body that legitimately shows a host path or a `NAME=value` secret-shaped assignment (for example `GH_TOKEN=<token>` in documentation). Rewrite the body with a placeholder rather than looking for a way round the check.
- A visibility lookup goes through the same `gh` (and any proxy) as everything else, so it can fail or be rate-limited; that is exit 1, never a silent pass. Only the not-found answer for a repository the text names is read as "private"; for the target it is exit 1. An access-denied answer (`HTTP 403`) is exit 1 for any repository, so a caller whose organisation enforces SSO gets a runtime failure, not a `private repository` refusal.
