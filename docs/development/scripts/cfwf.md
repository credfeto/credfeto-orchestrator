# cfwf

A bash helper (Credfeto WorkFlow) that gives each recurring multi-step `gh` pattern one flat command.

Back to the [development guide](../README.md).

## Purpose

Agents used to re-derive the same multi-statement `gh` scripts every session. `cfwf` replaces them with single commands, so one `command-allowlist` entry and one `Bash(cfwf *)` permission cover them. The commands are listed under [Running it](#running-it), and each is described in [How it works](#how-it-works).

The board, the field that carries its workflow (the project's built-in `Status` field) and the option ids are all looked up from `--repo` and `--status`, so callers never handle project, field or option ids. The board itself is described in `docs/workflow-board.md`.

## Running it

```bash
cfwf workflow-status --set   --repo <owner/repo> (--pr <n> | --issue <n>) --status <name>
cfwf workflow-status --check --repo <owner/repo> (--pr <n> | --issue <n>)
cfwf closing-issue-labels    --repo <owner/repo> --pr <n>
cfwf issue create            --repo <owner/repo> --priority <priority> --title <title> --body-file <file|-> [--label <label> ...]
cfwf issue view              --repo <owner/repo> --issue <n>
cfwf issue plan-status       --repo <owner/repo> --issue <n>
cfwf body check              --repo <owner/repo> --body-file <file|->
cfwf repo view               --repo <owner/repo>
cfwf repo collaborators      --repo <owner/repo>
cfwf auth status             [--rate-limit]
cfwf pr checks               --repo <owner/repo> (--pr <n> | --sha <40-hex> | --branch <name>) [--all]
cfwf pr view                 --repo <owner/repo> --pr <n> [--field <name> ...]
cfwf pr list                 --repo <owner/repo> [--issue <n>] [--head <branch>]
cfwf pr comments             --repo <owner/repo> --pr <n>
cfwf pr reply                --repo <owner/repo> --pr <n> --comment-id <id> --body-file <file|->
cfwf comment add             --repo <owner/repo> (--pr <n> | --issue <n>) --body-file <file|->
cfwf help [command]
```

Options, all validated before `gh` is called (test "--set rejects values that could alter a jq filter or a URL, without calling gh"):

- `--repo` must match `owner/repo` (`A-Za-z0-9_.-` on each side), and neither side may be `.` or `..` (`neither the owner nor the repository can be . or ..`), because `pr checks` puts it in REST paths (`repos/<owner>/<repo>/...`) where such a segment would reach another endpoint; a name that only starts with a dot, such as `.github`, is taken (test "pr checks refuses an owner or repository of . or .., which would change the API path, before any gh call").
- `--pr` and `--issue` are digits only and mutually exclusive; one is required for both `--set` and `--check`. `assign_option` keeps the number without its leading zeros (`without_leading_zeros`; all zeros becomes `0`), for every command that takes them, because `gh` reads `0123` as `123` and answers with the URL of `123`. So the item URL `--set` adds to the board, the `n` field and the listing filter of `--check`, the `gh pr view` of `closing-issue-labels`, the `repos/<repo>/pulls/<n>` read of `pr checks`, the `gh pr comment`/`gh issue comment` of `comment add`, the `gh issue view` of `issue view` and `issue plan-status` and every message name the number the same way (tests "--set builds the item URL from a number given with leading zeros as that number, without them", "--check reads a number given with leading zeros as that number, directly and from the listing", "closing-issue-labels reads a PR number given with leading zeros as that number, without them", "pr checks reads a PR number given with leading zeros as that number, without them", "comment add posts on a number given with leading zeros as that number, without them" and "issue view and issue plan-status read a number given with leading zeros as that number, without them").
- `--status` is any text without control characters, and must be one of the ten workflow states (`WORKFLOW_STATES`): Not Started, Planning, Approved, Development, AI Simplify, AI Review, AI Security Review, AI Coverage, Human Review or Complete. It is matched without regard to case and never put into a filter. Any other name, including one the board has as an option (such as Todo), is `unknown --status` before the fields are read, so nothing is written (tests "--set refuses an option the board has that is not a workflow state, and writes nothing (#1519)" and "--set refuses a built-in option that is not a workflow state, such as Todo, before calling gh (#1519)"). `--set` needs it; `--check` rejects it (`--status is only valid with --set`).
- `--set` and `--check` are mutually exclusive. `-h`/`--help` prints the usage of the current command and exits 0 without calling `gh`.
- The old id options (`--owner`, `--project-number`, `--project-id`, `--field-id`, `--option-id`, `--url`) no longer exist and are rejected as unknown (test "the board ids and the URL are not options any more").
- `closing-issue-labels` accepts only `--repo` and `--pr` (`closing-issue-labels takes only --repo and --pr`).
- `issue create` has its own parser (`parse_issue_options`, which like `body check`'s `parse_body_options` and `pr checks`' `parse_pr_checks_options` is `parse_command_options` given its own assign function, flags that take a value and flags that take none; each assign function refuses a repeated flag with `assign_once`, which says `<flag> can only be given once`), so `--priority`, `--title`, `--body-file` and `--label` are unknown options to the other commands, and `--pr`, `--issue`, `--status`, `--set` and `--check` are unknown options to `issue create`. `--repo` is always required and is never taken from the current directory.
- `--repo`, `--priority`, `--title` and `--body-file` may each be given once only. `--priority` is required, and one of `Security`, `Urgent`, `High`, `Medium` or `Low`, matched without regard to case and applied in its canonical spelling. `--label` may be repeated, may not contain a comma (`gh` splits on commas) or a control character, and may not be a priority label (the error says `use --priority <Priority>, not --label`). `--title` must not be blank and is at most 256 characters, and a `--label` must not be blank and is at most 50 (GitHub's limits), so a value it would refuse is caught before anything is created. Lengths are counted in characters, in a UTF-8 locale (`LC_ALL=C.UTF-8`), because bash counts bytes in the C locale a container usually has. A locale that is not installed is silently ignored, so `issue create` checks that `C.UTF-8` works (`require_utf8_locale`) just before it counts a title, a label or the body, and refuses to go on without it (`--help` and usage errors do not need it), and the image build fails if it is missing. The body's length is checked by the [body leak check](#body-leak-check) (`too long`). `--body-file` is a file, or `-` for stdin, and an empty or blank body is an error (exit 1). There is no `--status`: a new issue is always `Not Started`.
- `issue create`, `body check` and `comment add` compare each argument with their flags as a whole word (`is_one_of`), so one argument holding two flags and a space, such as `"--title --body-file"`, is `unknown option` (test "issue create refuses one argument that holds two of its flags as an unknown option").
- An argument cfwf does not know, whether a command, a subcommand or an option, is refused by `unknown_argument` (exit 2) as `unknown command`, `unknown <command> subcommand` or `unknown option`, followed by `(argument <n>; its value is not shown)`, where `<n>` is its position on the command line (`ARGUMENT_COUNT`, set in `main`). The argument itself is never printed: a stray value, such as the rest of an unquoted title the shell split into words, can hold a token, and the usage error comes before the leak check (test "a token-shaped stray argument is named by its position, never echoed, as a command, a subcommand or an option").
- `pr checks` has its own parser (`parse_pr_checks_options`, whose assign function is `assign_checks_option` and whose only flag without a value is `--all`) and accepts only `--repo`, `--pr`, `--sha`, `--branch` (each once, compared as whole words with `is_one_of`), `--all` and `-h`/`--help`. `--repo` is required. Exactly one of `--pr` (digits only), `--sha` (exactly 40 hexadecimal digits, in any case, lower-cased) and `--branch` is required (`require_one_checks_target`: `give exactly one of --pr, --sha and --branch`). A `--branch` must pass `valid_branch_name`, which asks git itself (`git check-ref-format --branch`, with `GIT_DIR=/dev/null` so git never expands `@{-1}` from a repository the caller is in, and the name git prints compared with the name given), so cfwf keeps no copy of git's rules: among others no control character, whitespace, `~`, `^`, `:`, `?`, `*`, `[` or `\`, no leading `-`, no `..` or `@{`, not `HEAD`, and no component that starts with `.` or ends with `.lock` (test "pr checks --branch judges a name as git does, even run from a repository where @{-1} names a branch"); a missing git is a runtime failure (`git is not installed`), never a usage error. The error (`it must be a branch name git allows`) never echoes it. Any byte git allows, such as `+`, `@` (and `@` alone), `%` or a non-ASCII letter, is allowed: `branch_path` percent-encodes every byte other than a letter, digit, `.`, `_`, `~`, `-` or `/` when the name goes in an API path, so no name can change the path or the query (test "pr checks percent-encodes a branch name git allows but an API path cannot hold as it is, rather than refusing it"). `/` is left as it is, because GitHub reads a branch name with slashes from the rest of the path, and the `.` and `..` components that could change a path are already refused. `--json`, `--jq`, `--template`, `--watch`, `--interval`, `-i` and `--required` are unknown options, so they exit 2 like any other (test "pr checks usage errors exit 2 before any gh call").
- `issue view` and `issue plan-status` share one parser (`parse_issue_read_options`: `parse_command_options` with the assign function `assign_issue_read_option`, then the two `require` checks) and accept only `--repo` and `--issue`, both required and each once (`assign_once`), and `-h`/`--help`. `--issue` is digits only. Nothing else is an option: `--json`, `--jq`, `--template`, `--comments`, `--web`, `--pr` and the options of `issue create` are all `unknown option`, so the fields read and the output format can never be changed from the command line (test "issue view and issue plan-status usage errors exit 2 with their own usage, before any gh call").
- `repo view` and `repo collaborators` share one assign function (`parse_command_options` given `assign_repository_option`, with no flag that takes no value) and accept only `--repo` (required, once, validated as for every other command) and `-h`/`--help`. `--json`, `--jq`, `--template`, `--hostname`, `--affiliation`, `--permission`, `--paginate`, `--limit`, `--branch` and `--web` are unknown options, so neither the fields read nor which collaborators are listed can be changed from the command line (test "repo view and repo collaborators usage errors exit 2 with their own usage and nothing on stdout, never echoing a value, before any gh call"). `auth status` takes no target: its only option is the switch `--rate-limit` (`assign_auth_option`), and `--repo`, `--hostname`, `--show-token`, `--active`, `--json` and `--jq` are unknown options, so there is no way to name a host or to ask for a token; `--rate-limit` given twice is taken as given once, as `--all` of `pr checks` is, since `parse_command_options` hands a switch to the assign function each time it is seen and a switch only sets a flag (tests "auth status takes --rate-limit given twice as given once, as pr checks takes --all: the same nine lines from the same three gh calls" and "auth status usage errors, --repo and every way of naming a host or asking for a token among them, exit 2 with its usage and nothing on stdout, never echoing a value, before any gh call"). `cfwf repo` and `cfwf auth` with no subcommand name theirs (`repo needs a subcommand (view, collaborators)`, `auth needs a subcommand (status)`), and `gh`'s other `auth` subcommands (`token`, `login`, `logout`, `refresh`, `setup-git`, `switch`) are unknown subcommands (test "repo and auth with no subcommand name theirs, and a subcommand neither has is refused by its position and never echoed, each exit 2 with nothing on stdout and no gh call"). Help: `cfwf repo view -h`, `cfwf repo collaborators -h` and `cfwf auth status -h` (or `--help`, or `cfwf help <command> <subcommand>`) each print that command's usage alone, `cfwf help repo` and `cfwf repo -h` print both `repo` usages, and `cfwf help auth` is the `auth status` usage (the `repo`, `"repo view"`, `"repo collaborators"` and `auth | "auth status"` arms of `usage_for`), which the test "repo view, repo collaborators and auth status help is the same from -h, --help and help with the command and its subcommand, is that command's alone, states its format, order, limit, refusals and exit codes, help repo gives both repo usages, and none calls gh" pins: update both when an option, the output, the limit or the exit codes change.
- A command with subcommands is run by `dispatch_subcommand <command> <subcommand> <function> ... -- <arguments>`, which sets `CURRENT_COMMAND` to the command and its subcommand (`issue view`), so a usage error, or a subcommand's `-h`, prints the usage of that subcommand alone (`usage_for`), while `cfwf help issue` and `cfwf issue -h` print the usage of all three `issue` subcommands. `cfwf help <command> <subcommand>` (`main` hands `usage_for` the two words as one pair) prints what that subcommand's `-h` prints, and a pair `usage_for` does not know, such as a mistyped subcommand, prints the usage of its command (test "help for a command and its subcommand prints what that subcommand's -h prints, and the command's usage for a subcommand it does not know"). A command given no subcommand is told which it has (`issue needs a subcommand (create, view, plan-status)`).
- `pr view` has its own parser (`parse_command_options` given `assign_view_option`, with no flag that takes no value) and accepts only `--repo` and `--pr` (each once, `--pr` digits only and above 0, both required), `--field` (repeatable) and `-h`/`--help`. A `--field` value must be one of the names in `PR_VIEW_FIELD_NAMES`, compared as a whole word with `is_one_of`, so a gh name such as `isDraft`, another case (`State`) or a comma-joined list is refused (`unknown --field: it must be one of the fields listed below`, never echoing the value). A `--pr` of `0` (or `000`) is refused (`invalid value for --pr: it must be a number above 0`, exit 2) before any `gh` call: `gh pr view` does not take 0 as a number and looks for a branch of that name instead, so it would answer with a failed read (exit 1, not 9) or with another pull request. A name given more than once counts once (`REQUESTED_FIELDS` is an associative array). `files` and `body` are refused when any other field is asked for with them (`resolve_view_fields`: `--field body can only be asked for alone: it is not printed as a key and value line`), because neither is a key and value line. `--json`, `--jq`, `--template`, `--web` and `--comments` are unknown options: there is no pass-through to gh (tests "pr view usage errors exit 2 with the pr view usage, before any gh call" and "pr view refuses body or files together with another field (exit 2) before any gh call"). A usage error in `pr view` prints the `pr view` usage alone (`CURRENT_COMMAND` is `pr view`), and `cfwf pr` with no subcommand names each of them (`pr needs a subcommand (checks, view, list, comments, reply)`). Help: `cfwf pr view -h` (or `--help`) and `cfwf help pr view` print the `pr view` usage alone (the `"pr view"` arm of `usage_for`). `cfwf help pr` and `cfwf pr -h` print the `pr checks` usage, which ends with a pointer to each of `cfwf pr comments --help`, `cfwf pr reply --help`, `cfwf pr view --help` and `cfwf pr list --help` (tests "pr list help gives the usage line, the eight columns, the limit and the exit codes, help pr and the general help point to it, and none calls gh" and "pr view help, from help pr view, pr view --help and pr view -h, lists every field and exit code and calls no gh").
- `body check` accepts only `--repo` and `--body-file` (both required, each once, validated as for `issue create`) and `-h`/`--help`. There is no option to skip the check: `--force` or `--skip-leak-check` is an unknown option (test "body check help and usage errors, none of which call gh").
- `comment add` accepts only `--repo`, exactly one of `--pr` or `--issue` (digits only), `--body-file` and `-h`/`--help`, each option once (`--pr` or `--issue` a second time, or both, is `--pr or --issue can only be given once, and not both`). `--body`, `--edit-last`, `--json` and `--jq` are unknown options, so a comment is only ever taken from `--body-file` and only ever added, never edited (test "comment add usage errors exit 2 with the usage on stderr and never call gh").
- `pr list` has its own parser (`parse_command_options` given `assign_list_option`, with no flag that takes no value) and accepts only `--repo` (required), `--issue` and `--head`, each once, and `-h`/`--help`. `--issue` is digits only and above 0 (`it must be a number above 0`), and its leading zeros are dropped, so `012` is `12`. `--head` must pass `valid_branch_name`, as `--branch` of `pr checks` must, and must also hold no control character (`holds_control_character`, which matches `CONTROL_PATTERN` in the C locale): git allows a C1 control in a branch name, and `pr list` prints one as a space, so such a value could never equal the head it is compared with. The error (`it must be a branch name git allows, with no control character`) never echoes the value. The `owner:branch` form is refused by git's rules (the colon). `--issue` and `--head` may be given together: `--head` chooses which pull requests are listed and `--issue` only adds a flag. `--json`, `--jq`, `--search`, `--state`, `--limit`, `--author`, `--app`, `--base`, `--draft` and `--web` are unknown options (tests "pr list usage errors exit 2 before any gh call, each with the pr list usage" and "pr list refuses a --head git would not allow, or one holding a control character, without echoing it or calling gh"). Help: `cfwf pr list -h` (or `--help`) and `cfwf help pr list` print the `pr list` usage alone (the `"pr list"` arm of `usage_for`), which the test "pr list help gives the usage line, the eight columns, the limit and the exit codes, help pr and the general help point to it, and none calls gh" pins: update both when its options, output, limit or exit codes change.

Environment variables: `CFWF_PRIVATE_OWNERS`, a space-separated list of owner logins whose repositories are all private (empty by default), read by the [body leak check](#body-leak-check) once per run (`load_private_owners`, which the body, the title and each label share). A value that is not an owner login is a runtime failure, which does not echo the value. `GH_HOST` is `gh`'s own, and `auth status` reads it only to print it (see [Repository and account lookups](#repository-and-account-lookups)); it is the one environment variable `cfwf` ever prints. `gh` reads its own (for example `GH_TOKEN`), and `mktemp` honours `TMPDIR`. `CFWF_BIN_DIR` belongs to `install-claude-hooks`, not to `cfwf`.

Output and exit codes:

- `--set` prints `Set <url> to <status>` (the canonical option name, so `ai security review` prints `AI Security Review`) and exits 0. The URL is `https://github.com/<repo>/pull/<n>` or `.../issues/<n>`.
- `--check` prints one line, the state name alone, for example `Development` (test "--check prints only the status name, with no parenthetical (#1519)"). It prints `(unset)` when the item has no workflow state. It exits 1 with `<repo>#<n> is not on project <number>` when the item is not on the board.
- `closing-issue-labels` prints the sorted, de-duplicated labels, one per line, leaving out exactly `Blocked` and `On-Hold` (`Blocked-by-upstream` is kept).
- `issue create` prints the issue URL and nothing else on stdout when it succeeds. If the issue was created but a later step failed, stderr ends with `the issue was already created: <url>`, so the issue is never lost; a failure before the issue exists never says that.
- `body check` prints nothing and exits 0 when the body passes.
- `pr list` prints one line for each open pull request, sorted by number, with no header and no summary: `<number>\t<head>\t<base>\t<author>\t<draft|ready>\t<flags>\t<url>\t<title>`. Each line has exactly eight tab-separated fields and none is ever empty: a field with no value, such as the author of a pull request whose account is gone, is `-`. The fixed fields come first and the only free text, the title, is last. `flags` is a comma-joined list, always in the order `issue`, `github-actions`, `fork`, or `-` when there is none, so a flag added later does not change the number of columns: `issue` when `--issue` was given and the head branch holds that number, `github-actions` when the author's login is exactly `app/github-actions`, and `fork` when the head branch is in another repository. An empty list prints nothing and exits 0. More than 1000 open pull requests to list (`PR_LIST_LIMIT`; with `--head`, more than 1000 on that branch) is exit 1 with `cfwf: <repo> has more than 1000 open pull requests, so none is printed`, and so is any failed read; nothing is printed in either case.
- `pr checks` prints one tab-separated line per judged check, sorted by name in the C locale, `<name>\t<pass|fail|pending>\t<completed_at>\t<run_id>` (where a name is required more than once, each line pinned to an app shows `<name> (app <id>)`, sorting after the bare name), then `summary passed=<a> failed=<b> pending=<c> head=<sha>`: the last line and the only one with no tab, as each check line has exactly four tab-separated fields, so a check named `summary` is never taken for it (test "pr checks keeps a check named summary apart from the summary line, the only line with no tab"). `completed_at` is empty for a result that has not finished (and for a pending commit status), and both it and `run_id` are empty for a required check with no result; for a commit status `run_id` is the status id and `completed_at` its `updated_at`. Nothing is printed until every read has succeeded. Its verdict codes (`CHECKS_FAILED_EXIT`, `CHECKS_PENDING_EXIT`, `NO_CHECKS_EXIT`) are shared by every `cfwf` command that judges checks: 0 every judged check passed, 3 at least one failed, 4 none failed and at least one is pending, 5 the head has no check runs or commit statuses at all (checked first, so a head with none exits 5 even where required checks are configured; they are still printed as pending).
- `issue view` prints four lines, each a field name, a tab and its value, then a blank line, then the body (test "issue view prints an open issue's title, state, labels and assignees, then its body unchanged, in one gh call"):

  ```text
  title<TAB><the title>
  state<TAB><OPEN|CLOSED>
  labels<TAB><the label names, comma separated>
  assignees<TAB><the assignee logins, comma separated>

  <the body>
  ```

  `labels` and `assignees` keep their tab and have nothing after it when there are none. Each control character in the title, a label name or a login is printed as a space (the jq definition `printable`), so each field stays on its own line and carries no terminal escape. The body is printed exactly as GitHub returns it, byte for byte (tabs, blank lines, trailing whitespace, CRLF line endings and trailing newlines included), followed by one newline, so the body is everything after the first blank line less the final newline; an issue with no body prints an empty line there. It is not filtered or checked for leaks: the leak check guards what `cfwf` posts, and this is a read of the repository's own content, so a caller must treat the body as untrusted text.
- `issue plan-status` prints `plan<TAB><yes|no>`, then `blocked<TAB><yes|no>`, and, only when there is a plan, `plan-at<TAB><createdAt>` (the ISO 8601 time GitHub gives the latest plan comment), `plan-by<TAB><author login><TAB><authorAssociation><TAB><url>` (who wrote that comment, and where it is) and one line for each comment after that plan, oldest first: `comment<TAB><createdAt><TAB><author login><TAB><authorAssociation><TAB><yes|no><TAB><url>`. The login is empty for a comment, or a plan, whose account was deleted. The `yes` or `no` says whether the comment's body holds a plan sign-off keyword outside a Markdown quote (see [How it works](#how-it-works)). A comment body is never printed (test "issue plan-status never prints a comment body, and keeps every line in its fields whatever a comment holds"). A `yes` is not an approval: who may sign a plan off is decided by login against a list the caller holds, which `cfwf` does not have, so it reports the login and the association and leaves that decision to the caller. The same goes for the plan: any comment with the heading line is one, whoever wrote it, so `plan-by` is there for the caller to check that the latest plan is from an author it trusts before reading a sign-off as being for it (test "issue plan-status reports who wrote the latest plan, so a caller can tell a plan from an author it does not trust").
- `repo view` prints six `<field>\t<value>` lines, always in this order: `default-branch`, `visibility` (GitHub's own value: `PUBLIC`, `PRIVATE` or `INTERNAL`), `allow-merge-commit`, `allow-squash-merge`, `allow-rebase-merge` (each `yes` or `no`) and `description`, the only free text, last. A field with no value prints its name, the tab and nothing else, so every line has exactly one tab: the default branch of an empty repository, a repository with no description, and a merge method GitHub did not give, which means not known and never `no`. Each control character in a value is printed as a space (`PRINTABLE_DEF`), as for `pr view`. The description is not checked for leaks, as no read is: treat it as untrusted text.
- `repo collaborators` prints one line for each collaborator, `<login>\t<role>`, sorted by login in the C locale (byte order, so every upper-case letter comes before every lower-case one), with no header and no summary. Each line has exactly two tab-separated fields and neither is empty: `role` is GitHub's `role_name` (`admin`, `maintain`, `write`, `triage`, `read` or the name of a custom role, each control character in it printed as a space) and `-` when GitHub gives none. A caller that wants the logins alone takes the first column. An empty list prints nothing and exits 0. More than 1000 collaborators (`COLLABORATOR_LIMIT`) is exit 1 with `cfwf: <repo> has more than 1000 collaborators, so none is printed`, and a caller without push access is exit 1 with `cfwf: could not list the collaborators of <repo>: gh: Must have push access to view repository collaborators. (HTTP 403)`; nothing is printed in either case, never part of a list or an empty one.
- `auth status` prints three `<field>\t<value>` lines, always in this order: `login` (the authenticated login, asked of GitHub each time), `host` (the value of `GH_HOST`, or `github.com` when it is unset or empty) and `gh` (the version number from the first line of `gh --version`). With `--rate-limit` six more follow: `core-remaining`, `core-limit`, `core-reset`, `graphql-remaining`, `graphql-limit` and `graphql-reset`, the counts as digits and each reset as ISO 8601 in UTC. Nothing is printed unless every read asked for succeeded, and no token, header or other environment variable is ever printed. Not authenticated is exit 1 with `cfwf: not authenticated`; any other failed read is exit 1 with its own message (`could not read the authenticated user: ...`, `could not read the rate limit: ...`, `could not read the version of gh: ...`), so a caller tells the two apart by the text.
- `comment add` prints the comment URL and nothing else on stdout when it succeeds.
- `pr view` prints one `<field>\t<value>` line for each field, always in the order of the table below whatever order `--field` was given in. With no `--field` it prints every field but `files` and `body` (18 lines). A field with no value prints its name, the tab and nothing else, so every line has exactly one tab and a caller can read a value with `cut -f2-`. Each control character in a value (C0, a tab, a newline and a carriage return included, DEL, and C1) is printed as a space (`PRINTABLE_DEF`, shared with `pr checks`), so no title, label, branch name or login can add a line or look like another field (test "pr view prints a tab, a newline or a carriage return in a title, label, branch or login as a space, so it never adds or alters a line"). Nothing is printed unless the read succeeded.

  | Field | gh `--json` field | Value |
  | --- | --- | --- |
  | `state` | `state` | `OPEN`, `CLOSED` or `MERGED` |
  | `draft` | `isDraft` | `yes` or `no` |
  | `title` | `title` | the title |
  | `url` | `url` | the pull request's URL |
  | `base` | `baseRefName` | the base branch |
  | `head` | `headRefName` | the head branch |
  | `head-sha` | `headRefOid` | the head commit |
  | `auto-merge` | `autoMergeRequest` | `on` when there is an auto-merge request, otherwise `off` |
  | `review-decision` | `reviewDecision` | GitHub's own value (`APPROVED`, `CHANGES_REQUESTED`, `REVIEW_REQUIRED`), empty when there is none |
  | `merge-state` | `mergeStateStatus` | GitHub's own value (`BEHIND`, `BLOCKED`, `CLEAN`, `DIRTY`, `DRAFT`, `HAS_HOOKS`, `UNKNOWN`, `UNSTABLE`) |
  | `mergeable` | `mergeable` | GitHub's own value (`MERGEABLE`, `CONFLICTING`, `UNKNOWN`) |
  | `created-at` | `createdAt` | when it was created |
  | `merged-at` | `mergedAt` | when it was merged, empty when it is not merged |
  | `merge-commit` | `mergeCommit` | the merge commit's SHA, empty when it is not merged |
  | `labels` | `labels` | the label names, comma-joined |
  | `assignees` | `assignees` | the assignees' logins, comma-joined |
  | `author` | `author` | the author's login |
  | `commit-authors` | `commits` | the distinct commit author logins, in the order first seen, comma-joined; a commit can have several authors, and one with no login is left out |
  | `files` | `files`, `changedFiles` | the changed paths, one a line (each made printable, as a value is); only when asked for alone |
  | `body` | `body` | the body, unchanged, byte for byte, with no newline added; only when asked for alone |

- Exit 0 is success and help; 1 is a runtime failure (`die`, prefixed `cfwf:`), including a repository visibility lookup or a leak-check scan that fails, any failed read in `pr checks`, which is never reported as a failed check, a repository `repo view` or `repo collaborators` does not find or cannot see, no push access or more than the limit in `repo collaborators`, and `auth status` when not authenticated (none of the three uses exit 9); 3, 4 and 5 are the `pr checks` verdicts above; 2 is a usage error, printed with the usage text on stderr; an error about an option's value names the option and the rule it broke (`invalid value for --title: it must not contain a control character`, `unknown --priority`, and the runtime failure `unknown --status`) and never the value, and an unknown argument is named only by its position, because a free-text value such as a title can hold a token and these checks run before the leak check (test "a usage error names the option and the rule but never echoes the value, which could hold a token"); 8 is a body refused by the leak check (`BODY_REFUSED_EXIT`), from `issue create`, `body check`, `comment add` or `pr reply`, or by `comment add`'s `approval keyword` rule, with `cfwf: body refused: <rule>` and `(line <n>)` where there is one on stderr; 9 is an issue or a pull request that does not exist: an issue (`ISSUE_NOT_FOUND_EXIT`), from `issue view` or `issue plan-status`, with `cfwf: <repo>#<n> was not found`, or `cfwf: <repo>#<n> is a pull request, not an issue` for a pull request's number, and a pull request (`PR_NOT_FOUND_EXIT`), from `pr view` or `pr comments`, with `cfwf: the pull request <repo>#<n> was not found`, the number of an issue included, or from `pr reply`, when `--comment-id` is not an inline review comment of that pull request (see [Pull request comments and replies](#pull-request-comments-and-replies), which also gives the output of both); each is on stderr with nothing on stdout, so a caller can tell a wrong number apart from a read that failed (1); a repository that is not there is a failed read, not a missing pull request. A bare `cfwf` prints the usage to stderr and exits 2.

## How it works

`workflow-status --set` (`workflow_status_set`):

1. `require` and `require_target` check the options (`--pr` becomes type `PullRequest`, URL kind `pull`; `--issue` becomes `Issue`, `issues`), and `require_gh` checks `gh` is installed.
2. `resolve_project` runs `gh repo view <repo> --json projectsV2` and keeps the one open project titled `Workflow` (a closed one is ignored; none or two is a `die`). The owner is taken from the project's own `resourcePath` (`/users/...` or `/orgs/...`), not assumed to be the repository owner.
3. `resolve_status` first checks `--status` with `canonical_workflow_state` and rewrites `STATUS` to its canonical spelling; an unknown name dies listing the ten states. It then runs `gh project field-list <n> --owner <owner> -L 100` and looks for an option with that name on the `Status` field and on a `Workflow Status` field. It uses the `Workflow Status` field whenever the board still has one, whatever `Status` holds, so `--set`, `--check` and the conversion agree on which value is the real one even on a board whose conversion stopped part way; on a converted board it uses `Status`. It dies naming the field it chose when that field has no such option. A field named `Status` that has no options is ignored. It sets `FIELD_ID`, `FIELD_NAME` and `OPTION_ID`.
4. `gh project item-add ... --format json --jq .id` adds the item (the help text says adding is idempotent), and the id is checked against `^[A-Za-z0-9_=-]+$` before use.
5. One `gh project item-edit` sets the chosen field; a failure dies naming that field (`could not set the <field> of <url>`). There is no read-back and no other `gh` call after that: the script prints `Set <url> to <status>`.

`workflow-status --check` (`workflow_status_check`) calls `resolve_project` and then `read_target_status`:

1. `gh_capture api graphql` runs a read-only query for the one issue (`issue(number:)`) or pull request (`pullRequest(number:)`), asking for `projectItems(first:100)` with `legacy:fieldValueByName(name:"Workflow Status")` and `status:fieldValueByName(name:"Status")` in the one query. The `--jq` filter keeps only the item whose `project.id` is the Workflow project's, then picks the value: the Workflow Status value when the board still has that field, otherwise the Status value when it is one of the ten states, otherwise `(unset)`. So on a board not yet converted a built-in Todo, In Progress or Done reads as `(unset)`. `gh_capture` is the wrapper the board read, the visibility lookup, the issue read of `issue view` and `issue plan-status`, the `repo view` read, the `repo collaborators` read, the reads of `auth status`, every `pr checks` read, the `pr view` read, the `pr list` read, the `pr comments` read and the read and the post of `pr reply` go through (`resolve_project`, the field list, the board listing and the closing-issue labels still call `gh` directly): it gives `gh` no stdin, puts stdout in `GH_OUTPUT` and stderr (through `GH_ERR_FILE`) in `GH_ERROR`, and returns `gh`'s exit status, so gh's stderr chatter can never end up in a value.
2. If GitHub answers `Could not resolve to an Issue with the number` (or `... a PullRequest ...`) that means not found, not failure.
3. Any other failure calls `fall_back_to_listing`: a warning on stderr (`gh_failure_text` quotes only the first line of `GH_ERROR`, or of `GH_OUTPUT` when stderr is empty, printable characters only, at most 200 characters) and then `gh project item-list <n> --owner <owner> --format json -L 10000` (`ITEM_LIMIT`), filtered by repository (case-insensitive), number and type, with the same choice between the two values.
4. If both fail, `cfwf` dies with `both the direct query and the listing of project <n> failed`.

`closing-issue-labels` (`cmd_closing_issue_labels`) reads `gh pr view --json closingIssuesReferences`, then `gh issue view <n> --repo <that issue's own repo> --json labels` for each (a PR can close an issue in another repository), filters out `Blocked` and `On-Hold`, and runs `sort -u`. An unreadable issue or a malformed reference produces a warning, still prints the other labels, and makes the exit status 1, so a partial list is never mistaken for a complete one.

`comment add` (`comment_add`), in this order, so a bad call posts nothing:

1. `parse_command_options assign_issue_option "--repo --pr --issue --body-file" ""`, `require REPO`, `require_target` and `require BODY_FILE` (exit 2), then `require_gh`.
2. `resolve_body`, as for `issue create`: the private copy, refused with exit 1 when it cannot be read or is blank, then `check_body_for_leaks` on that copy for `--repo` (exit 8). A missing, unreadable or blank body is a runtime failure (exit 1), as it is for `issue create` and `body check`, not a usage error (test "comment add refuses a missing, unreadable, empty or blank body as a runtime failure, without calling gh").
3. `check_comment_for_approval_keywords`: a copy of the body with every Markdown quote line (at most three spaces, then `>`; Markdown reads a deeper indent, or a tab, as code, so such a line is not exempt) blanked, so line numbers are kept, is scanned with `refuse_first_match ... -i` for `APPROVAL_KEYWORD_PATTERN`, the two plan-approval keywords between word boundaries. Letters, digits and `_` are word characters, so a longer word that holds the letters passes, an identifier such as `plan_approved` included, while one after or before punctuation (`(word)`, `word,`) is refused. Underscores that only wrap the keyword, with a boundary beyond them, are Markdown emphasis (`_word_`, `__word__`), which renders as the keyword alone, so that is refused too, as `**word**` is. A refusal is `cfwf: body refused: approval keyword (line <n>)`, exit 8. The rule exists because a comment an agent posts under a trusted human's account would otherwise read as that human approving a plan; quoting the human's own words on a `>` line is how the plan-approval rules say to mirror a real approval, so it passes (tests "comment add refuses a plan-approval keyword outside a quote with exit 8, in any case, naming only the line" and "comment add posts a plan-approval keyword inside a Markdown quote, and a longer word holding the letters"). The rule runs after the leak check, and `body check` does not apply it (test "body check does not apply the plan-approval keyword rule"), so a body that passes `body check` can still be refused here. A quote inside a list item (`- > ...`) is not a quote line and is refused.
4. `gh pr comment <n>` (for `--pr`) or `gh issue comment <n>` (for `--issue`), where `<n>` is the number without its leading zeros (see [Running it](#running-it)), with `--repo` and `--body-file <copy>`, stdin from `/dev/null` so `gh` can never wait on it. A failure dies with `could not post the comment on <repo>#<n>`.
5. The last line of `gh`'s output must look like `https://<host>/<owner>/<repo>/(pull|issues)/<n>#issuecomment-<digits>`, where `<n>` is that same number, otherwise it dies saying the comment may have been posted, without echoing the answer. As for `issue create`, the host, owner and repository are not compared (a proxy answers with its own host, a renamed repository with its new name), and `pull` and `issues` are both accepted whichever option was given, because GitHub answers a comment made on a pull request through its issue number with the pull request URL (tests "comment add accepts a comment URL from another host, and a pull URL for an issue number" and "comment add exits 1, printing nothing on stdout, when the result is not the comment URL of the target"). The URL is then printed.

`issue create` (`issue_create`), in this order, so a bad call leaves no issue behind:

1. `parse_issue_options` and the required-option checks (exit 2), then `collect_issue_labels`: the priority label first, then each `--label`, with a standard label written in its standard spelling and a repeat in any case dropped, and any priority among them refused.
2. `require_gh`, then `resolve_body`: a file must be a readable regular file, or `-` for stdin; one that is not dies with `cannot read the --body-file`, which never names the path, because it is usually a host path (a temporary or runtime directory) that the leak check would refuse to post (tests "issue create refuses a missing, unreadable, empty or blank body, without calling gh" and "body check refuses a missing or blank body as a runtime failure, without calling gh"); either is copied to a private temporary file (`BODY_PATH_TMP`), which must contain a non-blank character. `resolve_body` then runs `check_body_for_leaks` on that copy, the one `gh` is given, so a body file rewritten after the check, by a writer that has not finished or between the check and the post, is never posted unchecked (test "issue create hands gh the private copy it checked, so a body file rewritten after the check is never posted") (see [Body leak check](#body-leak-check)), so a refused body exits 8 before the board is read or anything is written (test "issue create refuses a body naming a private repository before any board read or write"). `check_value_for_leaks` then checks the `--title` and each `--label` as given, the same way (tests "issue create refuses a title or a label with a token or a host path, naming only the rule, before calling gh" and "issue create refuses a title or a label naming a private repository on a public target, before any write").
3. `resolve_project` and `resolve_status "Not Started"`, the same reads as `--set`, so a repository with no Workflow board, or a board with no `Not Started` option, fails here.
4. `ensure_labels_exist` lists the repository's labels once (`gh label list --limit 1000`, matched without regard to case) and runs `gh label create` for each missing one: with `--color` and `--description` from `STANDARD_LABELS` for a standard label, and with neither for any other, so `gh` picks the colour. The name comes after `--`, so a name that starts with a dash is not read as a flag. An `already exists` answer is not an error (the label appeared after the listing); any other failure dies before the issue exists.
5. `gh issue create --repo ... --title ... --body-file <path> --label ...` for every label. The last line of its output must look like `https://<host>/<owner>/<repo>/issues/<n>`, otherwise it dies saying the issue may have been created and naming what `gh` answered with. Neither the host nor the owner and repository are compared with anything: `gh` may be reached through a proxy that answers with its own host, and a renamed or transferred repository answers with its new name.
6. `CREATED_URL` is set, which makes the `EXIT` trap report the URL if the run then fails. `put_item_on_board` (the code `--set` uses) adds the item and sets it to `Not Started` on the field `resolve_status` chose (the Workflow Status field on a board not yet converted, test "issue create sets Not Started on the Workflow Status field of a board not converted yet (#1519)"), and the URL is printed.

`issue view` (`issue_view`) and `issue plan-status` (`issue_plan_status`) only read, each with a single `gh` call:

1. `parse_issue_read_options` checks the options (exit 2), then `require_gh`.
2. `read_issue <fields> <filter>` runs `gh issue view <n> --repo <repo> --json url,<fields> --jq <program>` through `gh_capture`: `url,title,state,labels,assignees,body` for `issue view` and `url,labels,comments` for `issue plan-status`. The field list and the jq program are fixed in the script, and each caller's filter starts with the jq definitions it uses (`PRINTABLE_DEF`, and `SIGNS_OFF_DEF` for `issue plan-status`), so `read_issue` itself knows nothing of what a filter prints; `gh` fetches every comment for `--json comments`, so no second call is made. If `gh` fails with `Could not resolve to an issue or pull request with the number` (`ISSUE_NOT_FOUND_TEXT`, how GitHub answers a number that is neither), `issue_not_found` prints `cfwf: <repo>#<n> was not found` and exits 9; any other failure, a repository that was not found included, dies with `cfwf: could not read <repo>#<n>: <gh's first error line>` (`gh_failure_text`), so a proxy 502 is never read as a missing issue (test "issue view and issue plan-status report a failing gh as a runtime failure (exit 1), never as a missing issue").
3. `gh issue view` answers a pull request's number with the pull request, so `read_issue` always reads `url` and puts a first line in front of the filter's output, `pull` when the URL ends in `/pull/<n>` and `issue` otherwise. `pull` exits 9 with `is a pull request, not an issue`; anything but `issue` followed by more output dies with `gh returned an unexpected result`. The rest is left in `GH_OUTPUT`.
4. `issue view`'s filter builds the whole output as one string that ends in `\x1f` (`OUTPUT_END`). `gh_capture` holds the output in a variable, and a command substitution drops every trailing newline, which would cut the blank lines at the end of a body; the `\x1f` after the body keeps them, and is removed before printing. The state line must be `OPEN` or `CLOSED` and the output must end with `OUTPUT_END`, otherwise it dies with `gh returned an unexpected result`, printing nothing.
5. `issue plan-status`'s filter finds the plan: the last comment, in thread order, with a line that is exactly `## Implementation Plan` (the body split into lines, a trailing carriage return dropped from each, and each compared whole and case-sensitively). This is the definition the plan-approval rules give (`ai/global/agent-roles.instructions.md`), so the command and the rules agree on which comment is the plan: a plan with a preamble before its heading counts, while a heading in another case, with anything else on its line (`## Implementation Plan (revised)`), or in the issue's description does not (tests "issue plan-status takes a comment as a plan wherever its heading line is, with LF or CRLF line endings" and "issue plan-status reports no plan, and no comment lines, for an issue with no plan comment, in one gh call"). `blocked` compares each label name, lower-cased, with `blocked`, so `Blocked-by-upstream` is not it. The comment lines are the comments after the plan by position in the thread, not by comparing times, since two comments can share a second. Every field of the `plan-by` line and of a comment line goes through `printable`.
6. The sign-off answer is the jq definition `signs_off` (`SIGNS_OFF_DEF`): the body is split into lines, each line that is a Markdown quote (`^ {0,3}>`: a `>` after at most three spaces, because Markdown reads four spaces or a tab as code) is dropped, and the answer is `yes` when any line left matches `APPROVAL_KEYWORD_PATTERN`, the one pattern `comment add`'s `approval keyword` rule also uses, without regard to case. The pattern takes either of the two keywords the plan-approval rules name (`ai/global/agent-roles.instructions.md`) as a whole word: a letter, digit or underscore on either side makes a longer word, which does not match, while underscores with only a boundary beyond them are Markdown emphasis, which renders as the keyword alone and does match (tests "issue plan-status says yes for a sign-off keyword as a whole word, in any case, with punctuation or Markdown emphasis around it", "issue plan-status says no for a sign-off keyword inside a longer word, and for a comment with none" and "issue plan-status ignores a sign-off keyword on a Markdown quote line, and only there"). The body is split into lines before either pattern is applied because `^` and `$` match at every line in `jq` but only at the ends of the text in `gh`'s `gojq`; on a single line both read them alike. The two commands differ in one case only: `comment add` matches bytes in the C locale, where every byte of a non-ASCII character is a boundary, while `jq` and `gojq` match characters and, told to ignore case, count a non-ASCII character that folds to an ASCII letter (such as U+212A, the Kelvin sign, and U+017F, the long s) as a letter. A keyword with such a character right against it is therefore refused by `comment add` and answered `no` here; `comment add` is the stricter of the two, so nothing it posts is answered `yes` (test "comment add refuses, and issue plan-status says no for, a keyword right against a non-ASCII character that folds to an ASCII letter").

`pr list` (`pr_list`) makes one read and nothing else:

1. `parse_command_options` with `assign_list_option` and `require` check the options (exit 2), then `require_gh`.
2. `gh_capture pr list --repo <repo> --state open --limit 1001 [--head <branch>] --json number,title,author,headRefName,baseRefName,isDraft,isCrossRepository,url --jq <program>`. It is one more read that goes through `gh_capture`, so it shares `GH_ERR_FILE` with the others. `gh` pages up to the limit itself, so a repository with at most 1000 open pull requests is read whole in the one call, and asking for one more than `PR_LIST_LIMIT` is what shows that there are more. `--head` goes to `gh` as its own argument, which filters on the head branch name in the listing; no `--search` is ever built. A failed read, a repository that is not found included, dies with `could not list the open pull requests of <repo>: <gh's first error line>` (`gh_failure_text`).
3. `pr_list_program` prints the jq program: `PRINTABLE_DEF`, then `field`, which makes a value a string, makes it printable and turns an empty one into `-`, then the number of pull requests on the first line and one row for each, sorted by number and joined with tabs. Every field read from GitHub goes through `field`, so a tab, a newline, a carriage return, DEL or a C1 control in a title, a branch name, a login or a URL is a space before the row is joined: no value can add a line, a field or a terminal escape (tests "pr list keeps a title with a tab, a newline, a carriage return or a whole forged row on one line of eight fields" and "pr list prints every C0, DEL and C1 control in a title or a branch name as a space, and keeps U+00A0, just past C1"). No field may be empty because a reader that splits on tabs with `read` collapses consecutive tabs, as the `ROW_SEPARATOR` comment in the script records. As in the rest of the script, invisible characters that are not controls, such as the bidi formatting ones, are left as they are.
4. The `issue` flag is the jq test `(^|[^0-9])0*<n>([^0-9]|$)` on `headRefName`: a run of digits whose value is the number, with no digit on either side. It is the digit-boundary test of `issue_branch_regex` in `lib/git`, applied on both sides and without its `<type>/` anchor. So `--issue 12` flags `feat/12-x`, `fix/12`, `12-x`, `feat/x-12_y` and `feat/012-x`, and not `feat/123-x`, `feat/312-x` or `feat/1x2`. The number is the only value of the caller's that is ever put in a jq program, which is safe because it is digits only; without `--issue` the test is the literal `false` (test "pr list --issue flags a head branch that holds the number with no digit on either side, however the number is written, and nothing without --issue").
5. Nothing is printed until the whole answer has been checked in bash: the first line must be a number, at most `PR_LIST_LIMIT`, and equal to the number of rows after it, so a row that a value managed to add is refused rather than printed; each row must start with a number; and with `--head` the head field of each row must be exactly the value given, whatever `gh` matched. Anything else dies with `gh returned an unexpected result for the open pull requests of <repo>` (tests "pr list prints nothing and exits 1 when gh's answer is not a count and that many rows, each starting with a number" and "pr list --head prints nothing and exits 1 when gh answers with a pull request of any other head branch").

`pr checks` (`pr_checks`) only reads, through `gh api`, and never waits or polls:

1. `parse_pr_checks_options`, `require` and `require_one_checks_target` check the options (exit 2), then `require_gh`.
2. `resolve_checks_head` sets `HEAD_SHA`, the commit judged, and `RULES_BRANCH`, the branch whose required checks apply: for `--pr`, `repos/<repo>/pulls/<n>`, where `<n>` is the number without its leading zeros (see [Running it](#running-it)), gives `head.sha` (the PR's `headRefOid`) and `base.ref`; for `--branch`, `repos/<repo>/branches/<name>` (`read_branch`) gives the tip (`commit.sha`) and the branch is the one given; for `--sha`, the SHA is used as given and `repos/<repo>` gives the `default_branch`. A head that is not 40 lower-case hexadecimal digits, or a branch from GitHub that fails `valid_branch_name` (one git itself would not allow), is a runtime failure (`gh returned an unexpected ...`); every other branch name is percent-encoded by `branch_path` in the paths below. A PR, branch or repository that answers 404 dies with `was not found`.
3. `read_required_checks <repo> <branch>` fills `REQUIRED_CHECKS` (an associative array keyed by the check's name and the app it must come from, empty for any source, so the two sources are merged without duplicates) from the classic branch protection, read from the branch itself (`repos/<repo>/branches/<branch>`, its `protection.required_status_checks`: each `checks[]` entry with its `app_id`, where null or -1 means any source (`app_of`, a jq definition in `APP_OF_DEF` shared with the rulesets read), and any name in `contexts` that `checks` does not have, for any source, because GitHub repeats every name of `checks` in `contexts`; a branch with no protection lists none, and an `enforcement_level` of `off` requires nothing whatever it lists, as `fetch_branch_requires_status_checks` in `lib/github` reads it), and from the rulesets that apply to the branch (`repos/<repo>/rules/branches/<branch>`, every page, the `required_status_checks` rules, each with its `integration_id`, which a rule that accepts any source leaves out (`app_of` again)). A required check pinned to an app is satisfied only by a check run from that app (its `app.id`), though a failed commit status of its name still fails it (a passing or pending status is not counted), and one for any source by every result of that name (test "pr checks matches a required check pinned to an app only with a run from that app, and any other by name alone"); a name required from two apps is judged, and printed, once for each, each line pinned to an app as `<name> (app <id>)` (test "pr checks shows the app of each line of a name required more than once, keeping four columns"). The branch is read rather than `repos/<repo>/branches/<branch>/protection/required_status_checks` because that endpoint needs admin rights and answers `HTTP 403` to an ordinary token, while the branch needs only read access (test "pr checks needs no admin rights: the protection endpoint, which answers 403 without them, is never read"). A 404 on the branch (it does not exist) is exit 1 with `cfwf: the branch whose required checks apply was not found in <repo>` (test "pr checks treats a missing PR, base branch or commit as a runtime failure (exit 1)"); any other failure of the branch read is exit 1, and so is any failed read of the rulesets, a 404 included (`cfwf: could not read the rulesets of <repo>: <gh's error>`): GitHub answers a branch no ruleset applies to, whether or not it exists, with `200` and an empty list ("The branch does not need to exist", in the REST reference for "Get rules for a branch"), so a 404 means the rules could not be read, and taking it as none would judge only the checks that happen to be present (test "pr checks treats a 404 from the rulesets as a failed read (exit 1), never as no rulesets"). The one exception is a repository whose plan has no rulesets (a private repository on GitHub Free): GitHub refuses the read with `HTTP 403` and `Upgrade to GitHub Pro or make this repository public to enable this feature.` (seen in practice; the REST reference lists only `200`), and a repository that cannot have rulesets has none, so an error holding that text (`RULESETS_NOT_IN_PLAN`) and `(HTTP 403)` is read as no rulesets and the classic branch protection alone is judged; any other 403, such as `Resource not accessible by integration`, is still exit 1 (test "pr checks reads the 403 for a plan with no rulesets as no rulesets, and still judges the branch protection"). The branch is read by `read_branch`, which asks for its tip and its protection in one call and keeps them (`BRANCH_TIP`, `PROTECTION_ROWS`) for the run, so with `--branch`, where `resolve_checks_head` has already read the branch for its tip, it is read once and the tip and protection come from the same state (test "pr checks --branch judges the branch tip against that branch's required checks"); a failed read names whichever caller made it first. This function does not depend on how the head was found, and is kept apart from the rest so a command that prints a branch's required checks can reuse it.
4. `read_check_results` reads every check run of `HEAD_SHA` (`repos/<repo>/commits/<sha>/check-runs?per_page=100&filter=all`, `--paginate`; `filter=all`, because GitHub's default `filter=latest` would drop runs before `record_check_rows` could compare them by id) and its combined status (`repos/<repo>/commits/<sha>/status`, `--paginate`). The `--jq` filters emit one row per result, fields joined by `\x1f` (`ROW_SEPARATOR`; a tab would not do, because `read` collapses consecutive tabs and an empty field would shift the rest), with each name given as two fields by the jq definition `name_fields` (`NAME_FIELDS_DEF`): the name as JSON, its key, so every name is grouped and matched against the required checks byte for byte and no key holds a newline or `\x1f`, and the name with each control character turned into a space (the jq definition `printable`, in `PRINTABLE_DEF`, which `issue view` and `issue plan-status` use too), which is only printed. The control characters are written out as a range (`[\x{0}-\x{1f}\x{7f}-\x{9f}]`: C0, tab and newline included, DEL, and C1), not as `[[:cntrl:]]`, because `gh --jq` runs gojq, whose Go regular expressions read `[[:cntrl:]]` as ASCII only and would print a C1 control such as U+009B (CSI, a terminal escape) as it is; jq reads the written-out range the same way, so the test stub, which runs jq, and `gh` agree (test "pr checks prints every C0, DEL and C1 control in a check name as a space, and keeps U+00A0, just past C1"). Two names that differ only in a control character, or a check really named like the `<name> (app <id>)` label of a name required twice, can print alike but are still judged, and counted, apart (tests "pr checks keeps apart two names that differ only in a control character, though both print alike" and "pr checks judges a check really named like the app label of a name required twice apart from that name"). Each check run row also carries its `app.id` and the kind `run` (a commit status row has the kind `status`). `record_check_rows` keeps the result with the highest id in each group: the runs of one name from one app, across every check suite on the commit. So a re-run (a later attempt, in the same check suite) and a new run of the workflow in a new check suite (a PR marked ready, reopened or relabelled, which with `concurrency: cancel-in-progress` leaves the older run `cancelled`) both replace the run before it whatever order GitHub lists them in, as GitHub's merge gate is seen to take only the latest run of a required name, while a run of the same name from another app is a result of its own and is still judged (test "pr checks judges the newest run of a name from each app across check suites, and fails a name when that of any app failed"). `record_check_rows` sorts the rows by id (`sort -k4,4n`, in the C locale) and takes them oldest first, so each row is newer than the run its group holds and replaces it, with one exception: a `skipped` check run did not run, so it replaces only a stored `skipped` or `cancelled` run (`GROUP_YIELDS`), never one that ran and decided (any other conclusion, or none yet). So a skipped run decides a group only when the group holds nothing else, or when the newest run that ran before it was cancelled (test "pr checks never lets a skipped run replace a run of its name that ran, whatever their order"). Taking the rows in id order is what makes the result the same whatever order GitHub lists them in; comparing two rows at a time could not, because a skipped run must lose to an older failure but win over an older cancelled run that superseded that failure. This is for a newer check suite whose job skips itself, such as a `labeled` event on a workflow whose job's `if:` is false for that label, which would otherwise hide an older failure. A `cancelled` run is different: `concurrency: cancel-in-progress` cancels the older run when that newer suite starts, so the cancelled run was superseded rather than decided, and the newer skipped run passes the check, as GitHub's merge gate does (test "pr checks lets a newer skipped run replace an older cancelled one, which was superseded, not decided, whatever their order"). A cancelled run with no newer skipped run, or one newer than the skipped run, still fails. Keeping an older failure over a newer skipped run is deliberately stricter than GitHub, which documents `skipped` as satisfying a required check ("Required status checks must have a `successful`, `skipped`, or `neutral` status", About protected branches) and does not document which of two runs of one name its merge gate takes, so GitHub may well let the newer skipped run through. `neutral` is a result the check chose after it ran, so it is not treated this way. Newest is creation order (the id). GitHub's documentation does not say how the merge gate orders runs of one name; field reports and the check-runs `filter=latest` wording ("Filters check runs by their completed_at timestamp") suggest it takes the one that finished last. The two agree when a newer run supersedes an older one, the case this is for, and creation order keeps a newer run that has not finished `pending` rather than needing a rule for a run with no `completed_at`. A commit status has no app id and is a group of its own (its kind), so it never replaces a check run: GitHub requires both to pass when a check run and a commit status share a required name (test "pr checks judges commit statuses, and a check run and a status of the same name must both pass"). `record_check_rows` also indexes the groups of each name in `NAME_GROUPS` (one per line), so `judge_check` reads only that name's groups. `judge_check` then gives a name its verdict from the newest result of each of its groups: `fail` when any failed, otherwise `pending` when any is pending, otherwise `pass`, with the `completed_at` and id of the result that decided it.
5. `check_run_verdict`: no conclusion is `pending`; `success`, `skipped` and `neutral` are `pass`; every other conclusion (`failure`, `cancelled`, `timed_out`, `action_required`, `startup_failure`, `stale`, or one GitHub adds later) is `fail`. Only the conclusion is looked at, so a run with a conclusion but a status that still says `in_progress` or `queued` is finished, and a `completed` run with no conclusion is pending. `commit_status_verdict`: `success` is `pass`, `pending` is `pending`, anything else (`failure`, `error`) is `fail`.
6. `report_checks` judges the required checks, or every check when `--all` is given or the branch requires none, plus every required check with no result, as `pending`. `--all` only adds a line for each name no required check has: a name that is required is judged only as required, so a run of it from an app other than the one it is pinned to is not judged even with `--all`, as GitHub ignores it too. It prints the lines and the summary only now, after every read has succeeded, and exits 5, 3, 4 or 0, in that order of precedence.

`api_read <failure> <endpoint> <filter> [gh options]` runs every one of these reads, the read of the comment `pr reply` answers and the `repo collaborators` read through `gh_capture`, so the answer is in `GH_OUTPUT`. It returns 1 on `HTTP 404`, and on `HTTP 422` with `No commit found for SHA` (how a commit endpoint answers a `--sha` that is not in the repository), so each caller says what not found means, and dies with `cfwf: <failure>: <gh's first error line>` on any other failure (`gh_failure_text`: printable characters only, at most 200), so a proxy 502, a rate limit or a refused token is exit 1 and never a check result.

`pr view` (`pr_view`) makes one read, `gh pr view <n> --repo <repo> --json <fields> --jq <program>`, and nothing else:

1. `PR_VIEW_FIELDS` is the one table of the command: each row is a field's name, the gh `--json` fields it is read from and the jq expression of its value, in the order the fields are printed. `PR_VIEW_FIELD_NAMES` (the valid `--field` values) is taken from it, and `PR_VIEW_ALONE_FIELDS` names the two that are not key and value lines.
2. `resolve_view_fields` runs before any `gh` call: with no `--field` it takes every field but those two, it refuses `files` or `body` asked for with another field, and it sets `VIEW_NAMES` and `VIEW_EXPRESSIONS` (in table order) and `VIEW_JSON_FIELDS`. So gh is asked only for what the request prints: the default call does not fetch `body` or `files`, and `commits` is fetched only when `commit-authors` is printed, which the default output does (test "pr view asks gh only for the fields the request needs: no body or files by default, and commits only for commit-authors").
3. `print_view_lines` builds the program from fixed pieces only (`PRINTABLE_DEF`, then `("<name>\t" + ((<expression>) // "" | tostring | printable))` for each field), so a null value prints as empty and every value is made printable. No caller text ever goes into the program: a field name is one of the table's own.
4. `print_view_files` asks for `changedFiles` as the first line and the paths after it. gh lists only the first 100 files, so a pull request that changes more files than were listed is refused (`<repo>#<n> changes <a> files and gh listed only the first <b>, so none is printed`, exit 1): part of a list is never printed as the whole (test "pr view --field files refuses a list gh cut short (exit 1), never printing part of it as the whole").
5. `print_view_body` has jq put `\x1f` (`OUTPUT_END`, the mark `issue view` ends its output with) after the body and takes it off again before printing with `printf '%s'`, because command substitution (`gh_capture`) drops every trailing newline, the body's own included, unless something follows them (test "pr view --field body prints the body unchanged, byte for byte, with its tabs, blank lines, carriage returns and trailing newlines").
6. `read_pull_request` runs the call through `gh_capture`. gh answers a number that is not a pull request (a missing one, or an issue) with `Could not resolve to a PullRequest with the number`, the same text `--check` reads as not found, and that exits 9. Any other failure dies with `could not read <repo>#<n>: <gh's first error line>` (`gh_failure_text`), exit 1.

### Body leak check

`check_body_for_leaks <body-path> <owner/repo>` is the one check every command that posts a body runs before `gh` is called. `resolve_body` runs it as its last step, so resolving a body always checks it; today that is `issue create`, `comment add`, `pr reply` and `body check` (`body_check`), which stops there, so an agent can test a body first. It runs on the exact file `gh` is given: the private temporary copy `resolve_body` makes of the body file or of stdin. The rules apply in this order and the first that matches wins (test "the first rule that matches wins, in the order token, host path, control character, invalid UTF-8, too long"):

1. `token` (`TOKEN_PATTERN`): `ghp_`, `gho_`, `ghs_`, `ghu_`, `ghr_` (GitHub's personal, OAuth, server, user-to-server and refresh tokens), `glpat-`, `sk-ant-` (an Anthropic key), `sk-proj-` (an OpenAI project key), or `xoxa-`, `xoxb-`, `xoxp-`, `xoxr-` or `xoxs-` (Slack; the same forms `notify-unit-failure` redacts) at a word start followed by a token character, a key of an exact length (`FIXED_LENGTH_KEY_PATTERN`) at a word start, `github_pat_` followed by a letter, a digit or `_`, `AKIA` or `ASIA` (an AWS long-term or temporary access key id) and 16 upper-case letters or digits, a `-----BEGIN ... PRIVATE KEY-----` line, a Discord webhook URL (`DISCORD_WEBHOOK_PATTERN`: `discord.com` or `discordapp.com`, then `/api/webhooks/`, a numeric id, `/` and a token character, since the URL itself is the credential), a password in a URL (`URL_CREDENTIAL_PATTERN`) or after the user name `x-access-token` (`ACCESS_TOKEN_USER_PATTERN`, at a word start), an `Authorization` header with a value (`AUTHORIZATION_HEADER_PATTERN`), a bearer token (`BEARER_PATTERN`), or a secret assignment (`SECRET_ASSIGNMENT_PATTERN`). A prefix on its own (`ghp_` or `sk-ant-` with nothing after) passes. A key of an exact length is `npm_` and 36 letters or digits (an npm token), `AIza` and 35 letters, digits, `_` or `-` (a Google API key), or `sk-` and 48 letters or digits (a legacy OpenAI key); the count is what tells it from ordinary text, so `npm_config_registry` and a key one character short pass, and the word start `TOKEN_PATTERN` puts before the prefix is why a word that ends in `sk-` passes. The pattern has no right boundary, so a longer run is refused too: its first characters are a key. A password in a URL is `://`, a user name that may be empty, `:`, one or more characters that are not whitespace, `/`, `?`, `#`, `@`, a double quote or a backtick (`PASSWORD_PATTERN`; any number of `@` may come before them, as described below), and `@`, as in `<scheme>://<user>:<password>@<host>`; a URL with a port and no password passes even with an `@` in its path, query or fragment, because whitespace, `/`, `?` or `#` ends its host first, and a URL has to percent-encode those characters in a password, so a password written with one of them unencoded is not seen. A double quote and a backtick are left out for the same reason (no URL holds either unencoded) and because they close a URL written in JSON or as Markdown code, so `{"url":"http://localhost:8080","email":"someone@example.com"}` passes. Three limits remain. A URL with a port that is followed, with no whitespace between, by other punctuation and then an `@` (`http://localhost:8080,someone@example.com`, or the same in single quotes) is refused, because a comma, a semicolon, a bracket and a single quote may all stand in a password; put a space after the URL. A user name may hold an unencoded `@`, as an email address used as the login of a mail server URL does (`smtp://someone@example.com:<secret>@smtp.example.com`), so `URL_USER_PATTERN` leaves out only whitespace, `/`, `?`, `#` and `:`, and the first colon after `://` is where the password starts, unless whitespace, `/`, `?` or `#` comes first and ends the host, so a colon and an `@` in the query or fragment of a URL with no port and no path (`https://example.com?at=12:30&to=someone@example.com`) pass; `ssh://git@example.com:22/path` and `docker://alpine@sha256:<digest>` still pass, having no `@` after the colon, and a URL with a user name, a port and no password is refused in the same case as one with no user name (`ssh://git@localhost:22,someone@example.com`). A Docker reference written as a URL with both a tag and a digest and no `/` in its name (`docker://alpine:3.20@sha256:<digest>`) is refused: the name, the colon, the tag and the `@` have the shape of a user name, a password and the `@` before a host, and the check fails closed rather than exempt a form a password could be written in. Give the digest alone, write the reference without `docker://`, or describe it in words; a reference whose name holds a `/` (a registry or a namespace before the image, as in `docker://library/alpine:3.20@sha256:<digest>`) passes, because the `/` ends the host before the colon. And only the password is examined, never the user name, so a key written as the user name with an empty password or none is not seen unless it has one of the prefixes above. `x-access-token:` followed by such a password and `@` is the form a Git remote URL carries a GitHub token in, and is refused with or without the scheme before it. The password is not examined beyond that: whatever stands between the colon and the `@` is one, so a placeholder (`<password>`, `***`, `xxx`, the word `password`, `$NAME` or `${...}`) is refused like a real password, and nothing has to tell the two apart. A documentation example therefore has to describe such a URL in words ("a URL with the user name and the password before the host") rather than write one out. A password may hold an unencoded `@`, since the last `@` before the host ends is the one that ends it, and may start with one, so the colon of either form may be followed by any number of them before the password's other characters (`CREDENTIAL_PASSWORD_PATTERN`): `https://user:@<secret>@example.com` is refused. A reference written with whitespace in it, such as `${{ secrets.NAME }}` after `x-access-token:`, is not seen, for the same reason as a password with unencoded whitespace; written without the spaces it is refused. A URL with a user name and no password (`ssh://git@example.com`, `https://user@example.com`, `git@example.com:owner/repo.git`) passes, as does one with only a port (`http://localhost:8080/path`). An empty password (`https://user:@example.com/path`) passes too, because no second `@` follows it before whitespace, `/`, `?` or `#`; one in a URL with no path that is followed, with no whitespace between, by other punctuation and then an `@` (`https://user:@localhost,someone@example.com`) is refused like the port URL above (tests "issue create refuses a body with any token form with exit 8, naming the rule and line only, before calling gh" and "body check passes a key one character short, a key prefix inside a word, an Authorization header name with no value and a URL with no password"). An `Authorization` header with a value is the name (in any of the spellings `Authorization`, `authorization` or `AUTHORIZATION`, optionally quoted as in JSON, where the closing quote may be escaped with a backslash as in JSON held inside a string), `:` or `=`, and one character that is not whitespace. The scheme is never looked at, so Basic, Bearer, Digest, Negotiate, `token` and a request signature are all refused, and so is a placeholder or a reference (`Authorization: Bearer <token>`, `Authorization: Basic $CREDENTIALS`), for the same reason as a URL password. Nothing has to come before the name, so `Proxy-Authorization` is refused too. The name with no value passes: "the Authorization header" in prose, or `Authorization:` at the end of a line. A colon followed by a closing quote or backtick (an empty JSON value, or the name and its colon written as Markdown code) has a character after it and is refused, so write the name without its colon. A documentation example has to describe the header in words ("an Authorization header with a Bearer token") rather than write one out (the same two tests). A bearer token is `Bearer` anywhere, in a header or not, followed by 20 or more token characters with at least one digit among them (`bearer_value_pattern`, which builds that as an alternation on where the first digit is, because ERE has no lookahead); so `Bearer <token>` and prose such as "a Bearer token" or "Bearer authentication-mechanism-description" pass, since words joined by hyphens hold no digit, while a real token, which almost always holds one, is refused wherever its first digit is; as does a webhook URL with `<id>` or `<token>` placeholders (test "body check passes a token prefix, Bearer with no token after it or a webhook placeholder with no secret after it"). A secret assignment is `NAME=value` where `NAME` is upper case and is `TOKEN`, `SECRET`, `KEY` or `PASSWORD`, or ends in one of them after an underscore (`GH_TOKEN`, `DB_PASSWORD`), so a name that merely ends in the letters, such as `MONKEY=banana`, passes; and where the value is not empty and, after an optional opening quote, does not start with `$`, so a variable or secret reference (`${GH_TOKEN}`, `${{ secrets.GITHUB_TOKEN }}`, `$API_KEY`, `"${GH_TOKEN}"`) passes (tests "issue create refuses a body with any token form with exit 8, naming the rule and line only, before calling gh" and "body check passes a NAME=value whose name only ends in the letters, or whose value is a reference"). Lower-case names (`api_key=...`) and the `NAME: value` and `NAME = value` forms are not checked: they are common in ordinary prose and configuration examples, and matching them would refuse far more harmless text than it would catch.
2. `host path` (`HOST_PATH_PATTERN`): `/home/`, `/Users/` (a macOS home), `/root/`, `/run/user/` (which holds the Claude scratchpad) or `/tmp/` at the start of a path: the start of a line, or after any byte but a letter, a digit, `.`, `~` or `-`. The boundary is a negative one so that whatever can come before a path in prose, markdown or a URL starts one: whitespace, quotes, a backtick, brackets, `=`, `:` (`PATH=/usr/bin:/home/...`), `,`, `*` and `_` (markdown emphasis), `<`, `|`, and `/` (so `file:///home/...` is caught by its third slash). A byte that can continue a word or a relative path does not, so `./tmp/x`, `../home/x`, `example.com/home/x` and the relative `tmp/x` pass. Nor does a boundary byte other than `/` that itself follows a `/`: it is a segment of a URL path, so `https://example.com/_/home/x` passes, while a slash always starts one (`///home/x`, `//home/x` after a word) and the same byte at a line start or after anything else still does (`_/home/x_`, `a,/run/user/...`; tests "body check passes a body with no leaks, printing nothing and calling gh for nothing" and "body check still refuses a host path after punctuation that does not follow a slash, at a line start, or after a run of slashes"). A home, root's home, a user runtime directory or tmp deeper inside an absolute path is a host path too, the same directories as at the start of a path (`/mnt/c/Users/...` under WSL, `/var/home/...` on Fedora Atomic, `/var/root/...` and `/private/tmp/...` on macOS, and `/var/tmp/...`), because each still names a user or a host temporary file. For that shape the path must not follow a `/` (unless as `file://`), so the path of a URL, whose host follows `//`, passes: `https://example.com/home/x` and `http://h/tmp/x` are not host paths. The third shape is a Windows drive path under `Users` (`C:\Users\...`, `C:/Users/...` or an escaped `C:\\Users\\...`, in any case), after a byte that is not a letter or digit (test "body check refuses a home, a user runtime directory or tmp deeper inside an absolute path, and a Windows drive path under Users"). `~/` is not a host path: a home-relative path names no user and is common in documentation, and the rule lists absolute paths only; `~/tmp/x` passes for the same reason. Upper-case `/Users/` is matched exactly, so the API path `/users/` passes.
3. `control character` (`CONTROL_PATTERN`): a C0 control other than tab and newline (carriage return included, so a body with CRLF line endings is refused at its first line), DEL, or a C1 control (U+0080 to U+009F, which UTF-8 writes as the byte 0xC2 followed by 0x80 to 0x9F). Nothing else is refused: other invisible or formatting characters, such as the bidi overrides, pass (test "body check passes a body with no leaks, printing nothing and calling gh for nothing" includes U+202E). The scan is byte by byte in the C locale, which finds exactly these in UTF-8 text because every byte of a multi-byte character is 0x80 or above, and 0xC2 only ever starts a character; NUL is mapped to 0x01 with `tr` first, since no pattern can hold a NUL; `write_nul_free_copy` writes that copy to a temporary file (`SCAN_TMP`, removed by the `EXIT` trap) rather than piping it, so a failed copy stops the check.
4. `invalid UTF-8` (`UTF8_LINE_PATTERN`): a line that is not valid UTF-8 as a whole, matched with `grep -xv` (`refuse_first_match` takes extra `grep` options for this) against the RFC 3629 table of ASCII (but NUL) and two, three and four byte sequences, with no overlong form, no surrogate and nothing above U+10FFFF, byte by byte in the C locale on the NUL-free copy, so it gives the same answer under any `grep` locale. It refuses a raw byte from another encoding, such as a lone 0x85 from Latin-1 or CP1252 text (the C1 scan above sees a C1 control only in its UTF-8 form), and a broken sequence. It runs before `too long` because `wc -m` does not count a byte that is not valid UTF-8, so such a body could pass the length check and be turned away by GitHub after labels were created (test "a body, a title or a label that is not valid UTF-8 is refused with exit 8, naming only the line, before calling gh"). Like the rules before it, it applies to a title and a label too.
5. `too long`: more than `BODY_LIMIT` (65536) characters, counted with `wc -m` in `C.UTF-8` after `require_utf8_locale`. A count that fails, or that is not a number, dies with `cfwf: could not count the characters of the body` (exit 1) rather than being reported as `too long` (test "a character count that fails or is not a number is a runtime failure (exit 1), never too long or a pass").
6. `private repository` (`check_repository_references`), only when the target repository is public. `repository_references` collects, with line numbers and with any trailing full stops, then `.git`, then `.wiki` (in any case, so a link to a wiki or its clone URL names the repository it belongs to; test "a link to the target's own wiki passes with no lookup, and another repository's wiki is looked up as that repository") dropped by `print_reference` (which skips a link left with no repository name, such as `github.com/<owner>/...`), links (`REPOSITORY_LINK_PREFIX`): `github.com/<owner>/<repo>` (with or without `www.`), `api.github.com/repos/<owner>/<repo>`, `raw.githubusercontent.com/<owner>/<repo>` and `codeload.github.com/<owner>/<repo>` (archive downloads), and `git@github.com:<owner>/<repo>` SSH remotes, with the owner taken as the segment after the last `/` or `:` before the repository. A link must not follow a letter, digit, `.` or `-`, so a host that only ends in the same letters (`notgithub.com`) and GitHub's other hosts (`docs.github.com`, and `gist.github.com`, whose paths are gists, not repositories) are not links; dots after such a boundary, or two dots anywhere (an ellipsis, as in `see...github.com/<owner>/<repo>`), are punctuation and do not stop a link (test "a gist, another GitHub host or a host that only ends in github.com is not a repository link, and passes with no lookup"). It also collects standalone `<owner>/<repo>#<n>` cross-references and `<owner>/<repo>@<sha>` commit autolinks (`<sha>` 7 to 40 hex digits; test "a public target refuses a codeload link or an owner/repo@sha autolink to a private repository"), and bare `<owner>/<repo>` words whose owner is in `CFWF_PRIVATE_OWNERS`. A bare `owner/repo` of any other owner is never looked at, because a relative path such as `test/cfwf.bats` has the same shape. A bare word preceded by a letter, digit, `_`, `.`, `/` or `-` (`REFERENCE_BOUNDARY`) is part of a longer path or host name and is skipped, except that underscores which open Markdown emphasis are passed over when the byte before them is a boundary, so `_<owner>/<repo>#5_` and `__<owner>/<repo>__` are read as the reference inside them (`*`, as in `*<owner>/<repo>#5*`, is a boundary byte itself), while `my_<owner>/<repo>#5` is not a reference (test "a reference in Markdown emphasis is still checked, and an underscore inside a word is not a boundary"). A cross-reference must also be standalone: `is_cross_reference` refuses one whose preceding byte is in `URL_PATH_BYTES` (`~`, `@`, `#`, `%`, `?`, `&`, `=` or `+`), which put it inside a URL, a query or another path, or when it is a `:` and the "owner" after it is all digits (a port, as in `localhost:8080/api#1`), while a reference straight after any other colon is still one (`Related:<owner>/<repo>#5`, as with `Fixes: <owner>/<repo>#5`; the `://` of a URL leaves a slash, not a colon, before its path), and a bare word of a listed private owner after one of those bytes (`REPO=<owner>/<repo>`) is still checked. A `#<n>` or `@<sha>` is a reference only when no letter, digit, `_` or `-` follows the digits, other than the underscores that close Markdown emphasis at the end of the word (`<owner>/<repo>#5_` is one, `<owner>/<repo>#5_x` is not) (so `owner/action@v4` and a 41-digit `@` value are not; test "an @ that is not followed by a commit SHA alone, or a host that only ends in codeload.github.com, passes with no lookup"), so a heading anchor such as `docs/setup.md#1-prerequisites`, a branch such as `fix/foo#12abc`, and `owner/repo#1` inside a query string are not looked up (test "a #n inside a longer word, or an owner/repo#n inside a path or a URL, is not a cross-reference, and passes with no lookup"). `grep` cannot look ahead, so the scan takes in every word character and `-` after a `#` or `@` and `repository_references` keeps only a `#` followed by digits alone or an `@` followed by a SHA alone; none of those characters can start the next reference, so references side by side are each still found (test "standalone cross-references side by side are each checked, so a private one after a public one is refused"). A `#<n>` on a word that looks like a file and ends there, such as `src/app.ts#12`, is still a cross-reference and is looked up. They are checked in line order. A reference to the target itself (compared without regard to case) passes, and so does a link whose first segment is one of GitHub's own pages (`GITHUB_RESERVED_PATHS`, for example `orgs`, `settings`, `advisories`, `stars`, `copilot` or `team`; test "links to GitHub's other pages, such as starred lists, Copilot and the team plan, pass with no lookup"). That list includes `user-attachments`, where GitHub stores every pasted image or file (`github.com/user-attachments/assets/<id>` and `.../files/<id>/<name>`), so a pasted screenshot passes on a public target; `assets` is not listed, because it is a real account, and an attachment under `<owner>/<repo>/assets/` is that repository's link like any other. GitHub's image hosts (`user-images.githubusercontent.com`, `private-user-images.githubusercontent.com`) are not repository links at all (test "a pasted image or file, or one on GitHub's image hosts, passes on a public target with no lookup"). The target's visibility is looked up only when the text names some other repository, so text that names none costs no `gh` call, and a `--repo` GitHub does not show the caller (a typo, a renamed repository, no access) is only a runtime failure once the text names another repository: text that names no other repository passes with no lookup of the target at all (test "a target repository GitHub does not show the caller is never looked up when the text names no other repository"). `cfwf help body` says the same. An owner in `CFWF_PRIVATE_OWNERS` is refused with no lookup. Any other repository is looked up with `gh repo view <repo> --json visibility` by `repository_is_public`, once per repository per run (`REPOSITORY_VISIBILITY`, keyed in lower case). `PUBLIC` passes; `PRIVATE` and `INTERNAL` are private; a lookup that fails with `Could not resolve to a Repository` or `HTTP 404` means the caller cannot see it, which counts as private for a repository the text names; any other failure, or an answer that is none of those, dies (exit 1). That includes `HTTP 403` (access denied, for example by an organisation that enforces SAML SSO, or by a proxy): it fails closed as a runtime failure, so nothing is posted, rather than counting as private (test "a visibility lookup that fails is a runtime failure (exit 1), never a pass or a refusal"). `look_up_visibility` makes the read through `read_repository`, the one `gh repo view` reader, which `repo view` shares (see [Repository and account lookups](#repository-and-account-lookups)), and records each answer (`public`, `private` or `missing`; tests "a visibility lookup gh answers with HTTP 404 is the one gh repo view of the visibility alone, and counts as a repository the caller cannot see: refused when the text names it, exit 1 when it is the target" and "a visibility lookup whose answer is not a visibility is a runtime failure (exit 1), never a pass or a refusal, for a repository the text names and for the target"); `repository_is_public` reads it for a named repository and `target_is_public` for the target, where `missing` dies with `cfwf: the repository <owner/repo> was not found, or the caller cannot see it` (exit 1), because counting an unresolvable target (a typo, a renamed repository, no access) as private would skip every private repository check and pass the text (test "a target repository GitHub does not show the caller is a runtime failure (exit 1), never a pass").

Every scan fails closed. `refuse_first_match` hands `grep` the file path (not a redirection, which would turn an unreadable file into "no match") and `repository_references` takes each `grep`'s output whole and checks its status rather than reading it through a process substitution, so a `grep` that fails (status 2) dies with `cfwf: could not scan the body` (exit 1) and never counts as a pass (test "a grep that fails while scanning the body is a runtime failure (exit 1), never a pass").

`check_value_for_leaks <value> <owner/repo> <title|label>` applies the same rules to a `--title` or a `--label` (`check_text_patterns` for token, host path, control character and invalid UTF-8, then `check_repository_references`), all but `too long`, since `validate_visible_text` has already limited its length. It writes the value to a temporary file (`VALUE_TMP`, removed by the `EXIT` trap), because the rules read a file and the reference scan reads it twice. A visibility lookup that fails for a repository a title or label names says `named in the title` or `named in the label` rather than a line.

`refuse_text` prints `cfwf: <subject> refused: <rule>`, where the subject is `body`, `title` or `label`. A body's refusal ends with `(line <n>)`, except for `too long` (every other rule has a line); a title or label is one line and has none. It exits 8. It never prints the matched text or the repository it named, because echoing a token into a transcript is itself the leak. A failed lookup of a referenced repository names only its line for the same reason.

External tools: `bash` 4+ (associative arrays and `${var,,}`; it is not POSIX sh), `gh` (authenticated), `mktemp`, `grep`, `sort`, `tr` and `wc`. The script runs `main` only when executed (`BASH_SOURCE[0] = $0`), so `test/status-mapping-parity.bats` can `source` it to reach `WORKFLOW_STATES`.

Shipping: the Dockerfile copies it to `/usr/local/bin/cfwf` (root:root, 0755) and checks presence and the executable bit. It is on `claude-hooks/command-allowlist` and `Bash(cfwf *)` is in `claude-settings.json`, kept in step by `test/command-allowlist-parity.bats`. On a host, `install-claude-hooks` runs `install_cfwf`: `install -m 0755` into `${CFWF_BIN_DIR:-/usr/local/bin}`, retried under `sudo` as root:root if that fails, and otherwise it prints the exact command to run. It is a copy, not a symlink, so re-run the installer after changing `cfwf`. The installer refuses to run inside a Claude Code session. Tests: `test/install-claude-hooks.bats` ("main installs cfwf into the shared bin directory, executable by everyone", "re-running main replaces an older installed cfwf", the sudo tests and "dies when the source cfwf script is missing").

### Pull request comments and replies

`pr comments` (`pr_comments`) prints everything said on a pull request, and `pr reply` (`pr_reply`) answers one inline comment. Both take `--repo` and `--pr` (each once, `--pr` above 0, leading zeros dropped) through `assign_pr_comment_option`; `pr reply` also takes `--comment-id` (1 to 19 digits, above 0, leading zeros dropped) and `--body-file`. Nothing else is an option: `--json`, `--jq`, `--template`, `--unresolved` and `--body` are unknown (tests "pr comments usage errors exit 2 before any gh call" and "pr reply usage errors exit 2 before any gh call"). `cmd_pr` hands both to `dispatch_subcommand`, as it does `checks`, `view` and `list`, which sets `CURRENT_COMMAND` to `pr comments` or `pr reply` so that help and usage errors print that command's usage (`usage_pr_comments`, `usage_pr_reply`). `cfwf help pr comments` and `cfwf help pr reply` print the same usage: `usage_for` has an arm for each of the two pairs, as it has for `pr view` and `pr list`, and `cfwf help pr` is still the usage of `pr checks` (test "pr comments and pr reply help describe the format, the exit codes and the retry rule, and call no gh").

#### The format of `pr comments`

Blocks separated by one blank line: the pull request, each top-level comment (oldest first), each review (oldest first), each review thread followed by its inline comments in thread order, then the summary. Apart from the empty lines between blocks, only three kinds of line exist:

- a header line, `key<TAB>value`, with exactly one tab. The value has every control character (C0, a tab and a newline included, DEL and C1) printed as a space by the jq definition `printable` (`PRINTABLE_DEF`), and U+2028 and U+2029 too (`text` in `PR_DISCUSSION_FILTER`, which every header value goes through): a file's path is not GitHub's to choose, and a reader that splits lines on those two would otherwise see a new line start inside a value (test "pr comments keeps a path, a login, a state and a URL with control characters or Unicode line ends on one line each"). An empty value prints the key and the tab alone;
- a body line, `|` and a space followed by the line, or `|` alone for an empty line;
- the last line, `summary comments=<a> reviews=<b> reviews-empty=<c> threads=<d> unresolved=<e> inline=<f>`, the only line that is not empty and has neither a tab nor a leading `|`.

The blocks and their keys, in order:

| Block | Keys |
| --- | --- |
| pull request | `pr` (`<owner/repo>#<n>`), `review-decision` (GitHub's value, empty when there is none) |
| top-level comment | `comment` (its id), `author`, `association`, `created-at`, `minimized`, `url`, `lines` |
| review | `review` (its id), `author`, `association`, `state`, `submitted-at`, `url`, `lines` |
| thread | `thread` (the id of its first inline comment), `resolved`, `outdated`, `path`, `line` (empty for an outdated or file-level thread), `original-line`, `comments` |
| inline comment | `inline` (its id), `in-reply-to` (empty on a thread's first comment), `review` (the review it belongs to), `author`, `association`, `created-at`, `minimized`, `url`, `lines` |

`resolved`, `outdated` and `minimized` are `yes` or `no`; a hidden comment is printed like any other. `lines` is the number of body lines that follow, so a reader can tell a lost line. A body (`body_lines` in `PR_DISCUSSION_FILTER`) has its trailing line ends dropped and is split on newlines; a carriage return at the end of a line is removed, and each line then goes through the same `text` as a header value, so every other control character in it, a tab included, and U+2028 and U+2029, is printed as a space. So a body line never holds a tab and never starts with anything but `|`: no body can pass for a header, a blank separator or the summary (test "pr comments lets no body pass for a header, a block, a blank separator or the summary"). Bidi formatting characters are not changed, as the leak check does not refuse them either. A body of blank lines only, or none at all, has `lines` 0 (test "pr comments counts the body lines it prints: none for an empty body or one of blank lines only"). The summary also marks the output as whole: a copy without it was cut off.

A review whose body is blank and whose state is `COMMENTED` is only the wrapper GitHub puts around inline comments. It is not printed; it is counted as `reviews-empty`, and its inline comments are printed in their threads, each naming its review (test "pr comments prints a review with a body or a state of its own, and only counts the blank COMMENTED wrapper").

`author` is who GitHub says wrote the item. `pr comments` makes no trust decision: the caller decides whose words to act on. The value is built from GraphQL's `__typename` and `login`: a user is the login alone (`credfeto`); a bot is `app/<slug>` (`app/github-actions`; REST calls the same account `<slug>[bot]`); any other kind is `<kind in lower case>/<login>` (`mannequin/<login>`, `organization/<login>`); a deleted account, for which GitHub gives no author, is an empty value, never `ghost`, which is a real login. No login holds a slash, so only a user can print as a user's login, and a bot whose slug is a user's login prints differently from that user (test "pr comments prints a user as the login, a bot as app/slug, any other kind as kind/login and a deleted account as empty").

#### How `pr comments` reads

1. One GraphQL query text (`PR_DISCUSSION_QUERY`) on `repository.pullRequest(number:)` asks for `reviewDecision` and three lists, `comments`, `reviews` and `reviewThreads`, each `first:100` with `totalCount` and `pageInfo{hasNextPage endCursor}`, and inside each thread `comments(first:100)` with the same. GraphQL is the one source because a thread's resolved state exists only there, it gives one form of author for all three lists, and every inline comment arrives grouped in its thread with `replyTo`. `--repo` is split into the `o` and `r` variables and is never a `gh` flag; the number goes with `-F`.
2. Each list has its own cursor variable (`commentsAfter`, `reviewsAfter`, `threadsAfter`) and its own `@include(if:)` switch (`comments`, `reviews`, `threads`). `read_discussion_page` sends the same query text again with only the unfinished lists switched on, until none has another page. `gh api graphql --paginate` is not used: it drives a single cursor. A cursor is sent only for a list that has one, and only after it matches `^[A-Za-z0-9+/=_-]+$`. GitHub leaves a list that is switched off out of its answer, which the filter reads as empty (tests "pr comments reads each list to its last page, asking each later page for that list alone" and "pr comments pages all three lists at once, each with its own cursor, and prints every item once in order").
3. Every id is `fullDatabaseId`, the id the REST API uses, so the `inline` id printed is the id `pr reply` takes, and each is checked to be digits (test "pr comments takes every id from fullDatabaseId, so one above 2^31 is whole and is the id pr reply takes").
4. The `--jq` program (`PR_DISCUSSION_FILTER`, after `PRINTABLE_DEF`) prints every block ready to print. Before each it prints a control row, which starts with `\x1e` (`CONTROL_ROW`), names the block's kind and ends with its id, its fields joined by `\x1f` (`ROW_SEPARATOR`); the last row of a page gives the review decision and, for each list, its `totalCount`, the number of nodes on the page, `hasNextPage` and `endCursor`. No printed line can start with `\x1e`: both bytes are control characters, printed as a space wherever GitHub's text holds them. `record_discussion_page` counts the blocks and keeps each one whole with the list it is of (`keep_page_block`), and `add_page_text` adds a page's blocks to each list's text once. A line is only ever added to its own block, so adding one costs no more the more the page holds or the more has been read: appending every line to one text for the list copies that text each time, which takes minutes for a page of a hundred comments of a thousand lines each. A row must have exactly the number of fields its kind has (`DISCUSSION_ROW_FIELDS`; the page row `PAGE_ROW_FIELDS`, ending in `end`), because `read` drops an empty last field: without the count, an inline comment with no id of its own would pass with its review's id standing in for it.
5. Nothing is printed until every page has been read and checked. A page must end with its control row, and the blocks received for each list must equal the nodes jq counted (`record_page_row`, `record_list_page`); a thread's own count of its comments must equal the comments that came with it (`record_thread_row`), and the inline blocks received must equal those; after the last page the items gathered for each list must equal its `totalCount` (the one read last, so a list that grew while it was read and was read whole still prints). Any mismatch is exit 1 with `the comments of <repo>#<n> changed or were cut short while they were read; nothing is printed` (test "pr comments prints nothing when a list is shorter than GitHub's count of it, or a page lost a block"). An answer that is not what the filter prints is exit 1 with `gh returned an unexpected answer` (test "pr comments refuses an answer that is not the pages it asked for, printing nothing").
6. A cursor GitHub repeats, and a list of more than 100 pages (`DISCUSSION_PAGE_LIMIT`), are exit 1, so a read can never loop (test "pr comments stops on a cursor that repeats, a cursor it would not send, and a list of more than 100 pages").
7. A thread with more than 100 comments (its own `hasNextPage`) is exit 1, naming the thread's first comment, and nothing is printed. Such a thread is very rare, and a loud failure cannot hide feedback the way a cut-off thread would (test "pr comments refuses a thread with more comments than one page holds, naming it, and prints nothing").
8. `Could not resolve to a PullRequest with the number` in what `gh` wrote to stderr is exit 9. Only stderr is read for it, so the same words in a comment's body, which `gh` can print on stdout when a call fails, are never taken for it. Any other failure, a repository that is not found included, is exit 1 with the first line of `gh`'s error (test "pr comments exits 9 for a number that is not a pull request, and 1 for any other failed read").

#### How `pr reply` posts

1. The options are checked (exit 2), then `resolve_body` copies the body to a private file and runs the [body leak check](#body-leak-check) on it before any other `gh` call: a refused body is exit 8, and a blank, missing or unreadable one exit 1 (tests "pr reply refuses a leaking body with exit 8, naming the rule and line only, before reading or posting anything" and "pr reply refuses a blank, missing or unreadable body as a runtime failure, without calling gh").
2. `resolve_reply_root` reads `repos/<repo>/pulls/comments/<id>` through `api_read`, taking `id`, `in_reply_to_id` and `pull_request_url` as one row (`FIELDS_ROW_DEF`, which the answer to the `POST` is read with too; the row ends with `end`, so one cut short is refused). The repository is in the path, so a comment of another repository is a 404. A 404, which is also how GitHub answers the id of a top-level comment or of a review, is exit 9. The comment must be on that pull request: only the number that ends `pull_request_url` is compared, never the host or the repository, because `gh` may be reached through a proxy that answers with its own host. Otherwise it is exit 9, `the comment <id> is not an inline review comment of <repo>#<n>` (test "pr reply exits 9 without posting for an id that is not an inline comment of that pull request").
3. When the comment is itself a reply, the reply is posted to the thread's first comment (`in_reply_to_id`), because GitHub refuses a reply to a reply and a thread is flat. So every `inline` id `pr comments` prints is one `pr reply` takes (test "pr reply posts to the thread's first comment when the id is that of a reply, and drops leading zeros").
4. `post_reply` makes one `POST` to `repos/<repo>/pulls/<n>/comments/<first comment's id>/replies` with `-F "body=@<private copy>"` through `gh_capture`. The comment replied to is in the path, digits only, so no field can be sent with the wrong type, and `gh` reads the body from the checked copy, so it is never an argument (test "pr reply reads the comment, posts the body once to the thread's first comment and prints the new comment").
5. The answer's `id` must be digits and its `html_url` must look like `https://<host>/<owner>/<repo>/pull/<n>#discussion_r<id>` (the host and the repository are not compared, as for `issue create`). Then three lines are printed, with the keys `pr comments` uses: `inline` (the new comment), `in-reply-to` (the thread's first comment) and `url`.
6. It never posts twice. When the `POST` fails and the first line of `gh`'s error ends with `(HTTP 400)`, `401`, `403`, `404`, `410` or `422` (`REPLY_REFUSED_PATTERN`), GitHub turned the request down as it stood and the message is `the reply was not posted`. After any other failure (a timeout, a 5xx, any other 4xx, an answer that is not the new comment) the message is `the reply may have been posted`, because it may be there (test "pr reply never posts twice: a status that refuses the post says not posted, and any other failure that it may have been posted"). The list is short on purpose: saying "not posted" of a reply that is there leads to a duplicate, while saying "may have been posted" of one that is not costs the caller a look. A caller must not run it again blindly: run `pr comments`, look in the thread for an `inline` block with the same `in-reply-to` and its own `author` value (its login, or `app/<slug>` when it posts as an app), allow a few seconds for GitHub to catch up, and post again only if it is not there.

The plan sign-off keywords are not refused in a reply. The repository's tooling reads a plan sign-off only from an issue's top-level comments, so an inline reply can never be taken for one (test "pr reply posts a body holding a plan sign-off keyword: only an issue's top-level comments are read for one"). `pr reply` does not read or change whether the thread is resolved.

### Repository and account lookups

`repo view` (`repo_view`), `repo collaborators` (`repo_collaborators`) and `auth status` (`auth_status`) only read. None looks at the working repository or the Workflow board, and none uses exit 9: a repository that is not there, or that the caller cannot see, is exit 1 with `cfwf: the repository <owner/repo> was not found, or the caller cannot see it`, the text `pr checks --sha` and the body leak check use. Every answer from GitHub is judged by `matches_pattern`, which matches in the C locale as `validate` does, so the result is the same whatever locale `cfwf` is run in.

`read_repository <repository> <json-fields> <jq-filter>` is the one `gh repo view` reader: it runs `gh repo view <repository> --json <fields> --jq <filter>` through `gh_capture`, leaves the output in `GH_OUTPUT`, and returns 0 when the read worked, 1 when `gh`'s error holds `Could not resolve to a Repository` or `HTTP 404` (GitHub answers a repository that is not there and one the caller cannot see alike), and 2 on any other failure. Each caller says what a missing repository means to it: `look_up_visibility`, which calls it with `visibility` and `.visibility` (so its `gh` call is `repo view <repo> --json visibility --jq .visibility`, made once per repository per run), records `missing`, and `repo view` dies.

`repo view` makes one read and nothing else:

1. `parse_command_options` with `assign_repository_option` and `require` check the option (exit 2), then `require_gh`.
2. `read_repository` with the fields `defaultBranchRef,description,visibility,mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed` (`REPO_VIEW_FIELDS`) and a fixed program (`REPO_VIEW_PROGRAM`): `PRINTABLE_DEF`, then one `<field>\t<value>` line for each field, each value made a string and printable, a null printed as empty, and each merge method `yes` for true, `no` for false and empty for anything else (test "repo view prints the six fields in their fixed order, GitHub's own visibility and yes or no for each merge method, and nothing gh was not asked for, from one gh repo view call for exactly its six fields"). `gh repo view --json` is used, not the REST endpoint `repos/<repo>`: REST gives `allow_merge_commit`, `allow_squash_merge` and `allow_rebase_merge` as null to a caller without push access, while `gh repo view` gives a read-only caller the real values. A null is still printed as an empty value, as a guard, and so are the default branch of an empty repository and a description that is not set (test "repo view prints an empty value, keeping the tab, for the default branch of an empty repository, a description that is null and a merge method GitHub did not give"). The default branch is not passed through `valid_branch_name`, so a pure read does not need git.
3. A missing repository dies with the repository message; any other failure dies with `could not read <repo>: <gh's first error line>` (`gh_failure_text`), so a proxy 502 or an access-denied 403 is never read as a missing repository (tests "repo view exits 1 with the repository message and nothing on stdout for a repository GitHub does not show the caller, whichever of its two answers gh gives" and "repo view exits 1 quoting only the first line of gh's error, and prints nothing, for any other failed read").
4. Nothing is printed until the whole answer matches `REPO_VIEW_PATTERN`: the six lines in their order, each of one field, a visibility of upper-case letters and `_`, and `yes`, `no` or nothing for each merge method. Anything else dies with `gh returned an unexpected result for <repo>` (test "repo view prints nothing and exits 1 when gh's answer is not its six lines in order, each one field, with a visibility and yes, no or nothing for each merge method, and prints an answer that is"). A tab, a newline, a carriage return, DEL or a C1 control in the description or the branch name is a space before the line is built, so no value can add a line or pass for another field (test "repo view keeps a description or a default branch holding a tab, a newline, a carriage return, a C1 control or a whole forged line on one line of two fields").

`repo collaborators` makes one paged REST read through `api_read`:

1. `parse_command_options` with `assign_repository_option` and `require` check the option (exit 2), then `require_gh`.
2. `repos/<repo>/collaborators?per_page=100` with `--paginate`. REST is used because `role_name` exists only there. With `--paginate`, `gh` runs the `--jq` program on each page, so the program prints one row for each collaborator (`[.login, .role_name, "end"] | fields_row`, the `FIELDS_ROW_DEF` row `pr reply` reads a comment with) and never a count: a count line would be printed once a page. No affiliation is sent, so GitHub's default, all, applies (test "repo collaborators prints each login and role sorted by login in the C locale, - for a role GitHub left out or left empty, from one paged read of 100 a page").
3. GitHub shows the collaborators only to a caller with push access, and answers any other with `HTTP 403` and `Must have push access to view repository collaborators.` (seen against a public repository the caller cannot push to). `api_read` dies on it with `could not list the collaborators of <repo>: <gh's first error line>`, so no access is never an empty list (test "repo collaborators exits 1 quoting GitHub's HTTP 403 for a caller without push access, never printing an empty list"). A 404 is the repository message; any other failure is `api_read`'s own (test "repo collaborators exits 1 with the repository message for a 404, and quoting only the first line of gh's error for any other failed read, printing nothing").
4. Nothing is printed until every row has been checked in bash. An empty answer is an empty list (exit 0). More than `COLLABORATOR_LIMIT` rows is exit 1 (test "repo collaborators prints exactly 1000 collaborators, and with 1001 prints none and exits 1"). Each row must have its three fields, the last being `end`, and its login must match `LOGIN_PATTERN` (letters, digits, `-` and `_`, with `[bot]` after an app's), otherwise the run dies with `gh returned an unexpected result for the collaborators of <repo>` (test "repo collaborators prints nothing and exits 1 for a login that is not a login or is missing, or a row that does not have exactly its fields, and prints a row that has them"). A role is free text (a custom role is named by the organisation), so it is made printable, cannot add a line or a field (test "repo collaborators keeps a role holding a tab, a newline or a whole forged row on one line of two fields"), and is `-` when empty.
5. The lines are sorted by `sort` in the C locale. A tab sorts before every character a login can hold, so sorting the whole line sorts by login.

`auth status` is the environment probe, and replaces `gh auth status`, `gh --version`, `gh api user --jq .login` and an echo of `GH_HOST`:

1. `parse_command_options` with `assign_auth_option` checks the options (exit 2), then `require_gh`.
2. `host` is `GH_HOST`, or `github.com` (`gh`'s default) when it is unset or empty. It must match `HOST_NAME_PATTERN` (letters, digits, `.` and `-`, then an optional `:port`); anything else is exit 1 with `GH_HOST is not a host name, with or without a port`, before any `gh` call and without echoing it (test "auth status prints a GH_HOST that is a host name, with or without a port, and exits 1 without echoing one that is not, before any gh call"). `gh`'s own configured default host is not consulted, because reading it means `gh auth status` or `gh config`.
3. `gh --version` (no network) gives the version: the first line must match `GH_VERSION_PATTERN` (`gh version <number>`, as in `gh version 2.102.0 (2026-09-30)`), and only the number is kept.
4. `gh api user --jq '.login // ""'` gives the login, which must match `LOGIN_PATTERN`. The `// ""` is there because a null would otherwise print as the word `null`, which has the shape of a login. The read is made every time, and is what proves the credential works (tests "auth status prints the login, github.com for a GH_HOST that is unset or empty, and the gh version, and nothing else of gh's answers, calling only gh --version and gh api user" and "auth status prints nothing and exits 1 for a gh version, a login or a rate limit that is not what it expects, and takes a version of two or more parts, with a suffix or with nothing after it").
5. Only with `--rate-limit`, `read_rate_limit` runs `gh api rate_limit` with a program that prints one `FIELDS_ROW_DEF` row: `remaining`, `limit` and `reset` of `.resources.core` and then of `.resources.graphql`, each reset turned from epoch seconds into ISO 8601 UTC by `todate` (a reset that is not a number is left empty, so it is refused below rather than failing inside jq). The row must be digits, digits and such a time, twice, then `end`, otherwise the run dies with `gh returned an unexpected result for the rate limit` (test "auth status --rate-limit adds the remaining, limit and reset of the core and graphql limits, each reset as ISO 8601 in UTC, from one more call, gh api rate_limit"). It is opt-in so that the default probe is three lines and does not fail because a second endpoint did.
6. `auth_read_failed` ends a failed read of the user or of the rate limit: `cfwf: not authenticated` when `gh`'s stderr holds `HTTP 401` (GitHub refused the credential) or `gh auth login` (`gh`'s own prompt when it has none), and otherwise the read's own message with `gh`'s first error line. Only stderr is read for it (`GH_ERROR`), so the same words in an answer's body, which `gh` can print on stdout when a call fails, are never taken for it (tests "auth status exits 1 with not authenticated, and prints nothing, for an HTTP 401 or gh's own prompt to log in, from the user read or the rate limit read, and never for the same words on the stdout of a read that failed otherwise" and "auth status exits 1 with the failed read's own message, quoting only the first line of gh's error, and prints nothing, when gh --version, the user read or the rate limit read fails otherwise").
7. Nothing is printed until every read asked for has succeeded and been checked.

What `auth status` never does is as much a part of it as what it prints. It runs `gh` only as `gh --version`, `gh api user` and `gh api rate_limit`: never `gh auth status` (which can print the token), `gh auth token` or `gh config`, and never with `-i`, `--include` or `--verbose` (which print request or response headers) or `--hostname`, so no token, header or configuration value is ever in its hands. It prints no environment variable but `GH_HOST`. Token scopes are left out for the same reason: their only token-free source is a response header. The test "auth status never prints a token from its environment or from GitHub's answer, on stdout or stderr, whether it works or fails, and never runs gh auth, gh config or gh with an option that shows headers or names a host" pins all of it.

`auth status` does not read or write the login cache. The hook `cache-gh-lookups` (see [claude-hooks](../claude-hooks.md)) rewrites a bare Bash-tool call of exactly `gh api user --jq '.login'` into a read of a cache file that `containers/agent/entrypoint.sh` seeds at container start. A `gh` call made inside `cfwf` is never seen by that hook, and the probe deliberately asks GitHub each time: it has to prove the credential works now, and `cfwf` is also installed on hosts where that cache does not exist.

### Why it is built this way

GitHub's project API lags behind writes, and `gh project` has no command that reads a single item. Those facts drive every design decision (issue #1491; the `--set` and `--check` help text and the comments in the script say the same):

- No read-back after `--set`. A read straight after a write cannot tell a lost write from lag: `gh project item-list` can leave out a newly added item for minutes, and a change to an existing item can take seconds to show even on a direct read. An earlier version read the value back and reported a false "did not persist" for writes that had persisted. Now `--set` trusts `gh project item-edit`'s exit status and prints `Set <url> to <status>`. This is the shared rule ([GitHub State Lags Behind Writes](../../../ai/global/github-cli.instructions.md#github-state-lags-behind-writes-mandatory)): a write whose call succeeded is done, so it is not re-read to confirm and not polled.
- `--check` reads one item directly. `gh project item-list` is a listing of the whole board: it is paged, capped (`-L`), can be slow, and is slow to show a new item. A single-item GraphQL query avoids the paging and the cap. This and the `pr comments` read (see [Pull request comments and replies](#pull-request-comments-and-replies)) are the only `gh api graphql` uses in `cfwf`. Both only read: neither query contains a mutation (tests "no gh api graphql call ever carries a mutation" and "pr comments pages all three lists at once, each with its own cursor, and prints every item once in order"). Every board write is a native `gh project` command, and every other write a native `gh` command or a REST call (`pr reply`).
- A fallback to listing exists, with a visible warning, so a GraphQL failure does not make `--check` useless. The listing asks for 10000 items (`ITEM_LIMIT`) rather than accept a default page; the field listing asks for 100 (`FIELD_LIMIT`, test "--set reads the project's fields with a limit above the default page size of 30").
- The list of workflow states is duplicated. `cfwf` is copied alone into the image and cannot source `lib/`, so `WORKFLOW_STATES` is a copy of the states in `lib/project-status`. `test/status-mapping-parity.bats` is the only thing stopping them drifting apart.
- Both fields are read and written while boards are converted one repository at a time. A converted board has only `Status`; a board not yet converted keeps its workflow in `Workflow Status`, and its `Status` holds Todo, In Progress or Done, which are not workflow states. Preferring `Status` when it has the state, and the Workflow Status value when that field exists, means `cfwf` gives the right answer on either kind of board without knowing which it is.
- The standard labels are hard-coded too. `cfwf` is installed standalone and cannot read `.github/labels.yml`, so `STANDARD_LABELS` is a copy of every label in that file (`name|colour|description` per line), used to give a label that `issue create` has to create its standard colour and description. `test/standard-labels-parity.bats` compares the copy with the file in both directions, so adding, removing or editing a label in `.github/labels.yml` fails that test until `STANDARD_LABELS` is updated to match.
- `issue create` validates and resolves everything before it writes anything. The board is resolved before the labels or the issue, because a half-done create (labels made, no issue; or an issue with no board item) is what the command exists to prevent. The one write that can still fail afterwards is the board write, and the `EXIT` trap in `cleanup` then names the issue URL on any non-zero exit after the issue was created.
- The body, from a file or from stdin, goes to a private temporary file and `gh` is handed that copy, never the path or `-` it came from: the body has to be checked before anything is created, stdin can only be read once, and a file could be rewritten between the check and the post, which several network calls separate. One `cleanup` function, installed as the `EXIT` trap in `main`, removes every temporary file and prints the created-issue notice. Each temporary file is made on first use by `ensure_temp_file <variable>`, which stores the path in the named global, at most once per run: `GH_ERR_FILE` (the one file `gh`'s stderr is captured in, shared by every `gh_capture` call: the GraphQL query, the visibility lookup, the issue read of `issue view` and `issue plan-status`, the `repo view` read, the `repo collaborators` read, the reads of `auth status`, the `pr checks` reads, the `pr view` read, the `pr list` read, the `pr comments` read and the read and the post of `pr reply`), `BODY_PATH_TMP` (the body copy), `SCAN_TMP` and `VALUE_TMP` (see [Body leak check](#body-leak-check)).
- Labels are created rather than left to fail. `gh issue create --label` refuses a label the repository does not have, so `ensure_labels_exist` creates it first. It never edits or deletes an existing label. A repository with more labels than `LABEL_LIMIT` (1000) would look as if it lacked one, which is why an `already exists` answer to a create is tolerated.
- The body leak check has no bypass option. A bypass flag would be used whenever the check got in the way, which is exactly when it matters; a body that has to discuss a path shape should use a placeholder instead (`<repo>/...` rather than a real `/home/...` path). Its refusal has its own exit code (8) so a caller can tell "fix the body" apart from a runtime failure (1) or a bad call (2).
- `pr list` replaces `gh pr list --json <fields> --jq <filter>`, which agents ran before starting work on an issue (to find a pull request that already covers it) and to find the pull request of the current branch, each time with a filter written afresh and often without `--repo`. It never prints part of a list: `gh pr list` stops at its `--limit` without saying so (30 by default), so `pr list` asks for one more than it will print and refuses when it gets it. The author is read from `gh pr list` and not from the REST pulls endpoint, because REST names the same author `github-actions[bot]`, while the agents' rules name it `app/github-actions`, as `gh` does. The flag is set on the login alone and not on `is_bot`: every app is a bot, so `is_bot` does not tell one app from another, and no user login can hold a `/`, so the login cannot be imitated. Draft is a column of its own (`draft` or `ready`) and not a flag, because each flag says how to read a line as earlier work on an issue (`issue` and `github-actions` point to it, `fork` says the line proves none), while draft is state, and a bare `yes` or `no` would mean nothing on a line with no header. The base branch is a column because it tells a pull request against `main` from a stacked one, and adding a column later would change the format.
- `repo view`, `repo collaborators` and `auth status` replace the raw `gh repo view <repo> --json defaultBranchRef,description`, `gh repo view <repo> --json mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed`, `gh api repos/<repo>/collaborators --jq '.[].login'`, `gh api user --jq '.login'`, `gh auth status` and `gh --version` an agent ran, each with fields and a filter written afresh. `repo view` has no `--field`: one call returns everything, so there is nothing to save by naming fields, and visibility is printed because it comes with the same read. `repo collaborators` prints the role beside the login because whether to trust what someone wrote differs between `read` and `write`, and a caller that wants the logins alone takes the first column. There is no separate login command: the first line of `auth status` is the login. The probe is a fixed read because `gh auth status` can print the token in some modes, and because a `GH_HOST` override typed by an agent tries to go round the proxy: `auth status` only reports the host it was given. Not authenticated has no exit code of its own (it is exit 1, told from any other failure by its message), so the exit codes stay the ones every other command uses.
- `pr checks` replaces `gh pr checks`, whose exit status is 1 both for a failed check and for an auth, proxy or network error, whose state column lags through the proxy, and whose `--json` exits 0 whatever the checks say. It resolves the head commit first and reads the check runs and statuses of that commit alone (both endpoints answer for one commit), so a run on an older, force-pushed head is never counted, and it keeps "a check failed" (3) apart from "the read failed" (1). It has no `--watch`: a caller polls by running it again (with Monitor or ScheduleWakeup), so it never holds the session. A conclusion it does not know is `fail`, not `pass`, so a new GitHub conclusion can never let a PR through.
- `pr view` replaces `gh pr view --json <fields> --jq <filter>`, the most used raw `gh` read, where callers guessed field names (`headOid`, `draft`), wrote a fresh filter each time and left out `--repo`. It has a fixed set of field names, one fixed output format and no `--json` or `--jq`, so one allowlist entry covers every read and no filter text comes from the caller. It keeps not found (9) apart from a failed read (1), which `gh pr view` reports alike as exit 1. `body` and `files` are only printed alone because neither fits a key and value line: a body is free text of any number of lines, and printing it beside other fields would let it imitate them.
- `issue create` never rewrites an existing item's status: it always sets `Not Started`, because a new issue can only be at the start, so it has no `--status`. `docs/workflow-board.md` describes the board.

## Tests

`test/cfwf.bats` covers help and usage, `--set`, `--check`, `closing-issue-labels`, `issue create`, `issue view`, `issue plan-status`, `repo view`, `repo collaborators`, `auth status`, `comment add`, `pr checks`, `pr view`, `pr list`, `pr comments`, `pr reply` and the body leak check (`body check`, and `issue create` refusing a leaking body before any write). `test/standard-labels-parity.bats` sources `cfwf` in a subshell and compares `STANDARD_LABELS` with `.github/labels.yml` (parsed with `awk`; the file is a flat list of name/colour/description triples), and checks that all five priorities are standard labels. `test/status-mapping-parity.bats` sources `cfwf` in a subshell and checks that `WORKFLOW_STATES`, `project_status_names` (lib/project-status) and `_WF_STATUS_ORDER` list the same ten states in the same order (tests "there are ten workflow states", "cfwf lists the same workflow states as lib/project-status, in the same order (#1519)" and "_WF_STATUS_ORDER lists the same workflow states as lib/project-status, in the same order (#1519)").

How `gh` is faked: `setup` builds a `gh` PATH stub with `make_stub_multiline gh`. The stub logs every call's arguments to `GH_LOG`, then routes on the first two words (`repo view`, `project field-list`, `project item-add`, `project item-edit`, `project item-list`, `api graphql`, `pr view`, `pr list`, `issue view`, `label list`, `label create`, `issue create`, `pr comment`, `issue comment`, `api user`, `api rate_limit` and `--version` alone). For every call except `project item-edit` and `label create` (which only succeed or fail), `issue create` (which prints the contents of `issue-create.out`), the two comment calls (which print `comment.out`) and `--version` (which prints `gh-version.out`) it applies the call's own `--jq` filter to a fixture file in `GH_FIXTURES` (`issue-view-<n>.json` for `issue view`), using the real `jq`, so the filters `cfwf` sends are run against real-shaped JSON and not merely recorded. Any other call exits 99 with `gh stub: unexpected call`.

- Failure switches are marker files in `GH_FIXTURES`: `repo-view.fail`, `item-add.fail`, `item-edit.fail`, `item-edit.failfield` (fails only the edit for the field id it contains), `item-list.fail`, `graphql.fail` (stderr text and exit 1), `graphql.failout` (stdout text and exit 1) and `graphql.stderr` (stderr noise on success), `label-list.fail`, `label-list.rewrite` (its content is a path, which the label listing overwrites, so a test can rewrite the body file after the check), `label-create.fail` (its content is the stderr text), `issue-create.fail`, `repository-<owner>_<repo>.fail` (its content is the stderr text of the `repo view` read, exit 1) and `repository-<owner>_<repo>.out` (printed as that read's answer, with no jq), `collaborators.out` (printed as the answer to the collaborators read, with no jq), `api-user.fail` and `api-rate_limit.fail` (the stderr text, exit 1; an empty file is a failure with nothing on stderr), `api-user.failout` and `api-rate_limit.failout` (the stdout text of that failing call, used only beside the `.fail`) and `gh-version.fail` (the stderr text of a failing `gh --version`). `issue create` also copies the file it is given with `--body-file` to `issue-body.txt`, so a test can check the body gh received.
- `repo view ... --json visibility` is routed on its own: it applies the filter to `visibility-<owner>_<repo>.json` (lower-cased, the path given by `visibility_fixture` and written by `write_visibility`), fails with an `HTTP 502` text when `visibility-<owner>_<repo>.fail` exists (`fail_visibility`), and with no fixture at all answers `Could not resolve to a Repository`, as GitHub does for a repository the caller cannot see.
- Fixture helpers for the leak check: `write_leak_body` (the leak on line 3), `run_body_check`, `run_issue_create_leak` (`issue create` on that body), `assert_refused` (given the run's status, stdout and stderr as arguments, so the helper never reads bats' run globals: exit 8, the rule and line 3 on stderr, nothing on stdout, the matched text absent), `visibility_lookups` and `leak_tokens`, which builds every token form from pieces so that no secret scanner flags the test file. `leak_tokens` ends with `leak_credential_forms` (the keys of an exact length, the `Authorization` headers, the URL passwords and the `x-access-token` user), and `harmless_credential_shapes` is its passing counterpart; both use `run_of` (a character repeated a number of times) and `url_with_password`, so neither a key nor a URL with a password is ever written out in the test file. A new credential form needs an entry in each.
- `pr view` answers from `pr-view.json`, cut down to the fields the call names in `--json` (written to `pr-view.asked.json`) before the call's `--jq` program is applied, as gh hands a program only the fields asked for; so a program that reads a field `cfwf` did not ask for sees null and its test fails. It fails with the text in `pr-view.fail` on stderr (exit 1) when that file exists, and with no fixture exits 1 with no output. `closing-issue-labels` is served by the same route.

Marker files: `pr-list.fail` (its content is the stderr text, exit 1), `pr-list.ignore-head` (`--head` is not applied, as if `gh` matched more than the exact name) and `pr-list.out` (its content is printed as the answer, with no jq, for an answer the program could not give).

- The `repo view` read is recognised before the routing, by a guard line that matches a `repo view` call whose `--json` list starts with `defaultBranchRef,`, so the `repo view` route for the board and the visibility lookup is as it was. ## Changing it safely

- Run `shellcheck containers/base/development-full/scripts/cfwf` and keep it clean.
- Run `bats test/cfwf.bats`, and `bats test/status-mapping-parity.bats` if the state list or the sourcing guard changed.
- Mutation-check any new test: break the code (for example swap `pullRequest` and `issue`, drop the `project.id` filter, or add a read-back after `--set`) and confirm the test fails, then restore it.
- A new command that posts a body must take it only from `--body-file <file|->`, call `resolve_body` (which runs `check_body_for_leaks`) before its first `gh` write, say so and mention exit 8 in its help text, and have a test proving the check runs before any write. Any other text it sends to GitHub, such as a title or a label, goes through `check_value_for_leaks` at the same point.
- Update the help text (`usage_workflow_status`, `usage_general`, `usage_closing_issue_labels`, `usage_issue_create`, `usage_issue_view`, `usage_issue_plan_status`, `usage_body`, `usage_repo_view`, `usage_repo_collaborators`, `usage_auth`, `usage_comment`, `usage_pr`, `usage_pr_view`, `usage_pr_list`, `usage_pr_comments`, `usage_pr_reply`; `usage_issue` prints the three `issue` ones together and `usage_repo` the two `repo` ones, and `usage_for` maps each command and each `<command> <subcommand>` to its text) and the test that pins it ("the workflow-status help states that --set does not read back, ...").
- Update `containers/base/development-full/README.md` (the `cfwf` bullet), `docs/workflow-board.md` (the Status field section) and the `Dockerfile` comment when the surface changes. ## Gotchas

GitHub API behaviour `cfwf` has to allow for, and what it does:

- Lagging reads after a write. `--check` straight after `--set` may still show the old value, even from the direct query. `--set` therefore never verifies. A `--check` that disagrees with a write just made is lag, not a failed write: do not poll `--check` or repeat the write; if a later step needs the value, check again at that step (and repeat the write only if the value is still wrong then). `--check` itself does not retry.
- Listing omits new items. Only the fallback path lists the board, so the fallback can report `is not on project` for an item that was just added. The direct query does not depend on the listing.
- Listing paging and cap. The fallback reads at most 10000 items (`ITEM_LIMIT`), so on a bigger board it can miss an item. The direct query is not capped in this way. Field lists ask for 100 (`FIELD_LIMIT`).
- No single-item read in `gh project`. That is why `--check` uses GraphQL; `projectItems(first:100)` in that query is itself a limit on how many projects one issue can be on.
- `gh` may print to stderr even on success (test "anything gh writes to stderr on a successful read never ends up in the value"), and with `--jq` it can put an error body on stdout, which is why `gh_failure_text` falls back to stdout.
- The test stub does not run the GraphQL query text on a server, so a wrong field name in the query would not be caught by the tests. The tests assert on the logged query text and the filter only.
- The same holds for `pr comments`: its stub answers from fixtures and never runs `PR_DISCUSSION_QUERY`, so the query text is asserted, not executed. The filter is run, but by `jq`, while `gh --jq` runs gojq, and the two are different programs with different regular expression engines: gojq, for one, splits an empty string into one empty string where `jq` gives none (seen with `gh` 2.102 and `jq` 1.8). `PR_DISCUSSION_FILTER` is written so that it does not depend on such differences: an explicit test for an empty body, `\z` for the end of the text, and a written-out character class rather than `\s` for blank. After changing the query or the filter, run `cfwf pr comments` against a real pull request with more than 100 reviews, and one with an empty review body.
- `pr comments` reads at most 100 inline comments of one thread and fails rather than print part of a longer one, and reads at most 100 pages (10000 items) of each list.
- `pr reply` says "not posted" only for the statuses in `REPLY_REFUSED_PATTERN`. A 408, a 409 or a 429 can come from a proxy between `gh` and GitHub, or from a limit, after the request was passed on, so those, like every status not in the list, say "may have been posted". Add a status to the list only when it cannot follow a post that was made.
- The REST repository endpoint (`repos/<repo>`) gives `allow_merge_commit`, `allow_squash_merge` and `allow_rebase_merge` as null to a caller without push access, which is why `repo view` reads through `gh repo view --json`, where a read-only caller gets the real values. An empty value on an `allow-` line still means not known, never `no`.
- GitHub lists a repository's collaborators only for a caller with push access, a public repository included, and answers anyone else with `HTTP 403`. `repo collaborators` is exit 1 there: it cannot be used to see who may write to a repository the caller only reads.
- The collaborators read has no total to check the rows against (REST gives none, and with `--paginate` the jq program runs on each page), so a list GitHub cut short without an error cannot be told from a whole one; a page that fails does fail the read. The limit of 1000 (`COLLABORATOR_LIMIT`) is checked after every page has been read, and there is no option to raise it.
- `auth status` reports the host `gh` is pointed at by `GH_HOST`, not who answers behind it: through a proxy the login and the rate limits are those of the credential the proxy uses. With no `GH_HOST` it prints `github.com`, `gh`'s default, even where `gh`'s own configuration names another default host, because reading that configuration is what the command exists to avoid.
- `auth status` prints any `GH_HOST` that has the shape of a host name, and a secret of that shape is not told apart from one: a value made only of letters, digits, `.` and `-` is printed as `host` whatever it is. A GitHub token is refused, because every form of one holds an underscore, but a key written with dashes alone (the Slack, GitLab and Anthropic prefixes the body leak check lists are of that kind) would be printed if someone put it in `GH_HOST`. The check keeps a value from adding a line or a field; it is not a leak check.
- `auth status` reads "not authenticated" from `gh`'s error text (`HTTP 401`, or `gh auth login` in its prompt). If `gh` rewords its prompt, a run with no credential is still exit 1, with `could not read the authenticated user: ...` in place of `not authenticated`.
- The test stub runs jq where `gh --jq` runs gojq, so the `repo view`, `repo collaborators` and `auth status` tests pin the programs, not the engine. After changing one, run the command against GitHub. The calls in them that an engine could read differently are `gsub` with a regular expression (in `printable`, which every value goes through and whose character range is written out so that jq and gojq read it alike) and `todate`, in the rate limit program; the rest is field access, `//`, `if`, `tostring`, `map`, `type` and joining.

Other things that bite:

- `--issue` with a pull request number (or the reverse) is "not on project", not an error, because `issue(number:)` resolves only issues and `pullRequest(number:)` only PRs.
- While a board still has a Workflow Status field (not converted yet, or a conversion that stopped part way), `--set` writes only that field and `--check` reads it, whatever `Status` holds. The two fields can therefore disagree until the board is converted; the Workflow Status value is the one that counts.
- `--status` is matched only against the ten workflow states, so `--status Todo` is `unknown --status` even on a board whose `Status` field still has a Todo option.
- Two open projects titled `Workflow` linked to a repository make `cfwf` refuse to guess. Close the old one.
- The item-listing JSON key used by the fallback for a Workflow Status field is `"workflow Status"` (with a lower-case `w`) as `gh` emits it, and `status` for the built-in field. If `gh` changes the first key, the fallback on a board not yet converted will read the built-in value, and so report `(unset)` for a Todo, In Progress or Done.
- Unknown options exit 2 before any `gh` call, so a typo never reaches `gh`; options after `--help` are never looked at.
- The leak check refuses a body that legitimately shows a host path or a `NAME=value` secret-shaped assignment (for example `GH_TOKEN=<token>` in documentation), or a URL with a made-up password or an `Authorization` header with a made-up value in it. Rewrite the body with a placeholder rather than looking for a way round the check; a URL with a password and an `Authorization` header with a value are refused even with a placeholder, so describe those in words.
- `issue view` and `issue plan-status` take an issue number only. `gh issue view` itself answers a pull request's number with the pull request, which is why both read the URL and exit 9 for one (test "issue view and issue plan-status exit 9 for a number that is no issue, or that is a pull request's").
- `issue plan-status` reports, it does not decide. A `yes` on a comment line is a keyword in a comment, from whoever wrote it; the caller must still check the login against its trusted list, and that `Blocked` is off, before treating a plan as signed off. It counts every comment, including one that is minimised or was edited after it was posted, and takes any comment with the heading line as a plan, whoever wrote it: a comment from anyone that holds the heading becomes the latest plan, and every sign-off after it then reads as being for it, so check `plan-by` too. `gh issue view --json comments` does not say when a comment was last edited, so a sign-off cannot be told apart from one given before the plan comment was edited; a caller that needs that must read the comment at the `plan-by` URL.
- `issue plan-status` is stricter about what a plan is than `oneshot`'s own check in `lib/github-status`, which takes the first comment with the heading anywhere in it, in any case and with other text on its line, and accepts more keywords. The two answer different callers (`oneshot`'s is not changed here), so do not expect them to agree on an unusual thread.
- The comments come from the one `gh issue view --json comments` call, which pages through the thread itself; a thread too long for `gh` to return whole would make `plan-status` miss comments, and it cannot tell.
- `pr list --head <branch>` can print more than one line: a pull request from a fork whose branch has the same name matches too. That line carries the `fork` flag, and a line with `fork` is never the pull request of a branch in this repository: ignore it when looking for your own branch's pull request.
- `pr list` lists at most 1000 open pull requests (`PR_LIST_LIMIT`) and fails (exit 1) when the read returns more; it has no option to page or to raise the limit. With `--head` the limit is on the pull requests of that branch, because `gh` filters on the head branch before it counts, so a branch can still be looked up in a repository with more than 1000 open pull requests (test "pr list prints exactly 1000 pull requests, and with more open prints none and exits 1").
- The `issue` flag of `pr list` marks a branch that holds the number, not one that is known to be for the issue: `--issue 12` also flags `chore/bump-12` and `feat/012-x`. Flagging more is the safe direction; the caller decides whether the pull request is earlier work on the issue.
- A `pr list` line flagged `fork` is a pull request anyone can open without access to the repository, on a branch named as they like (one holding any issue number, or the name of a branch in this repository) and with any title. So `issue` together with `fork` is no proof of earlier work on the issue, and neither is the title: do not skip an issue or take over a pull request on the strength of such a line. The help text says the same under `fork` and `--head` (pinned by the help test).
- The test stub runs jq where `gh --jq` runs gojq, so the `pr list` tests pin the program, not the engine.
- `pr checks` exits 5 straight after `gh pr ready` on a PR whose workflows wait for it to be ready: the head has no checks yet. That is not a pass; run it again later.
- `gh pr view` lists at most 100 files and reads at most 100 commits. `pr view --field files` checks the list against `changedFiles` and exits 1 rather than print part of it; use the files API for a larger pull request. `gh pr view --json` has no commit count field to check against (only the length of the list it cut, and a list of exactly 100 may be whole), so `commit-authors` on a pull request of more than 100 commits holds only the authors of the first 100, with no warning: for a pull request that may be that large, do not take a login missing from `commit-authors` as proof that it authored no commit.
- `labels`, `assignees` and `commit-authors` are comma-joined, so a label whose own name holds a comma cannot be told apart from two labels.
- The line format is safe for a reader that splits lines on a newline only (`cut`, `grep`, `awk`, bash `read` and `mapfile`): `PRINTABLE_DEF` turns the C0, DEL and C1 controls into spaces and leaves every other character, U+2028 and U+2029 (the Unicode line and paragraph separators) included, so a reader that also splits on those, such as Python's `str.splitlines()`, must split on `\n` instead. The same holds for the names `pr checks` prints.
- `merge-state` and `mergeable` are GitHub's own values and are `UNKNOWN` while GitHub is still working them out (straight after a push, and for a merged pull request); read them again later rather than treating `UNKNOWN` as a verdict.
- A new `pr view` field is one row in `PR_VIEW_FIELDS`, placed where it is to be printed, plus its line in `usage_pr_view` and in the table above; a field that is not a key and value line also goes in `PR_VIEW_ALONE_FIELDS` and needs its own printer.
- With `--branch`, a required check whose workflow runs only on pull requests (an `on: pull_request` job, or a job gated on the PR not being a draft) never gets a result on the branch's tip, so `pr checks` reports it as `pending` for ever and exits 4 however long a caller waits. That is expected, not a fault in `pr checks`: a branch tip has no pull request for such a job to run on. A caller should pass `--all` to see every other check on the tip with its actual result; a required name is still judged only as required, so these checks still show as `pending` and the exit is still 4, and the caller has to read the lines rather than the exit code.
- A check skipped while the PR was a draft counts as a pass, as GitHub counts it, when no run of its name has run on the head; once a post-ready run of that name is created it decides instead, so until then a caller that needs results from after the PR was marked ready must compare each line's `completed_at` with the time it was marked ready.
- A skipped run never replaces a run of its name that ran and decided, so `pr checks` fails a name whose older run failed (or timed out, or needs action), even where GitHub may let the newer skipped run satisfy the required check. It is deliberately stricter than GitHub's merge gate there. An older run that was cancelled (for example by `cancel-in-progress` when a label event started the newer suite) was superseded rather than decided, so the newer skipped run does replace it and the name passes, as on GitHub.
- The rulesets read recognises a plan with no rulesets only by GitHub's error text (`Upgrade to GitHub Pro or make this repository public`, with `HTTP 403`), which GitHub does not document; if GitHub rewords it, `pr checks` on such a repository fails with exit 1 (`could not read the rulesets`) rather than judging too few checks.
- A commit status carries no app id in the REST API, so it never satisfies a required check pinned to an app (a failed status of that name still fails it); such a check stays `pending` until a check run from that app reports, even where GitHub would accept a status the app set.
- A visibility lookup goes through the same `gh` (and any proxy) as everything else, so it can fail or be rate-limited; that is exit 1, never a silent pass. Only the not-found answer for a repository the text names is read as "private"; for the target it is exit 1. An access-denied answer (`HTTP 403`) is exit 1 for any repository, so a caller whose organisation enforces SSO gets a runtime failure, not a `private repository` refusal.
